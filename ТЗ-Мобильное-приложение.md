**Версия:** 1.0
**Дата:** 31.08.2026
**Статус:** Черновик
**Платформа:** Android (React Native / Expo)

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Наименование системы
Мобильное приложение «Цифровой чек-лист инженера» (далее — Приложение).

### 1.2. Назначение системы
Нативное мобильное приложение для Android, обеспечивающее работу инженера по техническому обслуживанию оборудования в полевых условиях: создание и ведение визитов, заполнение параметров оборудования, фотофиксация, работа офлайн, синхронизация с сервером при появлении сети.

### 1.3. Отношение к существующей системе
Приложение является **дополнительным клиентом** к существующему веб-приложению (PWA). Оба клиента работают с одним REST API. Функциональная логика (модели данных, бизнес-правила, валидация) — единая. Настоящее ТЗ описывает **мобильно-специфичные требования**; общие функциональные требования (формы параметров, типы задач, правила валидации) — в «Техническое задание.md» (раздел 4.1).

### 1.4. Цели проекта
- Обеспечить надёжную офлайн-работу без потери данных (SQLite вместо IndexedDB)
- Решить проблему потери сессии при Service Worker eviction
- Обеспечить надёжные push-уведомления через FCM
- Предоставить нативный доступ к камере (фонарик, фокус, зум) и GPS
- Упростить вход через биометрию (отпечаток/лицо) и PIN-код
- Публикация в Google Play для удобного распространения на рабочие устройства

### 1.5. Нормативные ссылки
- ФЗ-152 «О персональных данных»

- ПУЭ (Правила устройства электроустановок)

## 2. ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

| Термин | Определение |
|--------|-------------|
| **Визит** | Совокупность работ на одном объекте за одну смену (общее определение — из ТЗ ТО) |
| **Задача** | Единица обслуживания одной единицы оборудования (общее — из ТЗ ТО) |
| **SQLite** | Локальная реляционная база данных на устройстве — основное хранилище офлайн-данных |
| **Secure Store** | Защищённое хранилище Android (Keystore) для JWT, refresh token, PIN |
| **Sync Engine** | Подсистема приложения, управляющая очередью мутаций и синхронизацией с сервером |
| **Outbox** | Очередь исходящих мутаций (создание/обновление/удаление), ожидающих отправки на сервер |
| **FCM** | Firebase Cloud Messaging — сервис push-уведомлений Google |
| **EAS Update** | OTA-обновления JS-бандла Expo без публикации в Google Play |
| **Deep link** | Переход к конкретному экрану приложения из push-уведомления |
| **Touch target** | Область касания интерактивного элемента (минимум 48dp × 48dp на Android) |
| **Auto-lock** | Автоматическая блокировка приложения при неактивности |
| **Биометрия** | Аутентификация по отпечатку пальца или Face Unlock |
| **PIN-код** | Резервный способ разблокировки (4-6 цифр), если биометрия недоступна |
| **Сжатие фото** | Уменьшение разрешения и качества JPEG для AI-распознавания (1280px, quality 0.6-0.7) |

## 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 4.1. Модуль «Авторизация и безопасность»

**US-AUTH-01 — Вход по логину и паролю**
*Как* инженер, *я хочу* входить в приложение по логину (email) и паролю, *чтобы* получить доступ к своим визитам и данным.
Первый вход — обязательно по логину/паролю. После успешного входа — предложение настроить биометрию.

**US-AUTH-02 — Вход по биометрии**
*Как* инженер, *я хочу* входить в приложение по отпечатку пальца или Face Unlock, *чтобы* не вводить пароль в полевых условиях (перчатки, грязные руки, яркий свет).
Биометрия предлагается после первого входа. При согласии — refreshToken сохраняется в Secure Store, последующие запуски — по биометрии без ввода пароля.

**US-AUTH-03 — PIN-код как резервный вход**
*Как* инженер, *я хочу* иметь PIN-код (4-6 цифр) для входа, когда биометрия недоступна (мокрые/грязные руки, перчатки, сбой датчика), *чтобы* не зависеть от биометрии.
PIN-код настраивается при первом входе (опционально) или в профиле. Хранится в Secure Store. При вводе — проверка без обращения к серверу.

**US-AUTH-04 — Автоблокировка при неактивности**
*Как* система, *я хочу* блокировать приложение через 5 минут неактивности (переход в фон, сворачивание), *чтобы* защитить данные при потере или краже устройства.
При разблокировке — экран с запросом биометрии или PIN-кода (не экран логина). Сессия не теряется — данные и открытый визит сохраняются.

**US-AUTH-05 — Автоматическое обновление токена**
*Как* система, *я хочу* автоматически обновлять access token через refresh token при истечении срока действия, *чтобы* инженер не терял сессию при длительной работе.
Если refresh token истёк — экран логина. Если network error при обновлении — retry при появлении сети.

### 4.2. Модуль «Главный экран — Список визитов»

**US-HOME-01 — Список визитов с табами**
*Как* инженер, *я хочу* видеть визиты разделёнными на табы «Активные» и «Завершённые», *чтобы* быстро находить текущие и архивные работы.
На каждом табе — бейдж с количеством визитов.

**US-HOME-02 — Карточка визита**
*Как* инженер, *я хочу* видеть для каждого визита: адрес (крупно), дату/время, статус (цветной бейдж), прогресс (N/M задач, прогресс-бар), специализацию (цветной тег), *чтобы* понимать состояние работ без перехода в детали.
Карточка кликабельна целиком (touch target ≥ 48dp).

**US-HOME-03 — Создание нового визита**
*Как* инженер, *я хочу* нажимать «+ Новый визит» и выбирать адрес из справочника с поиском, *чтобы* начать работу на объекте.
Функционал аналогичен PWA (US-1.1 — US-1.9 из ТЗ ТО). Выбор адреса — через полнотекстовый поиск с автодополнением.

**US-HOME-04 — Pull-to-refresh**
*Как* инженер, *я хочу* обновлять список визитов свайпом вниз, *чтобы* получить актуальные данные после появления сети.
Pull-to-refresh отключён на экранах с горизонтальным скроллом и вложенными ScrollView.

**US-HOME-05 — Сортировка визитов**
*Как* инженер, *я хочу* видеть визиты отсортированными по дате (новые сверху) или по статусу, *чтобы* быстро находить нужные.

**US-HOME-06 — Skeleton loading**
*Как* инженер, *я хочу* видеть скелет-загрузку (повторяющую форму карточек) при первой загрузке, *чтобы* понимать, что данные загружаются, а не видеть пустой экран.
Skeleton показывается при ожидании > 300 мс. Не показывается при < 200 мс (избегать мерцания).

**US-HOME-07 — Пустое состояние**
*Как* инженер, *я хочу* видеть понятное сообщение «Нет визитов» с кнопкой «+ Создать первый визит», *чтобы* понимать, что визитов нет, а не что приложение сломалось.

### 4.3. Модуль «Визит (детальная страница)»

**US-VISIT-01 — Метаданные визита**
*Как* инженер, *я хочу* видеть на странице визита: адрес (крупно), дату/время, сезон (Лето/Зима — автоопределение), ФИО инженера, GPS-координаты (ссылка на карту), статус, *чтобы* понимать контекст работ.

**US-VISIT-02 — Список задач**
*Как* инженер, *я хочу* видеть список задач (оборудования) с цветовой индикацией статуса: серый (not_started), синий (in_progress), зелёный (completed), *чтобы* понимать, что уже сделано и что осталось.
Для каждой задачи: тип оборудования, помещение, статус, прогресс параметров.

**US-VISIT-03 — Добавление оборудования**
*Как* инженер, *я хочу* нажимать «+ Добавить оборудование» и выбирать тип + помещение, *чтобы* формировать состав визита.
Функционал аналогичен PWA (US-1.4, US-1.8, US-GROUP-01, US-GROUP-02 из ТЗ ТО). Фильтрация по специализации инженера — как в PWA.

**US-VISIT-04 — Завершение визита**
*Как* инженер, *я хочу* нажимать «Завершить визит» с валидацией обязательных полей и фото, *чтобы* отправить отчёт.
Валидация: все задачи в статусе completed, обязательные фото загружены, при замечаниях — заполнены рекомендации.

**US-VISIT-05 — Индикатор синхронизации**
*Как* инженер, *я хочу* видеть статус синхронизации: «Сохранено локально» / «Синхронизировано» / «Ошибка синхронизации», *чтобы* понимать, актуальны ли данные на сервере.

**US-VISIT-06 — Формирование отчёта**
*Как* инженер, *я хочу* формировать PDF-отчёт по завершённому визиту, *чтобы* отправить результат заказчику.
Функционал аналогичен PWA (US-4.1 — US-4.4 из ТЗ ТО). PDF генерируется на сервере, приложение отображает и предоставляет Share.

### 4.4. Модуль «Задача (параметры оборудования)»

**US-TASK-01 — Формы параметров**
*Как* инженер, *я хочу* заполнять параметры оборудования через формы, специфичные для каждого типа (13 типов — см. ТЗ ТО раздел 4.1.2), *чтобы* фиксировать контролируемые показатели.
Формы идентичны PWA. Все числовые поля — с `keyboardType="numeric"`. Видимые лейблы над каждым полем.

**US-TASK-02 — Авто-сохранение**
*Как* система, *я хочу* автоматически сохранять параметры в SQLite каждые 30 секунд, *чтобы* не потерять данные при краше или разрядке устройства.
Индикатор «Сохранено локально» / «Синхронизировано» отображается на экране задачи.

**US-TASK-03 — Валидация при потере фокуса**
*Как* система, *я хочу* валидировать поля при потере фокуса (не при submit), *чтобы* инженер сразу видел ошибку и мог исправить.
Числовые поля — проверка допустимого диапазона. Обязательные поля — пометка красным.

**US-TASK-04 — Заключение и рекомендации**
*Как* инженер, *я хочу* выбирать заключение: «Исправно, замечаний нет» / «Исправно, есть замечания» / «Неисправно», *чтобы* классифицировать результат осмотра.
При «Исправно, есть замечания» или «Неисправно» — поле «Дополнительные рекомендации» становится обязательным (US-2.2 из ТЗ ТО).

**US-TASK-05 — Быстрый ввод рекомендаций**
*Как* инженер, *я хочу* отмечать типовые рекомендации чекбоксами из справочника (с фильтрацией по типу оборудования), *чтобы* не печатать текст на телефоне.
Функционал аналогичен PWA (US-2.1 из ТЗ ТО).

**US-TASK-06 — Сброс задачи**
*Как* инженер, *я хочу* сбрасывать только текущую задачу (не весь визит), *чтобы* случайное нажатие не уничтожило работу по другим задачам.
Функционал аналогичен PWA (US-2.3 из ТЗ ТО).

### 4.5. Модуль «Камера и фотофиксация»

**US-CAM-01 — Нативная камера**
*Как* инженер, *я хочу* использовать нативную камеру с полным контролем (фонарик, фокус по тапу, pinch-to-zoom), *чтобы* делать качественные фото в любых условиях (подвалы, серверные, тёмные помещения).
Камера по умолчанию — тыловая. Переключение фронтальная/тыловая — кнопкой.

**US-CAM-02 — Фонарик**
*Как* инженер, *я хочу* включать/выключать фонарик при съёмке, *чтобы* фотографировать в тёмных помещениях (щитовые, подвалы).
Кнопка toggle на экране камеры.

**US-CAM-03 — Сжатие фото для AI**
*Как* система, *я хочу* автоматически сжимать фото до 1280px (JPEG, quality 0.6-0.7, ~150 КБ) сразу после съёмки, *чтобы* ускорить загрузку на сервер и сэкономить хранилище, сохраняя достаточное качество для AI-распознавания.
Исходное фото не хранится. Если нужно лучшее качество — переснять.

**US-CAM-04 — Фото ДО и ПОСЛЕ**
*Как* инженер, *я хочу* делать фото «до» и «после» для каждой задачи, *чтобы* зафиксировать результат работ.
Для большинства типов: 2 фото (before/after). Для РЩ/ГРЩ, счётчиков: 1 фото (before).
Предпросмотр с возможностью переснять.

**US-CAM-05 — Именование фото**
*Как* система, *я хочу* автоматически именовать фото по шаблону `{№}_{equipment_code}_{room_code}_{moment}.jpg`, *чтобы* файлы были упорядочены и идентифицируемы.
Пример: `01_rsch_server_before.jpg`.

**US-CAM-06 — Галерея как fallback**
*Как* инженер, *я хочу* выбрать фото из галереи, если камера недоступна (сломана, нет разрешения), *чтобы* не прерывать работу.
Предупреждение: «Фото должно быть сделано сегодня». Проверка EXIF-даты — если старше 24 часов, показать предупреждение.

**US-CAM-07 — Обработка ошибок камеры**
*Как* система, *я хочу* показывать понятные сообщения при проблемах с камерой: «Камера занята другим приложением», «Нет разрешения — откройте настройки», «Недостаточно места», *чтобы* инженер мог устранить проблему.

**US-CAM-08 — Предупреждение 152-ФЗ**
*Как* система, *я хочу* показывать предупреждение о персональных данных при первом использовании камеры, *чтобы* инженер убедился, что в кадр не попали лица и персональные данные.
Функционал аналогичен PWA (US-3.3 из ТЗ ТО). Флаг согласия хранится в Secure Store. При переустановке — показывать снова.

### 4.6. Модуль «Геолокация»

**US-GEO-01 — Автозапрос GPS при создании визита**
*Как* система, *я хочу* автоматически запрашивать GPS-координаты при создании визита, *чтобы* зафиксировать местоположение инженера.

**US-GEO-02 — Отображение координат**
*Как* инженер, *я хочу* видеть адрес, координаты (широта/долгота), точность в метрах с цветовой индикацией (🟢 < 50 м, 🟡 50-200 м, 🔴 > 200 м), *чтобы* понимать качество определения позиции.

**US-GEO-03 — Обновление координат**
*Как* инженер, *я хочу* нажимать «Обновить координаты» для повторного запроса GPS, *чтобы* получить более точное значение.

**US-GEO-04 — Ссылка на карту**
*Как* инженер, *я хочу* нажимать на координаты и открывать карту (Google Maps / Яндекс.Карты), *чтобы* видеть точное местоположение объекта.

### 4.7. Модуль «Офлайн-режим и синхронизация»

**US-OFF-01 — Полная офлайн-работа**
*Как* инженер, *я хочу* создавать визиты, заполнять параметры, делать фото без подключения к интернету, *чтобы* работать в подвалах, серверных, тепловых узлах.
Все данные сохраняются в SQLite. Справочники (адреса, оборудование) кешируются при первом получении.

**US-OFF-02 — Индикатор онлайн/оффлайн**
*Как* инженер, *я хочу* видеть в шапке статус подключения (онлайн/оффлайн), *чтобы* понимать, синхронизированы ли данные.

**US-OFF-03 — Очередь мутаций (Outbox)**
*Как* система, *я хочу* записывать все действия (создание визита, сохранение параметров, загрузка фото) в очередь мутаций и отправлять при появлении сети, *чтобы* данные не терялись.

**US-OFF-04 — Автосинхронизация при появлении сети**
*Как* система, *я хочу* автоматически синхронизировать очередь при появлении интернета, *чтобы* инженер не нажимал кнопку «Синхронизировать».
Триггеры: NetInfo listener (появление сети), AppState (возврат в приложение), pull-to-refresh (вручную).

**US-OFF-05 — Индикатор прогресса синхронизации**
*Как* инженер, *я хочу* видеть прогресс синхронизации: «3 из 12 синхронизировано», прогресс загрузки фото, *чтобы* понимать, сколько данных ожидает отправки.

**US-OFF-06 — Уведомление о синхронизации**
*Как* система, *я хочу* показывать уведомление «Данные синхронизированы» после успешной синхронизации, *чтобы* инженер был уверен, что данные на сервере.

**US-OFF-07 — Retry при ошибке**
*Как* система, *я хочу* повторять отправку мутации до 5 раз с увеличением интервала (exponential backoff), *чтобы* справиться с временными сбоями сети.

**US-OFF-08 — Разрешение конфликтов**
*Как* система, *я хочу* разрешать конфликты синхронизации: server-wins для статусов, last-write-wins для параметров (с пометкой при расхождении < 60 сек для ручного разрешения), *чтобы* данные оставались консистентными.

**US-OFF-09 — Кеширование справочников**
*Как* система, *я хочу* кешировать только назначенные инженеру адреса и оборудование (не все ~12000 записей), *чтобы* не перегружать хранилище устройства.
Delta-синхронизация: при обновлении — только изменения с последней синхронизации.

### 4.8. Модуль «Push-уведомления»

**US-PUSH-01 — Получение push-уведомлений**
*Как* инженер, *я хочу* получать push-уведомления о назначении на заявку/визит, изменении статуса, напоминания о незавершённых визитах, *чтобы* быть в курсе без постоянного открытия приложения.
Доставка через FCM (Firebase Cloud Messaging).

**US-PUSH-02 — Настройка уведомлений**
*Как* инженер, *я хочу* включать/выключать уведомления, настраивать звук и вибрацию, *чтобы* управлять оповещениями.

**US-PUSH-03 — Deep link из push**
*Как* инженер, *я хочу* при тапе на push-уведомление переходить к соответствующему визиту/заявке, *чтобы* сразу видеть контекст.
Cold start: авторизация → переход к визиту. Warm start: переход без авторизации. Если визит не загружен — skeleton + загрузка.

**US-PUSH-04 — In-app уведомления**
*Как* инженер, *я хочу* видеть баннер «Новая заявка назначена» при активном использовании, тост «Визит сохранён локально» при офлайн-сохранении, *чтобы* получать обратную связь от приложения.

### 4.9. Модуль «Заявки»

**US-REQ-01 — Список заявок**
*Как* инженер, *я хочу* видеть список своих заявок с табами: Все / Новые / В работе / Завершённые, *чтобы* управлять назначенными работами.
Бейджи с количеством на каждом табе.

**US-REQ-02 — Карточка заявки**
*Как* инженер, *я хочу* видеть для каждой заявки: номер, адрес, вид оборудования, статус исполнения, кнопки действий (Начать визит / Продолжить визит), *чтобы* быстро переходить к работе.

**US-REQ-03 — Создание визита из заявки**
*Как* инженер, *я хочу* нажимать «Начать визит» на заявке и автоматически создавать визит по адресу заявки, *чтобы* не вводить адрес вручную.

### 4.10. Модуль «Отчёты»

**US-REP-01 — Просмотр PDF-отчёта**
*Как* инженер, *я хочу* просматривать сгенерированный PDF-отчёт прямо в приложении, *чтобы* проверить содержимое перед отправкой.

**US-REP-02 — Отправка через Share**
*Как* инженер, *я хочу* отправлять ZIP-архив (PDF + фото) через Android Share API (email, мессенджер, облако), *чтобы* доставить отчёт заказчику.

**US-REP-03 — Офлайн-просмотр отчётов**
*Как* инженер, *я хочу* просматривать ранее сгенерированные отчёты без интернета, *чтобы* иметь доступ к истории работ.
Отчёты кешируются в File System устройства.

### 4.11. Модуль «Профиль»

**US-PROF-01 — Просмотр профиля**
*Как* инженер, *я хочу* видеть ФИО, email, телефон, роль, специализацию, статистику (всего/завершённых/активных визитов), *чтобы* понимать свой статус.

**US-PROF-02 — Настройки**
*Как* инженер, *я хочу* настраивать push-уведомления (вкл/выкл), биометрию (вкл/выкл), PIN-код (сменить), тему (Светлая / Тёмная / Как в системе), *чтобы* адаптировать приложение под свои предпочтения.

**US-PROF-03 — Выход**
*Как* инженер, *я хочу* выходить из аккаунта, *чтобы* передать устройство другому сотруднику.
При выходе — очистка SQLite (кроме справочников), удаление токенов из Secure Store.

### 4.12. Модуль «Навигация»

**US-NAV-01 — Нижняя навигация (Tab Bar)**
*Как* инженер, *я хочу* переключаться между основными разделами через нижнюю навигацию: Визиты / Заявки / Профиль, *чтобы* быстро перемещаться по приложению.

**US-NAV-02 — Кнопка «Назад»**
*Как* инженер, *я хочу* возвращаться на предыдущий экран аппаратной кнопкой «Назад» или swipe-жестом, *чтобы* навигация была привычной для Android.
Стек навигации сохраняется. Камера → возврат к задаче (не к списку визитов).

**US-NAV-03 — Бейджи на табах**
*Как* инженер, *я хочу* видеть количество активных визитов и новых заявок на табах нижней навигации, *чтобы* понимать, есть ли требующие внимания элементы.

## 5. ТРЕБОВАНИЯ К UI/UX

### 5.1. Touch targets
- Все интерактивные элементы — минимум **48dp × 48dp** (стандарт Android)
- Карточки визитов — кликабельны целиком
- Расстояние между элементами — минимум 8dp

### 5.2. Формы и ввод
- Каждый input — с видимым лейблом над полем (placeholder — не замена лейблу)
- Числовые поля — `keyboardType="numeric"`
- Email — `keyboardType="email-address"`
- Телефон — `keyboardType="phone-pad"`
- Валидация — при потере фокуса

### 5.3. Загрузка контента
- Skeleton loading при ожидании > 300 мс
- Не показывать при < 200 мс (избегать мерцания)
- Skeleton повторяет форму контента

### 5.4. Empty states
- Каждый экран с данными — пустое состояние с CTA-кнопкой
- «Нет визитов» → «+ Создать первый визит»
- «Нет интернета» → «Работайте офлайн — данные синхронизируются»

### 5.5. Тёмная тема
- Автопереключение по системной настройке
- Ручной override: Светлая / Тёмная / Как в системе
- Палитра — в Спецификации (раздел 5.0)

### 5.6. Контраст и доступность
- Текст — контраст ≥ 4.5:1 (WCAG AA)
- Цветовые индикаторы — дублировать текстом
- Иконки — с accessibilityLabel

## 6. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 6.1. Производительность

| Метрика | Целевое значение |
|---------|-----------------|
| Холодный старт | < 3 сек |
| Переход между экранами | < 300 мс |
| Рендер списка (100 визитов) | < 500 мс |
| Синхронизация 50 мутаций | < 30 сек (4G) |
| Загрузка фото (150 КБ) | < 2 сек (4G) |

### 6.2. Безопасность
- JWT и refresh token — в Secure Store (Android Keystore)
- PIN-код — в Secure Store
- Auto-lock через 5 минут неактивности
- Запрет логирования токенов, паролей, email в Sentry
- Certificate pinning — опционально (оценить необходимость)

### 6.3. Надёжность
- Crash-free rate > 99%
- Данные в SQLite не теряются при краше
- Sync Engine — идемпотентность, order guarantee, dedup
- Retry до 5 раз с exponential backoff

### 6.4. Обновления
- Google Play — основное обновление (1-3 дня)
- EAS Update (OTA) — критичные баги за часы
- Минимальная версия API — сервер проверяет X-API-Version

## 8. ЗАВИСИМОСТИ

### 8.1. Серверные эндпоинты
Приложение использует существующие API-эндпоинты (полный список — в Спецификации, раздел 13). Ключевые зависимости:
- `POST /api/sync/batch` — пакетная синхронизация (**P0**, должен быть реализован до Этапа 4)
- `POST /api/push/register` — регистрация FCM-токена (P1)
- `GET /api/refs/*?updated_since=<date>` — delta-синхронизация (P1)

### 8.2. API-версионирование
- Сервер отправляет `X-API-Version` в заголовке
- Сервер поддерживает N-1 версию
- При несовместимой версии — экран «Обновите приложение»

### 8.3. Переиспользование из PWA
- `shared/types/index.ts` — 100% (общие TypeScript-типы)
- Валидация параметров — ~90% (чистые функции)
- Логика синхронизации — ~60% (переписать на SQLite)
- UI-компоненты — ~20% (Ant Design → React Native Paper)
