# СПЕЦИФИКАЦИЯ НА РАЗРАБОТКУ
## Web-приложение «Цифровой чек-лист инженера по техническому обслуживанию оборудования»

**Версия:** 17.0
**Дата:** 21.08.2026
**Статус:** Готов к разработке

---

## 1. ОБЗОР ПРОЕКТА

### 1.1. Наименование
Web-приложение «Цифровой чек-лист инженера по техническому обслуживанию оборудования» (далее — Приложение).

### 1.2. Назначение
Автоматизация деятельности инженера по техническому обслуживанию оборудования:
- Создание чек-листа работ на объекте
- Фиксация контролируемых параметров оборудования
- Фотофиксация состояния оборудования «до» и «после»
- Формирование PDF-отчёта с маркированными фотографиями
- Отправка отчёта заказчику по email

### 1.3. Ключевые ограничения
- **Офлайн-работа** — обязательна (подвалы, серверные, тепловые узлы без связи)
- **Мобильный интерфейс** — основной сценарий инженера (смартфон/планшет)
- **Соответствие 152-ФЗ** — предупреждения о персональных данных при фотофиксации
- **Все тексты интерфейса** — на русском языке

#### 3.2.18. visit_requests — Связь визитов с заявками (многие-ко-многим)

| Поле | Тип | Nullable | Описание |
|------|-----|:--------:|----------|
| id | UUID | ❌ | Первичный ключ |
| visit_id | UUID | ❌ | FK → visits.id (визит) |
| imported_request_id | UUID | ❌ | FK → imported_requests.id (заявка) |
| created_at | TIMESTAMP | ❌ | Дата создания связи |

- UNIQUE(visit_id, imported_request_id) — защита от дубликатов

- INDEX(imported_request_id) — быстрый поиск визитов по заявке

**Бизнес-логика:**
- Связующая таблица для отношения многие-ко-многим между визитами и заявками
- **Заявка «ИСЖ объекта»** — заявка, у которой `equipment_type_code` соответствует специальному виду «ИСЖ объекта». Такая заявка подразумевает ТО **всего** оборудования объекта, и каждый инженер (с разной специализацией) создаёт свой визит. Все визиты связываются с одной и той же заявкой через `visit_requests`
- **Автопривязка при создании визита инженером:** когда инженер создаёт визит на объект, система ищет все импортированные заявки (`imported_requests`) по `object_code` этого объекта и автоматически создаёт записи в `visit_requests`, связывая новый визит с найденными заявками
- **Отображение в списке визитов:** API возвращает объединённый список номеров заявок из `importedRequests` (прямая привязка по `visit_id`) и из `visitRequests → importedRequest` (связь через таблицу). В UI показываются первые 2 номера + счётчик «+N»

**GET `/api/visits`** — параметры и формат ответа:
- Query-параметры: `page` (номер страницы, по умолчанию 1), `pageSize` (записей на странице, по умолчанию 20), `status` (одиночный статус), `statuses` (мульти-фильтр, comma-separated), `search` (поиск по адресу или коду объекта, case-insensitive), `date_from`, `date_to`, `user_id`, `include_deleted` (только admin)
- Ответ: `{ data: Visit[], total: number, page: number, pageSize: number, globalStats: { total, planned, inProgress, completed } }`
- `globalStats` — сводная статистика по **всем** визитам (без учёта пагинации и без учёта фильтра по статусам), рассчитывается через `groupBy` по статусам
- **Объединение заявок:** каждый визит в ответе содержит поле `requests[]` — объединённый массив номеров заявок из двух источников:
  1. `importedRequests` — заявки, привязанные напрямую через `imported_requests.visit_id` (устаревшая привязка один-ко-многим)
  2. `visitRequests → importedRequest` — заявки, привязанные через связующую таблицу `visit_requests` (актуальная связь многие-ко-многим)
  
  Дедупликация по `imported_request_id`. В UI отображаются первые 2 номера заявок + счётчик «+N» (если их больше)

**POST `/api/visits`** — автопривязка заявок:
- При создании визита инженер указывает `addressId` (адрес объекта)
- Сервер автоматически находит все записи `imported_requests` с совпадающим `object_code` (через `addresses.object_code`)
- Для каждой найденной заявки создаётся запись в `visit_requests`, связывающая новый визит с заявкой
- Если заявка имеет `equipment_type_code` вида «ИСЖ объекта» — визит помечается `is_multi_specialist = TRUE`
- Автопривязка не создаёт дубликатов (UNIQUE constraint на `visit_id + imported_request_id`)

  "dateTo": "YYYY-MM-DD",

**Логика отчётов для заявок «ИСЖ объекта» (type=requests):**
- Заявка «ИСЖ объекта» подразумевает ТО **всего** оборудования объекта, а не отдельного вида оборудования
- При формировании отчёта по таким заявкам система находит **все** визиты, связанные с заявкой через `visit_requests` (многие-ко-многим), а также через `imported_requests.visit_id` (прямая привязка)
- Отчёт агрегирует данные из **всех** связанных визитов: задачи, фото, рекомендации — независимо от того, какой инженер их создал
- Таким образом, полный отчёт по заявке ИСЖ объекта содержит результаты работы нескольких инженеров с разными специализациями (ВиК, ИСЖ, ГПМ и др.), каждый из которых выполнил ТО своей части оборудования

Все существующие эндпоинты уведомлений фильтруют `is_deleted = false` — удалённые уведомления не возвращаются.

### 4.10. Системные эндпоинты

| Метод | Путь | Описание | Авторизация |
|-------|------|----------|:-----------:|
| POST | `/api/system/webhook/deploy` | Webhook от CI/CD: создание уведомлений о релизе | HMAC-подпись |
| POST | `/api/admin/system-notifications` | Ручное создание системного уведомления (админ) | Auth (admin) |
| POST | `/api/internal/cron/process-expired-proposals` | Cron-обработка истёкших proposals (ежедневно 03:00) | `CRON_SECRET` |

**POST `/api/system/webhook/deploy`** — webhook для автоматического оповещения о деплое:
- Заголовки: `X-Webhook-Signature: sha256=<HMAC>`, `X-Webhook-Timestamp: <unix_timestamp>`
- Тело: `{ "version": "v2.4.0", "release_notes": "..." }`
- Логика: проверка HMAC-подписи (`WEBHOOK_SECRET`), проверка timestamp (±5 мин), защита от дубликатов по `system_releases.version`, массовое создание уведомлений `system_release` для всех активных пользователей
- Rate limit: 10 запросов / 15 минут

**POST `/api/admin/system-notifications`** — ручное создание:
- Тело: `{ "title": "...", "message": "...", "version": "v2.5.0" }`
- Запись в `system_releases` (`deployed_by: 'admin_manual'`), массовое создание уведомлений

**POST `/api/internal/cron/process-expired-proposals`** — ежедневная обработка:
1. Пометить истёкшие proposals: `status = 'expired'`
2. Откатить `object_equipment` для `room_change` (восстановить `old_room_type_code`)
3. Деактивировать `object_equipment` для `new_equipment` (`is_active = false`)
4. Создать уведомления `proposal_expired` и `proposal_expiring_soon` (за 3 дня до истечения)
5. Защита от повторной обработки через `reviewed_at >= NOW() - 1 hour`

## 6. БИЗНЕС-ЛОГИКА

### 6.1. Создание визита

1. Инженер выбирает адрес из справочника (поиск с автодополнением)
2. Поля «Дата начала» и «Время начала» заполняются автоматически (текущие дата/время)
3. Поле «Сезон» вычисляется автоматически по дате:
   - Апрель (1+) – Октябрь (31) → «Лето»
   - Ноябрь (1) – Март (31) → «Зима»
4. При изменении даты — пересчёт сезона с подтверждением пользователя

### 6.2. Управление задачами

1. Кнопка «+ Добавить оборудование» → модальное окно:
   - Вид оборудования (dropdown из справочника)
   - Тип помещения (dropdown из справочника)
   - Местоположение / Назначение (текстовое поле, необязательно)
2. Новая задача получает статус «Не начато»
3. Клик на задачу → переход на страницу параметров (4.x)
4. Статус задачи меняется на «В работе» при первом редактировании
5. Статус «Выполнено» — после сохранения параметров с заключением

### 6.3. Условная обязательность

- Поле «Дополнительные рекомендации» обязательно ТОЛЬКО при:
  - Заключение = «Исправно, есть замечания» ИЛИ
  - Заключение = «Неисправно»
- Валидация при сохранении задачи

### 6.4. Фотофиксация

1. Количество фото определяется типом оборудования:
   - `photos_required = 2` (СС, МСС, VRV, вентиляция): фото ДО + фото ПОСЛЕ
   - `photos_required = 1` (РЩ, счётчики, сети): только фото ДО
2. Для оборудования с 1 фото — поле «Фото ПОСЛЕ» скрыто
3. Предупреждение 152-ФЗ — при первом фото в помещениях с типами:
   - Клиентский зал, Зона самообслуживания, Касса, Санузел, Крыльцо
4. Фото сохраняются в файловое хранилище, метаданные — в БД

### 6.5. Завершение визита

1. Кнопка «Завершить визит» активна при наличии ≥1 выполненной задачи
2. При завершении:
   - Заполняется `time_end`
   - Статус визита → `completed`
   - Генерируется PDF-отчёт
   - Формируется ZIP-архив (PDF + фото)
3. Переход на страницу отправки отчёта (Страница 6)

### 6.6. Маркировка фотографий

**Шаблон имени файла:**
```
{№}_{equipment_code}_{room_code}_{moment}.jpg
```

- `{№}` — порядковый номер задачи в визите (01, 02, 03...)
- `{equipment_code}` — код типа оборудования из справочника
- `{room_code}` — код типа помещения из справочника
- `{moment}` — `before` или `after`

**Примеры:**
- `01_rsch_server_before.jpg`
- `02_splitvn_server_before.jpg`
- `02_splitvn_server_after.jpg`

### 6.7. Формирование PDF-отчёта

**Структура документа** (согласно `Шаблон акта.md`):

1. Заголовок: «Акты выполненных работ»
2. Общий блок:
   - Адрес объекта
   - Дата проведения
   - Время начала / окончания
   - Сезон
   - Инженер (ФИО из профиля)
3. Для каждой задачи:
   - Номер и вид оборудования + местоположение
   - Местоположение (тип помещения)
   - Контролируемые параметры (список)
   - Фотофиксация (встроенные изображения)
   - Заключение
   - Рекомендации (выбранные + дополнительные)
4. Подпись инженера

**Технические требования:**
- Формат: PDF/A-1b
- Страница: A4
- Шрифт: Arial / Roboto, 11pt
- Фото: 150 DPI, встроенные в PDF
- Имя файла: `OTCHET_{street}_{house}_{date}.pdf`

### 6.8. Формирование ZIP-архива

```
OTCHET_{street}_{house}_{date}.zip
├── OTCHET_{street}_{house}_{date}.pdf
└── Photos/
    ├── 01_rsch_server_before.jpg
    ├── 02_splitvn_server_before.jpg
    ├── 02_splitvn_server_after.jpg
    └── ...
```

### 6.9. Отправка email

- **Протокол:** SMTP / SMTPS
- **Кому:** `customer_email` из справочника адресов
- **Тема:** `Акт выполненных работ: {full_address} от {dd.mm.yyyy}`
- **Тело письма:** Шаблон с краткой сводкой (адрес, дата, кол-во задач)
- **Вложение:** ZIP-архив (до 25 МБ)
- **Резерв:** При недоступности email — кнопка «Скачать»

### 6.10. Офлайн-режим

1. **Service Worker** кэширует:
   - Статические ресурсы (HTML, CSS, JS, иконки)
   - API-ответы справочников
2. **IndexedDB** хранит:
   - Текущие визиты и задачи
   - Очередь изменений (pending mutations)
   - Загруженные фото (до синхронизации)
3. **Автосохранение:** каждые 30 секунд (хук `useAutoSave`)
4. **Автосинхронизация:** при появлении сети — отправка накопленных данных
5. **Предупреждение:** при закрытии вкладки с несохранёнными данными (`beforeunload`)

**Обновление PWA:**
- `registerType: 'prompt'` — при обнаружении новой версии показывается баннер «Доступна новая версия приложения» с кнопкой «Обновить»
- Хук `usePWAUpdate` + компонент `PWAUpdateBanner` — отслеживают обновление Service Worker

**Автообновление данных:**
- При событии `visibilitychange` (возврат на вкладку) запускается синхронизация данных
- Список визитов (`VisitListPage`) перезагружается при каждом возврате на вкладку
- Запросы оборудования объекта (`/refs/object-equipment`) включают `_t=timestamp` для обхода кэша Workbox — данные всегда загружаются с сервера при открытии модального окна

### 6.11. Сброс задачи

- Кнопка «Сбросить задачу» очищает ТОЛЬКО текущую задачу
- Сбрасываются: параметры, рекомендации, фото, заключение
- Статус задачи → «Не начато»
- Остальные задачи визита не затрагиваются

### 6.12. Офлайн-режим

**Локальное хранилище (Dexie / IndexedDB):**
- Таблицы: visits, tasks, photos, syncQueue, cachedRefs
- Каждая запись имеет флаг `dirty` (требует синхронизации)
- Фото хранятся как Blob

**Синхронизация:**
1. При восстановлении связи — `processSyncQueue()` обрабатывает очередь
2. Каждая операция воспроизводится на сервере (create → POST, update → PUT, delete → DELETE)
3. При успехе — запись удаляется из очереди, `dirty = false`
4. При ошибке — retry до 5 раз, затем исключение из очереди
5. После push — `pullVisitsFromServer()` обновляет данные с сервера

**Стратегии кэширования (Workbox):**
| Ресурс | Стратегия | TTL |
|--------|-----------|-----|
| Изображения | CacheFirst | 30 дней |
| /api/refs/* | StaleWhileRevalidate | 1 день |
| /api/* (прочее) | NetworkFirst (timeout 3с) | 7 дней |

## 14. ТЕСТОВЫЕ СЦЕНАРИИ

### 14.1. Основной сценарий (Happy Path)

1. Инженер входит в систему
2. Создаёт визит, выбирает адрес
3. Добавляет 3 задачи (разные типы оборудования)
4. Заполняет параметры для каждой задачи
5. Делает фото ДО и ПОСЛЕ
6. Завершает визит
7. Формирует отчёт (PDF генерируется на сервере)
8. Скачивает ZIP-архив (PDF + маркированные фото) на устройство

### 14.2. Офлайн-сценарий

1. Инженер создаёт визит без интернета
2. Заполняет задачи и делает фото
3. Данные сохраняются в IndexedDB
4. При появлении сети — автосинхронизация
5. Отчёт формируется и отправляется

### 14.3. Административный сценарий

1. Администратор добавляет новый адрес
2. Привязывает email заказчика
3. Добавляет новую рекомендацию
4. Создаёт учётную запись инженера

### 14.4. Сценарий ТМ

1. Вход как ТМ (tm@example.com / tm12345)
2. Просмотр дашборда с визитами инженеров
3. Фильтрация по конкретному инженеру
4. Просмотр деталей визита инженера
5. Переназначение визита другому инженеру
6. Формирование и отправка отчёта
7. Soft delete визита

## 15. ПРИНЯТЫЕ РЕШЕНИЯ (уточнения к ТЗ)

> Ниже зафиксированы решения по вопросам, отсутствующим в исходном техническом задании.

### 15.1. Технологический стек ✅
- **Frontend:** React 18+ / TypeScript, Zustand, Ant Design Mobile / Vant, Workbox
- **Backend:** Node.js / Express, Prisma ORM, Nodemailer
- **Генерация ZIP:** JSZip (на клиенте)

### 15.2. Источник данных инженера ✅
ФИО инженера **вводятся вручную** при создании визита (поле в форме визита). В последующих визитах поле автозаполняется последним использованным значением.

### 15.3. Время окончания визита ✅
`time_end` заполняется **автоматически** при нажатии «Завершить визит» (текущее серверное время).

### 15.4. История визитов ✅
Инженер видит **список своих визитов** с возможностью:
- Просмотра деталей визита
- **Повторного скачивания** PDF + ZIP отчёта
- Фильтрации по дате и статусу

### 15.5. Удаление визитов ✅
Инженер может удалить визит в **любом статусе** (в работе, завершён, отправлен). При удалении удаляются все связанные задачи и фото.

### 15.6. Восстановление пароля ✅
Механизм **сброса по email**: пользователь запрашивает сброс → получает письмо со ссылкой → устанавливает новый пароль. Ссылка действительна 1 час.

### 15.7. SMTP-конфигурация ✅
На этапе разработки — **Ethereal Email** (тестовый SMTP). В production — будет настроен реальный SMTP-сервер (конфигурация через .env).

### 15.8. Хранилище фотографий ✅
**Локальная файловая система** сервера (директория `uploads/`). В дальнейшем планируется миграция на S3-совместимое хранилище. Максимальный размер фото: 10 МБ, максимальное разрешение: 4032×3024 (авто-ресайз при загрузке).

### 15.9. Нумерация задач в фото ✅
Порядковый номер `{№}` — номер задачи в рамках визита. При удалении задачи **номера пересчитываются** для оставшихся задач.

### 15.10. Редактирование завершённого визита ✅
Завершённый визит **можно редактировать**. При повторном сохранении PDF перегенерируется автоматически.

### 15.11. Конфликты синхронизации ✅
Стратегия **«последняя запись побеждает»** (last-write-wins) с timestamp. При конфликте справочников — приоритет у серверной версии.

### 15.12. Уведомления ✅
Push-уведомления **не требуются**. Статусы отображаются в интерфейсе.

### 15.13. Логирование и аудит ✅
**Полный журнал аудита** — таблица `audit_log`:
- id, user_id, action, entity_type, entity_id, old_value, new_value, created_at
- Логируются: вход/выход, создание/редактирование/удаление визитов, задач, справочников

### 15.14. Резервное копирование ✅
Ежедневный бэкап PostgreSQL (pg_dump) + архив директории uploads. Срок хранения: 30 дней.

### 15.15. Домен и SSL ✅
- **Домен:** checkonout.ru (привязан к IP 31.128.38.54)
- **SSL:** Let's Encrypt, сертификат получен через Certbot, автообновление
- **HTTPS:** Nginx слушает 443, HTTP (80) → редирект 301 на HTTPS
- **Хостинг:** Beget VPS, 14 ГБ диск, 1.9 ГБ RAM + 2 ГБ swap

### 15.16. Отправка по email — исключена из UI ✅
Функционал отправки отчёта по email **удалён из пользовательского интерфейса** по решению заказчика. Вместо него реализовано **скачивание ZIP-архива** (PDF + фото) на устройство инженера. Серверный эндпоинт `POST /api/reports/:id/report/send` сохранён для будущего использования.

- **Импорт Excel** — `POST /api/requests/import` принимает `.xlsx` файл с колонками: № заявки, Статус, Вид оборудования, Код объекта, Адрес
- **Предварительная валидация** — `POST /api/requests/import?mode=validate` выполняет проверку файла без создания записей, возвращает список ошибок (номер строки, № заявки, описание). Фронтенд показывает модальное окно с таблицей ошибок перед импортом
- **Парсинг и маппинг** — поиск вида оборудования по `name` в `equipment_types` (регистронезависимо), поиск объекта по `object_code` (приоритет) или по нормализованному адресу
- **Вид оборудования "ИСЖ объекта"** — специальный вид с `specialization_req = NULL`, означает "любая специализация". При импорте не создаёт задачи, визит помечается `is_multi_specialist = TRUE`. Проверка специализации при назначении пропускается
- **Статус 'skipped'** — дубликаты заявок (уже импортированные или внутри файла) помечаются статусом `skipped`, а не `error`
- **Нормализация адреса** — утилита `addressNormalizer.ts`: удаление лишних пробелов, приведение сокращений (ул/улица, д/дом, к/корпус), lower case
- **Группировка по объекту** — несколько заявок на один `object_code` → один визит с несколькими задачами
- **Статус `awaiting_assignment`** — новый статус визита (визит создан, но инженер не назначен); `userId = NULL`
- **Таблица `imported_requests`** — хранит импортированные заявки с FK на `equipment_types`, `addresses`, `visits` (см. раздел 3.2.17)
- **Таблица `visit_requests`** — связующая таблица многие-ко-многим между визитами и заявками (visit_id + imported_request_id). Автопривязка при создании визита инженером, поддержка нескольких визитов на одну заявку «ИСЖ объекта» (см. раздел 3.2.18)
- **Таблица `visit_engineers`** — связующая таблица для множественного назначения (visit_id + engineer_id + is_primary) (см. раздел 3.2.19)
- **Таблица `request_assignment_log`** — история действий: assigned/unassigned/declined с причиной (см. раздел 3.2.20)
- **Валидация специализации** — при назначении проверяется `equipment_type.specialization_req` против булевых флагов инженера (`specialization_vik/iszh/gpm/dgu/ibp`)
- **Множественное назначение** — ТМ может назначить нескольких инженеров на любую заявку; первый назначенный становится основным (`is_primary = true`)
- **Отказ инженера** — `POST /api/requests/decline` с причиной, уведомление ТМ
- **Уведомления** — типы `request_assigned`, `request_unassigned`, `request_declined`, `request_imported`
- **Ручная привязка** — `POST /api/requests/:id/bind` для заявок со статусом `error`
- **Отчёт по заявкам** — расширен `POST /api/reports/summary-generate` типом `requests` с фильтрацией по `requestIds`. Для заявок «ИСЖ объекта» отчёт агрегирует данные из **всех** связанных визитов (через `visit_requests`), а не только из одного визита
- **Поиск по номерам** — `POST /api/requests/search-by-numbers` для автокомплита в отчёте
- **Асинхронный импорт** — для файлов >100 строк через `import_log` со статусом `processing` + polling
- **Фронтенд (ТМ/Админ)** — страница `/requests`: таблица заявок, импорт Excel, назначение/снятие инженеров, ручная привязка, сортировка по колонкам (№ заявки, статус, код, адрес), фильтр по статусу исполнения и инженеру, пагинация по 10 записей. ТМ видит только заявки по своим адресам и своим инженерам. Все страницы ТМ/Админа: `maxWidth: 1400px`
- **Фронтенд (Инженер)** — страница `/my-requests`: список назначенных заявок с табами-фильтрами (Все/Новые/В работе/Завершённые). На мобильном — карточки (`.request-card`), на десктопе — таблица. Умные кнопки: «Начать визит»+«Отказаться» для новых заявок, «Продолжить визит» для активных, без кнопок для завершённых. Автоматическая смена статуса визита на «В работе» при первом посещении страницы визита или создании/обновлении задачи
- **API-клиент** — методы `importRequests`, `getRequests`, `assignEngineer`, `unassignEngineer`, `declineRequest`, `searchRequestsByNumbers`

### 15.38. Связь визитов с заявками через VisitRequest (многие-ко-многим) ✅
- **Таблица `visit_requests`** — связующая таблица для отношения многие-ко-многим между `visits` и `imported_requests` (поля: `visit_id`, `imported_request_id`, уникальный составной ключ)
- **Бизнес-правило «ИСЖ объекта»:** заявка с видом оборудования «ИСЖ объекта» подразумевает ТО **всего** оборудования объекта. Каждый инженер (с разной специализацией) создаёт свой визит, и все визиты связываются с одной заявкой через `visit_requests`
- **Автопривязка при создании визита:** когда инженер создаёт визит на объект, сервер автоматически ищет все записи `imported_requests` по `object_code` этого объекта и создаёт записи в `visit_requests`. Если среди заявок есть «ИСЖ объекта» — визит помечается `is_multi_specialist = TRUE`
- **Объединение заявок в API:** эндпоинты `GET /api/visits` и `GET /api/visits/:id` возвращают объединённый массив номеров заявок из двух источников — `importedRequests` (прямая привязка по `visit_id`) и `visitRequests → importedRequest` (через связующую таблицу). Дедупликация по `imported_request_id`
- **Отображение в UI:** в списке визитов показываются первые 2 номера заявок + счётчик «+N» (если их больше)
- **Отчёты для заявок ИСЖ объекта:** при формировании сводного отчёта (`type=requests`) система находит **все** визиты, связанные с заявкой через `visit_requests`, и агрегирует задачи, фото и рекомендации из каждого визита — так отчёт содержит результаты работы всех инженеров, участвовавших в ТО объекта

## 17. Часовые пояса

### 17.1. Проблема

Сервер работает в Docker-контейнере с часовой зоной UTC. При генерации PDF-отчётов даты и время форматировались через `toLocaleDateString('ru-RU')` / `toLocaleString('ru-RU')` без указания часового пояса, что приводило к отображению UTC-вреени вместо московского (сдвиг −3 часа).

### 17.2. Решение

Все серверные вызовы форматирования дат (`toLocaleDateString`, `toLocaleTimeString`, `toLocaleString`) используют параметр `timeZone: 'Europe/Moscow'`:

- `server/src/services/report.ts` — функция `formatDate()`, метки «Отчёт сформирован»
- `server/src/services/unifiedReport.ts` — функция `formatDate()`, «Дата формирования», «Отчёт сформирован»
- `server/src/routes/reports.ts` — тема email, даты диапазонов

Дополнительно исправлены вычисления, использующие `getHours()/getMinutes()/getMonth()/getDate()`:

- `server/src/routes/visits.ts` — `timeEnd` при завершении визита (московское время)
- `server/src/routes/admin.ts` — форматирование дат в экспорте журнала аудита
- `server/src/services/requestImport.ts` — определение сезона при импорте заявок
- `server/src/routes/requests.ts` — определение сезона при создании визита из заявки
- `server/src/routes/profile.ts` — начало месяца для статистики профиля

### 17.3. Клиент

Клиентские отображения дат (`toLocaleDateString('ru-RU')`) работают корректно без изменений — браузер автоматически конвертирует UTC в локальный часовой пояс пользователя.

## 19. ГОЛОСОВОЙ ВВОД (SPEECH-TO-TEXT)

> Раздел добавлен в соответствии с ТЗ «Голосовой ввод» v1.1 от 23.07.2026.

### 19.1. Назначение

Функция голосового ввода текста в свободное текстовое поле **«Дополнительные рекомендации»** на страницах задач. Позволяет инженеру надиктовать текст, когда руки заняты или загрязнены.

**Область применения:** только поле «Дополнительные рекомендации» (свободный текст). К чек-боксам типовых рекомендаций не применяется.

**Страницы интеграции:**
- `client/src/pages/TaskPage.tsx` — индивидуальная задача
- `client/src/pages/GroupTaskPage.tsx` — групповая задача (климатическое оборудование)

### 19.2. Архитектура

| Файл | Назначение |
|------|-----------|
| `client/src/hooks/useSpeechRecognition.ts` | Кастомный хук — инкапсуляция Web Speech API |
| `client/src/components/VoiceInput.tsx` | UI-компонент: TextArea + кнопка микрофона |
| `client/src/types/speech-recognition.d.ts` | TypeScript-типы для SpeechRecognition (ambient declaration) |

**Хук `useSpeechRecognition`** — интерфейс:
```typescript
interface UseSpeechRecognitionReturn {
  isListening: boolean;       // идёт ли запись
  isSupported: boolean;       // поддерживается ли Speech API
  interimTranscript: string;  // промежуточный текст (interim results)
  startListening: () => void; // начать распознавание
  stopListening: () => void;  // остановить распознавание
  error: string | null;       // текст ошибки
}
```

### 19.3. Параметры распознавания (Web Speech API)

| Параметр | Значение | Описание |
|----------|----------|----------|
| `lang` | `'ru-RU'` | Русский язык |
| `interimResults` | `true` | Промежуточные результаты отображаются курсивом в реальном времени |
| `continuous` | `true` | Непрерывный режим (паузы не останавливают распознавание) |

**Таймаут тишины:** автоматическая остановка через 5 секунд тишины (fallback, если инженер забыл остановить вручную).

**Ручная остановка:** повторный клик по микрофону вызывает `recognition.stop()`.

### 19.4. Состояния пиктограммы микрофона

| Состояние | Визуальное отображение | Поведение |
|-----------|----------------------|-----------|
| Ожидание | Серый контурный микрофон | Клик запускает распознавание |
| Запись | Красный микрофон с пульсацией | Повторный клик — остановка |
| Ошибка | Красный перечёркнутый микрофон | Тултип с причиной |
| Недоступно | Полупрозрачный серый | Офлайн-режим, клик неактивен |

### 19.5. Логика вставки текста

- Текст вставляется в позицию курсора или в конец (если курсор не установлен)
- Если в поле уже есть текст — надиктованный текст добавляется через пробел
- Автоматическая очистка пробелов (`.trim()`)
- Промежуточные результаты (`interim`) отображаются курсивом, финальные — обычным текстом

### 19.6. Взаимодействие с автосохранением

На время записи (состояние «Listening») автосохранение **приостанавливается**. После остановки — возобновляется и сохраняет итоговый текст. Это предотвращает множественные срабатывания автосохранения при каждом interim-результате.

### 19.7. Офлайн-режим

Web Speech API требует активного подключения к сети (распознавание происходит на серверах Google/Apple). При отсутствии сети:
- Используется хук `useOnlineStatus` для определения статуса
- Пиктограмма микрофона переходит в состояние «Недоступно» (Disabled)
- Тултип: *«Голосовой ввод недоступен без подключения к интернету»*
- При восстановлении сети — автоматический возврат в активное состояние

### 19.8. Совместимость браузеров

| Платформа | Поддержка |
|-----------|-----------|
| Android Chrome / Edge | Полная поддержка |
| Android Samsung Internet | Частичная (`continuous` может работать нестабильно) |
| iOS Safari 14.5+ | `webkitSpeechRecognition` (может потребоваться разрешение микрофона при первом использовании) |
| Браузер без поддержки | Компонент рендерит обычный `TextArea` без кнопки микрофона |

### 19.9. Безопасность и приватность

- Данные с микрофона **не отправляются** на бэкенд приложения — обрабатываются браузером и сервисами ОС (Google/Apple)
- При первом использовании отображается предупреждение: *«Голосовой ввод использует сервисы распознавания речи вашего браузера (Google/Apple). Не диктуйте конфиденциальную информацию.»*
- Флаг показа предупреждения хранится в `localStorage`

> Раздел добавлен в соответствии с ТЗ «Фонарик» v1.1 от 24.07.2026.

### 20.1. Назначение

Управление встроенным фонариком мобильного устройства из интерфейса визита. Функция доступна только инженерам в мобильном PWA (≤768px). В десктопной версии не отображается.

### 20.3. Web API

- **MediaDevices.getUserMedia()** — запрос доступа к камере (`facingMode: "environment"`)
- **MediaTrackCapabilities.torch** — проверка поддержки фонарика
- **MediaTrackConstraintSet.torch** — включение/выключение через `applyConstraints({ advanced: [{ torch: true }] })`
- **Battery API** (опционально) — уведомление при заряде < 5%

### 20.4. Состояния пиктограммы

| Состояние | Отображение | Поведение |
|-----------|-------------|-----------|
| Выключен | Серый контурный (#94A3B8) | Клик → включение |
| Включен | Жёлтый со свечением (#FBBF24) | Клик → выключение |
| Недоступно | Скрыт | — |
| Камера занята | Полупрозрачный серый | Тултип «Камера используется для фотофиксации» |

### 20.5. Автовыключение

Фонарик автоматически выключается при:
- Сворачивании приложения (`visibilitychange` → `hidden`)
- Завершении сессии (logout)
- Блокировке устройства
- Критической ошибке API

Фонарик **остаётся включённым** при навигации между страницами визита (единый сеанс).

### 20.6. Уведомления

- **Низкий заряд (< 5%)** — toast: *«Низкий заряд батареи. Фонарик может ускорить разряд.»*
- **Перегрев (> 15 мин)** — toast: *«Фонарик работает более 15 минут. Рекомендуется выключить.»*

### 20.7. Fallback для iOS

Если Torch API недоступен (iOS Safari < 17) — модальное окно с инструкцией по включению фонарика через Пункт управления.

### 20.8. Совместимость

| Браузер | Поддержка |
|---------|-----------|
| Chrome Android 90+ | ✅ Полная |
| Samsung Internet | ✅ Полная |
| Firefox Android | ⚠️ Частичная |
| Safari iOS 17+ | ⚠️ Ограниченная |
| iOS Safari < 17 | ❌ Fallback-инструкция |

### 20.9. Безопасность

- Доступ к камере запрашивается **только при первом включении** фонарика (не при загрузке)
- Видеопоток **не записывается и не передаётся** на сервер
- Результат `isSupported()` **кэшируется** — нет повторного запроса разрешения
- iOS: не вызывать `getUserMedia` при загрузке страницы (диалог запроса камеры)

| Статус | Описание | Кто устанавливает |
|--------|----------|-------------------|
| `draft` | Черновик, данные не сохранены на сервере | Инженер (автоматически) |
| `in_progress` | Визит в работе, инженер на объекте | Инженер (при начале работ) |
| `completed` | Визит завершён, все условия выполнены | Инженер (при завершении) |
| `sent` | Отправлен ТМ на согласование | Инженер (после завершения) |
| `accepted` | Принят ТМ | ТМ МТР |
| `rejected` | Отклонён ТМ (с указанием причины) | ТМ МТР |

**Переходы:**

- **draft → in_progress** — инженер начинает заполнение работ / делает фото
- **in_progress → completed** — инженер нажимает «Завершить визит» (без модального подтверждения); выполняется автоматический переход на страницу отчёта
- **completed → sent** — инженер отправляет визит ТМ
- **sent → accepted / rejected** — ТМ принимает или отклоняет визит
- **completed → in_progress** — при сохранении визита в статусе `completed`, если условия завершения не выполнены (например, удалены работы или фото), статус автоматически возвращается в `in_progress`

### 21.6. Сценарий визита МТР

Полный сценарий работы инженера МТР на объекте:

```
1. Фото ДО          — фиксация исходного состояния (через камеру устройства)
2. Добавление работ  — выбор видов работ из справочника, указание количества
3. Фото ПОСЛЕ        — фиксация результата выполненных работ
4. Завершить визит   — статус → completed, автоматический переход на страницу отчёта
5. Страница отчёта   — просмотр сводки: адрес, работы, фото
6. Скачать ZIP       — архив содержит PDF-отчёт + все фотографии визита
```

### 21.7. Офлайн-режим

Модуль МТР поддерживает полную работу без сетевого соединения:

- **Локальное хранилище** — все данные визитов, работ и фото сохраняются в IndexedDB через Dexie.js
- **Очередь синхронизации (sync queue)** — действия, выполненные офлайн (создание визита, добавление работ, загрузка фото), помещаются в очередь
- **Автоматическая синхронизация** — при восстановлении соединения очередь воспроизводится: данные отправляются на сервер в порядке поступления
- **Разрешение конфликтов** — при конфликте (например, визит удалён на сервере) пользователь получает уведомление
