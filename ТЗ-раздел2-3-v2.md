# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (разделы 2 и 3, редакция 2.1)

## 2. ИЗМЕНЕНИЯ В СТРУКТУРЕ БАЗЫ ДАННЫХ

### 2.0. Принцип: расширяем существующие сущности

В проекте **уже есть** инфраструктура для предложений по оборудованию:

| Сущность | Что уже есть | Что добавим |
|----------|-------------|-------------|
| `EquipmentProposal` | Создание, одобрение, отклонение, статусы pending/approved/rejected | Тип запроса (новое/перенос), TTL, причина отклонения, старое помещение |
| `ObjectEquipment` | Поля `roomConfirmedAt`, `roomConfirmedBy`, `isActive` | Статус подтверждения (`confirmed`/`pending`), создатель, TTL |
| `Model` | Модерация моделей (pending/approved/rejected) | *Без изменений* — используется как есть для новых моделей |
| `Manufacturer` | Справочник производителей | *Без изменений* — инженер добавляет через существующий API |
| `Task` | Поля `brand`, `model`, `serialNumber`, `roomTypeCode` | *Без изменений* — уже хранит snapshot-данные |

**Не создаётся** новая таблица `equipment_change_requests` — её функциональность полностью покрывается расширением `EquipmentProposal`.

**Создаётся** новая таблица `notifications` — в проекте отсутствует инфраструктура уведомлений.

### 2.1. Таблица `equipment_proposals` — расширение

#### Новые поля

```sql
ALTER TABLE equipment_proposals
  ADD COLUMN request_type VARCHAR(20) NOT NULL DEFAULT 'new_equipment'
    CHECK (request_type IN ('new_equipment', 'room_change', 'brand_change')),
  ADD COLUMN old_room_type_code VARCHAR(50),
  ADD COLUMN rejection_reason TEXT,
  ADD COLUMN pending_until TIMESTAMP,
  ADD COLUMN object_equipment_id UUID REFERENCES object_equipment(id);
```

| Поле | Назначение | Заполняется при |
|------|-----------|-----------------|
| `request_type` | Тип запроса: новое оборудование, перенос в другое помещение, смена бренда/модели | Всегда |
| `old_room_type_code` | Код помещения, откуда переносится оборудование | `room_change` |
| `rejection_reason` | Причина отклонения администратором | Отклонение |
| `pending_until` | Дата автоматического истечения (TTL) | Создание инженером |
| `object_equipment_id` | Ссылка на существующую запись `object_equipment` (для переноса) | `room_change` |

#### Индексы

```sql
CREATE INDEX idx_equipment_proposals_request_type ON equipment_proposals(request_type);
CREATE INDEX idx_equipment_proposals_pending_until ON equipment_proposals(pending_until);
CREATE INDEX idx_equipment_proposals_oe_pending ON equipment_proposals(object_equipment_id, status)
  WHERE status = 'pending';
```

Последний индекс — частичный — обеспечивает быструю проверку «есть ли уже pending-proposal для этого оборудования» (защита от конфликтующих переносов).

#### Заполнение существующих данных

Все существующие записи `equipment_proposals` получают:
- `request_type = 'new_equipment'` (через `DEFAULT`)
- `pending_until = NULL` (существующие записи уже рассмотрены — `approved` или `rejected`, TTL для них не применяется)

### 2.2. Таблица `object_equipment` — расширение

#### Новые поля

```sql
ALTER TABLE object_equipment
  ADD COLUMN confirmation_status VARCHAR(20) DEFAULT 'confirmed'
    CHECK (confirmation_status IN ('confirmed', 'pending')),
  ADD COLUMN created_by UUID REFERENCES users(id),
  ADD COLUMN pending_until TIMESTAMP;
```

| Поле | Назначение |
|------|-----------|
| `confirmation_status` | Статус записи: `confirmed` (создана администратором/импортом) или `pending` (создана инженером, ждёт подтверждения) |
| `created_by` | Кто создал запись (для отслеживания) |
| `pending_until` | Дата истечения TTL. `NULL` для `confirmed` записей |

#### Заполнение существующих данных

Все существующие записи `object_equipment` получают:
- `confirmation_status = 'confirmed'` (через `DEFAULT`)
- `created_by = NULL` (созданы администратором/импортом)
- `pending_until = NULL`

#### Логика переноса (без дублирования)

При переносе оборудования из помещения А в помещение Б **не создаётся новая запись** в `object_equipment`. Вместо этого:

1. **Обновляется** существующая запись: `roomTypeCode` меняется на код помещения Б
2. **Создаётся** запись в `equipment_proposals` с `request_type = 'room_change'`, `object_equipment_id = id записи`, `old_room_type_code = код помещения А`
3. Записи `object_equipment` присваивается `confirmation_status = 'pending'`, `pending_until = NOW() + 30 дней`

Это работает благодаря тому, что уникальные индексы `[addressId, equipmentTypeCode, serialNumber]` и `[addressId, equipmentTypeCode, locationDescription]` **не включают `roomTypeCode`** — смена помещения не нарушает уникальность.

#### Откат переноса при отклонении

Если администратор отклоняет proposal типа `room_change`:
- `object_equipment.roomTypeCode` восстанавливается из `equipment_proposals.old_room_type_code`
- `confirmation_status` возвращается в `'confirmed'`
- `pending_until` обнуляется

### 2.3. Таблица `notifications` — новая

В проекте отсутствует инфраструктура уведомлений (нет таблицы, API, клиентских компонентов). Создаётся минимальная таблица для внутренних уведомлений.

```sql
CREATE TABLE notifications (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id),
  type VARCHAR(30) NOT NULL
    CHECK (type IN (
      'proposal_created',       -- администратору и ТМ: создана новая pending-запись
      'proposal_approved',      -- инженеру: запись подтверждена
      'proposal_rejected',      -- инженеру: запись отклонена
      'proposal_expiring_soon', -- администратору и ТМ: TTL истекает через 3 дня
      'proposal_expired',       -- инженеру: запись удалена по TTL
      'equipment_removed'       -- инженеру: оборудование удалено из активного визита
    )),
  title VARCHAR(200) NOT NULL,
  message TEXT NOT NULL,
  entity_type VARCHAR(30),       -- 'equipment_proposal' | 'object_equipment' | 'visit'
  entity_id UUID,                -- ID связанной сущности
  is_read BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_notifications_user_unread ON notifications(user_id, is_read);
CREATE INDEX idx_notifications_created ON notifications(created_at);
```

#### Prisma-модель

```prisma
model Notification {
  id         String   @id @default(uuid())
  userId     String   @map("user_id")
  type       String
  title      String
  message    String
  entityType String?  @map("entity_type")
  entityId   String?  @map("entity_id")
  isRead     Boolean  @default(false) @map("is_read")
  createdAt  DateTime @default(now()) @map("created_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, isRead])
  @@index([createdAt])
  @@map("notifications")
}
```

В модель `User` добавляется связь:
```prisma
notifications Notification[]
```

### 3.1. Расширение `/api/proposals` — новые эндпоинты

#### 3.1.1. Предложение переноса оборудования

```
POST /api/proposals/room-change
```

**Роль:** engineer

**Тело запроса:**
```json
{
  "objectEquipmentId": "uuid",          // ID переносимой записи
  "newRoomTypeCode": "client_room"      // Код нового помещения
}
```

**Логика:**
1. Найти `object_equipment` по `objectEquipmentId`, проверить `isActive = true`
2. Проверить, что новое помещение отличается от текущего `roomTypeCode`
3. **Проверить, что для этой записи нет другого pending-proposal** (запрос в `equipment_proposals WHERE object_equipment_id = ? AND status = 'pending'`). Если есть — вернуть `409 Conflict` с сообщением: *"Для этого оборудования уже есть ожидающий подтверждения запрос. Дождитесь рассмотрения или отмените предыдущий запрос."*
4. Создать `equipment_proposal`:
   - `request_type = 'room_change'`
   - `object_equipment_id = objectEquipmentId`
   - `old_room_type_code = текущий roomTypeCode записи`
   - `roomTypeCode = newRoomTypeCode`
   - `addressId, equipmentTypeCode, brand, model, serialNumber` — копируются из записи
   - `status = 'pending'`
   - `pending_until = NOW() + 30 дней`
5. Обновить `object_equipment`:
   - `roomTypeCode = newRoomTypeCode` (оборудование сразу «переезжает»)
   - `confirmation_status = 'pending'`
   - `pending_until = NOW() + 30 дней`
6. Создать `notification` для всех администраторов **и** ТМ, привязанных к этому объекту: `type = 'proposal_created'`
7. Записать в `audit_log`

**Ответ:** `201 Created` — созданный proposal

**Ошибки:**
- `404` — `object_equipment` не найден или неактивен
- `409` — уже есть pending-proposal для этой записи
- `400` — новое помещение совпадает с текущим

#### 3.1.2. Расширенное создание предложения (новый изготовитель / модель)

```
POST /api/proposals  (расширение существующего)
```

**Тело запроса (новые опциональные поля):**
```json
{
  "addressId": "uuid",
  "equipmentTypeCode": "splitvn",
  "roomTypeCode": "server",
  "brand": "Samsung",
  "model": "AR12",
  "serialNumber": "SN987654321",
  "locationDescription": "Над кассой №3",
  "newManufacturer": {               // ← НОВОЕ: добавить нового производителя
    "name": "Samsung",
    "country": "Южная Корея"
  },
  "newModel": {                      // ← НОВОЕ: добавить новую модель
    "modelName": "AR12",
    "fullModelName": "AR12 Series"
  }
}
```

**Логика:**
1. Если `newManufacturer` указан — найти существующего по имени (case-insensitive) или создать запись в `manufacturers`
2. Если `newModel` указан — создать запись в `models` со `status = 'pending'` (используя существующий механизм модерации моделей). `submittedById = req.userId`
3. Далее — стандартная логика создания proposal (как сейчас)
4. `pending_until = NOW() + 30 дней`
5. `confirmation_status = 'pending'` для создаваемой записи `object_equipment`
6. Создать `notification` для администраторов и ТМ объекта

**Ответ:** `201 Created`

#### 3.1.3. Редактирование pending-предложения (инженер)

```
PATCH /api/proposals/:id
```

**Роль:** engineer (только свои proposals в статусе `pending`)

**Тело запроса (все поля опциональны):**
```json
{
  "roomTypeCode": "client_room",
  "brand": "Daikin",
  "model": "FTXS35K",
  "serialNumber": "SN12345678",
  "locationDescription": "У окна"
}
```

**Логика:**
1. Проверить: proposal существует, `status = 'pending'`, `proposedById = req.userId`
2. Если `request_type = 'room_change'` и изменился `roomTypeCode` — также обновить `object_equipment.roomTypeCode`
3. Обновить proposal
4. Записать в `audit_log`

**Ответ:** `200 OK` — обновлённый proposal

---

#### 3.1.4. Удаление (отмена) pending-предложения (инженер)

```
DELETE /api/proposals/:id
```

**Роль:** engineer (только свои proposals в статусе `pending`)

**Логика:**
1. Проверить: proposal существует, `status = 'pending'`, `proposedById = req.userId`
2. Если `request_type = 'room_change'` — откатить `object_equipment`:
   - Восстановить `roomTypeCode` из `old_room_type_code`
   - `confirmation_status = 'confirmed'`, `pending_until = NULL`
3. Если `request_type = 'new_equipment'` — деактивировать связанную `object_equipment`:
   - `is_active = FALSE`, `confirmation_status = 'confirmed'`, `pending_until = NULL`
   - **Физическое удаление не производится** (согласовано с принципом soft delete проекта)
4. Обновить proposal: `status = 'rejected'`, `reviewedById = req.userId`, `reviewedAt = NOW()`, `rejection_reason = 'Отменено инженером'`
5. Записать в `audit_log`

**Ответ:** `200 OK` — обновлённый proposal со статусом `rejected`

**Примечание:** Proposal не удаляется физически — он остаётся в БД со статусом `rejected` для аудита. Это согласовано с подходом cron-задачи (раздел 3.4), которая не производит физического удаления.

---

#### 3.1.5. Одобрить перенос (расширение существующего approve)

```
PUT /api/proposals/admin/:id/approve  (расширение)
```

**Логика для `request_type = 'room_change'`:**
1. Найти proposal, проверить `status = 'pending'`
2. Предложение уже применено (roomTypeCode обновлён при создании) — просто подтверждаем:
   - `object_equipment.confirmation_status = 'confirmed'`
   - `object_equipment.pending_until = NULL`
   - `object_equipment.roomConfirmedAt = NOW()`
   - `object_equipment.roomConfirmedBy = req.userId`
3. Обновить proposal: `status = 'approved'`, `reviewedById`, `reviewedAt`
4. Создать `notification` инженеру: `type = 'proposal_approved'`

**Логика для `request_type = 'new_equipment'`:**
1. Создать `object_equipment` из данных proposal (аналогично существующей логике)
2. Установить `confirmation_status = 'confirmed'`, `created_by = proposal.proposedById`
3. Обновить proposal: `status = 'approved'`, `reviewedById`, `reviewedAt`
4. Обновить `proposal.object_equipment_id` — связать с созданной записью
5. Создать `notification` инженеру: `type = 'proposal_approved'`

#### 3.1.6. Отклонить с причиной (расширение существующего reject)

```
PUT /api/proposals/admin/:id/reject  (расширение)
```

**Тело запроса (новое опциональное поле):**
```json
{
  "reason": "Оборудование уже учтено в другом помещении"
}
```

**Логика для `request_type = 'room_change'`:**
1. Откатить `object_equipment`:
   - `roomTypeCode = proposal.old_room_type_code`
   - `confirmation_status = 'confirmed'`
   - `pending_until = NULL`
2. Обновить proposal: `status = 'rejected'`, `reviewedById`, `reviewedAt`, `rejection_reason = reason`
3. Создать `notification` инженеру: `type = 'proposal_rejected'`

**Логика для `request_type = 'new_equipment'`:**
1. Если `object_equipment` уже создана — деактивировать: `is_active = FALSE`
2. Обновить proposal: `status = 'rejected'`, `reviewedById`, `reviewedAt`, `rejection_reason = reason`
3. Создать `notification` инженеру: `type = 'proposal_rejected'`

#### 3.1.7. Массовые действия

```
PUT /api/proposals/admin/batch
```

**Роль:** admin

**Тело запроса:**

1. Применить approve/reject для каждого proposal (по цепочке логики из 3.1.5 / 3.1.6)

3. Создать уведомления для каждого инженера
4. Вернуть результат: `{ approved: N, rejected: M, errors: [{ id, message }] }`

### 3.4. Cron-задача (внутренний эндпоинт)

```
POST /api/internal/cron/process-expired-proposals
```

**Защита:** Вызывается только изнутри контейнера (localhost) или по секретному токену из переменной окружения `CRON_SECRET`.

**Расписание:** Ежедневно в 03:00 (через `node-cron`, инициализация в `server/src/index.ts`).

**Логика:**

```
Шаг 1. Пометить истёкшие proposals:
  UPDATE equipment_proposals
  SET status = 'expired', reviewed_at = NOW()
  WHERE status = 'pending' AND pending_until < NOW()

Шаг 2. Откатить object_equipment (для room_change):
  UPDATE object_equipment
  SET room_type_code = ep.old_room_type_code,
      confirmation_status = 'confirmed',
      pending_until = NULL
  FROM equipment_proposals ep
  WHERE ep.object_equipment_id = object_equipment.id
    AND ep.status = 'expired'
    AND ep.request_type = 'room_change'
    AND ep.reviewed_at >= NOW() - INTERVAL '1 hour'
    -- ^ защита от повторной обработки: только записи, помеченные на шаге 1
    --   (т.е. reviewed_at обновлён в последние минуту)

Шаг 3. Деактивировать object_equipment (для new_equipment):
  UPDATE object_equipment
  SET is_active = FALSE,
      confirmation_status = 'confirmed',
      pending_until = NULL
  FROM equipment_proposals ep
  WHERE ep.object_equipment_id = object_equipment.id
    AND ep.status = 'expired'
    AND ep.request_type = 'new_equipment'
    AND ep.reviewed_at >= NOW() - INTERVAL '1 hour'

Шаг 4. Пометить в активных визитах (только new_equipment):
  UPDATE task_equipment_items
  SET status = 'removed_expired'
  WHERE object_equipment_id IN (
    SELECT object_equipment_id FROM equipment_proposals
    WHERE status = 'expired'
      AND request_type = 'new_equipment'
      AND reviewed_at >= NOW() - INTERVAL '1 hour'
  )

Шаг 5. Уведомить инженеров об истечении (без дублей):
  INSERT INTO notifications (user_id, type, title, message, entity_type, entity_id)
  SELECT ep.proposed_by_id, 'proposal_expired',
    'Оборудование не подтверждено',
    'Оборудование "' || COALESCE(ep.brand || ' ', '') || COALESCE(ep.model, '') || '" удалено из справочника, т.к. не было подтверждено',
    'equipment_proposal', ep.id
  FROM equipment_proposals ep
  WHERE ep.status = 'expired'
    AND ep.reviewed_at >= NOW() - INTERVAL '1 hour'
    AND NOT EXISTS (
      SELECT 1 FROM notifications n
      WHERE n.entity_id = ep.id AND n.type = 'proposal_expired'
    )

Шаг 6. Предупреждение за 3 дня до истечения (без дублей):
  INSERT INTO notifications (user_id, type, title, message, entity_type, entity_id)
  SELECT DISTINCT ep.proposed_by_id, 'proposal_expiring_soon',
    'Предложение скоро истечёт',
    'Оборудование "' || COALESCE(ep.brand || ' ', '') || COALESCE(ep.model, '') || '" будет удалено через ' ||
      EXTRACT(DAY FROM (ep.pending_until - NOW()))::int || ' дн.',
    'equipment_proposal', ep.id
  FROM equipment_proposals ep
  WHERE ep.status = 'pending'
    AND ep.pending_until BETWEEN NOW() AND NOW() + INTERVAL '3 days'
    AND NOT EXISTS (
      SELECT 1 FROM notifications n
      WHERE n.entity_id = ep.id AND n.type = 'proposal_expiring_soon'
    )
```

**Защита от повторной обработки:** Шаг 1 обновляет `reviewed_at`, шаги 2–3 фильтруют по `reviewed_at >= NOW() - 1 hour`. Это гарантирует, что при повторном запуске cron уже обработанные записи не будут обработаны повторно.

**Защита от дублей уведомлений:** Шаги 5–6 используют `NOT EXISTS` для проверки, что уведомление данного типа для данной сущности ещё не создано.

**Важно:** Физическое удаление записей **не производится**. Истёкшие proposals остаются в БД со статусом `expired` для аудита. `object_equipment` помечаются `is_active = FALSE` (soft delete).

### 3.5. Уведомления для ТМ

При создании pending-предложения уведомления получают не только администраторы, но и ТМ, привязанные к данному объекту через `tm_objects`.

**Логика отправки `proposal_created`:**
```sql
INSERT INTO notifications (user_id, type, title, message, entity_type, entity_id)
SELECT u.id, 'proposal_created',
  'Новое предложение по оборудованию',
  'Инженер ' || author.full_name || ' предложил изменение для объекта ' || a.full_address,
  'equipment_proposal', proposal.id
FROM users u
JOIN tm_objects tm ON tm.tm_id = u.id AND tm.address_id = proposal.address_id
CROSS JOIN (SELECT full_name FROM users WHERE id = proposal.proposed_by_id) author
CROSS JOIN (SELECT full_address FROM addresses WHERE id = proposal.address_id) a
WHERE u.role = 'tm' AND u.is_active = true;

-- Плюс все администраторы:
INSERT INTO notifications (user_id, type, title, message, entity_type, entity_id)
SELECT u.id, 'proposal_created', ...
FROM users u
WHERE u.role = 'admin' AND u.is_active = true;
```

Аналогичная логика применяется для `proposal_expiring_soon`.
