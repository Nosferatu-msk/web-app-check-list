## 3. Что может пойти не так

### 3.1. Эндпоинт создаёт некорректные визиты

**Симптомы:**
- Клонированный визит имеет битые задачи (нет equipmentTypeId, дубликаты)
- Автопривязка заявок создала некорректные VisitRequest
- Параметры задач не очищены

**Причины:**
- Ошибка в логике транзакции
- Неправильный маппинг полей задач
- Баг в автопривязке заявок

### 3.2. UI сломал существующий dropdown

**Симптомы:**
- Кнопка ⋮ в VisitPage не работает
- Dropdown не открывается или показывает пустое меню
- Существующие действия (удаление) не работают

**Причины:**
- Конфликт с существующим кодом VisitPage
- Неправильный импорт компонентов Ant Design

### 3.3. Клонирование визитов коллег — неправильная фильтрация

**Симптомы:**
- Инженер ВИК видит задачи ИСЖ в клонированном визите
- Задачи не фильтруются по специализации

**Причины:**
- Ошибка в логике проверки `specializationReq`
- Неправильное определение специализации инженера

### 3.4. Дубликаты активных визитов

**Симптомы:**
- Инженер клонировал визит, но у него уже был активный визит по адресу
- Защита от дубликатов не сработала

**Причины:**
- Неправильный SQL-запрос проверки (не учитывает `visitEngineers`)
- Граничный случай с датой (визит создан в конце прошлого месяца)

### Этап 2: Удаление некорректных клонированных визитов (если данные уже созданы)

**Время отката:** 10–30 минут (зависит от количества)

**Шаг 2.1: Диагностика — найти все клонированные визиты**

Клонированные визиты можно найти по AuditLog:
```sql
SELECT 
  al.entity_id AS visit_id,
  al.old_value->>'sourceVisitId' AS source_visit_id,
  al.created_at,
  al.user_id,
  v.address_id,
  v.status,
  v.date_start
FROM audit_log al
JOIN visits v ON v.id = al.entity_id
WHERE al.action = 'visit_cloned'
ORDER BY al.created_at DESC;
```

**Шаг 2.2: Показать Анне список клонированных визитов**

```sql
SELECT 
  v.id AS clone_id,
  v.date_start AS clone_date,
  v.engineer_name,
  a.full_address,
  v.status,
  (SELECT COUNT(*) FROM tasks WHERE visit_id = v.id) AS tasks_count,
  al.old_value->>'sourceVisitId' AS source_id,
  al.created_at
FROM audit_log al
JOIN visits v ON v.id = al.entity_id
JOIN addresses a ON a.id = v.address_id
WHERE al.action = 'visit_cloned'
ORDER BY al.created_at DESC;
```

**Шаг 2.3: Согласовать с Анной удаление конкретных визитов**

⚠️ **НЕ УДАЛЯТЬ БЕЗ ПОДТВЕРЖДЕНИЯ АННЫ** (feedback-approve-data-changes.md)

**Шаг 2.4: Мягкое удаление визитов (isDeleted = true)**

```sql
-- Для конкретного клонированного визита:
UPDATE visits 
SET is_deleted = true, 
    deleted_at = NOW(), 
    deleted_by_id = '<admin_user_id>'
WHERE id = '<clone_visit_id>' 
  AND is_deleted = false;
```

**Шаг 2.5: Удаление VisitRequest (связи с заявками)**

```sql
-- VisitRequest каскадно удаляется при удалении визита (onDelete: Cascade)
-- Проверить:

```

## 5. SQL-скрипты отката (подготовлены заранее)

### 5.1. Диагностика: все клонированные визиты

```sql
-- Файл: server/scripts/diagnose-cloned-visits.sql
SELECT 
  v.id AS clone_id,
  v.date_start AS clone_date,
  v.engineer_name,
  v.status,
  a.full_address,
  (SELECT COUNT(*) FROM tasks WHERE visit_id = v.id) AS tasks_count,
  (SELECT COUNT(*) FROM visit_requests WHERE visit_id = v.id) AS requests_count,
  al.old_value->>'sourceVisitId' AS source_id,
  al.created_at AS cloned_at,
  u.full_name AS cloned_by
FROM audit_log al
JOIN visits v ON v.id = al.entity_id
JOIN addresses a ON a.id = v.address_id
LEFT JOIN users u ON u.id = al.user_id
WHERE al.action = 'visit_cloned'
ORDER BY al.created_at DESC;
```

### 5.2. Мягкое удаление конкретного клона

```sql
-- Файл: server/scripts/soft-delete-cloned-visit.sql
-- Заменить <CLONE_VISIT_ID> и <ADMIN_USER_ID>
UPDATE visits 
SET is_deleted = true, 
    deleted_at = NOW(), 
    deleted_by_id = '<ADMIN_USER_ID>'
WHERE id = '<CLONE_VISIT_ID>' 
  AND is_deleted = false;
```

### 5.3. Массовое мягкое удаление всех клонов


## 6. Проверочные запросы после отката

### 6.1. Проверить, что клоны удалены

```sql
SELECT COUNT(*) AS active_clones
FROM visits v
JOIN audit_log al ON al.entity_id = v.id
WHERE al.action = 'visit_cloned'
  AND v.is_deleted = false;
-- Ожидается: 0
```

### 6.2. Проверить, что заявки не пострадали

```sql
-- Проверить, что VisitRequest для исходных визитов на месте
SELECT 
  v.id AS source_visit_id,
  COUNT(vr.id) AS requests_count
FROM visits v
LEFT JOIN visit_requests vr ON vr.visit_id = v.id
WHERE v.id IN (
  SELECT (old_value->>'sourceVisitId')::uuid 
  FROM audit_log 
  WHERE action = 'visit_cloned'
)
GROUP BY v.id;
-- Ожидается: requests_count > 0 для визитов с заявками
```

### 6.3. Проверить, что существующие визиты не затронуты

```sql
-- Количество визитов за последний месяц (до и после отката должно совпадать)
SELECT 
  DATE_TRUNC('day', date_start) AS day,
  COUNT(*) AS visits_count
FROM visits
WHERE date_start >= CURRENT_DATE - INTERVAL '30 days'
  AND is_deleted = false
GROUP BY 1
ORDER BY 1;
```

## 7. Критерии успеха отката

| Критерий | Проверка | Ожидается |
|---|---|---|
| Клонированные визиты удалены | `active_clones` (запрос 6.1) | 0 |
| Заявки исходных визитов на месте | `requests_count` (запрос 6.2) | > 0 |
