# ТЗ: Привязка заявок к конкретному оборудованию по серийному номеру

**Дата:** 14.10.2026  
**Статус:** Утверждено (вопросы закрыты, ревью пройдено)

---

## 1. Проблема

Текущий процесс связывания заявок с визитами работает **без учёта конкретной единицы оборудования**. Если на объекте 10 единиц одного типа (например, 10 пурифаеров), а заявка создана на 1 конкретный (с известным серийным номером), то система связывает визит со **всеми 10 заявками** на пурифаеры этого объекта.

**Корень проблемы:** в модели `ImportedRequest` отсутствует поле `serialNumber`. Автопривязка ищет заявки только по паре `(addressId, equipmentTypeId)` — без идентификации конкретной единицы оборудования.

**Последствия:**
- Инженер создаёт визит с задачей по 1 пурифаеру → 10 связей с заявками
- Другой инженер делает визит на тот же объект → ещё 10 связей с теми же заявками
- Невозможно определить, какая заявка фактически выполнена
- Отчёты по заявкам показывают некорректные данные

## 2. Целевое решение

### 2.1. Новое поле в заявке

Добавить в модель `ImportedRequest` поле `serialNumber` (String, nullable).

### 2.2. Правила связывания

| Тип заявки | Связь | Логика привязки |
|---|---|---|
| **ИСЖ объекта** (`iszh_object`) | 1 заявка → **много визитов** | Без изменений. Привязка по `(addressId, contractId, период)`. Серийный номер игнорируется. |
| **Конкретное оборудование** (не `iszh_object`) + `serialNumber` | 1 заявка → **1 визит** (в рамках месяца) | Привязка по `(addressId, contractId, equipmentTypeCode, serialNumber, период)`. Визит может содержать задачи из разных заявок. |
| **Конкретное оборудование** (не `iszh_object`) + `serialNumber = null` | **Не привязывается автоматически** | Заявка импортирована, но ждёт указания serialNumber. Связи с визитами нет. |

### 2.3. Условия связи заявки с визитом

Заявка связывается с визитом при **совпадении ВСЕХ** условий:
1. **Адрес:** `matchedAddressId = visit.addressId`
2. **Договор:** если `visit.contractId` не null → `contractId = visit.contractId`. Если `visit.contractId = null` (у ТМ нет договора с этим объектом) → проверка договора пропускается.
3. **Период:** `startDate ≤ visit.dateStart ≤ deadline`
4. **Для не-ИСЖ с serialNumber:** совпадение `(equipmentTypeCode, serialNumber)` заявки с `(equipmentTypeCode, serialNumber)` оборудования в задаче визита

> **Примечание:** `contractId` автоматически устанавливается у визита из связи ТМ → объект → договор. Если у ТМ нет договора с этим объектом — `contractId = null`.

### 2.4. Ограничение уникальности

- В одном отчётном периоде (месяц) заявка на конкретное оборудование (кроме ИСЖ объекта) может быть связана **только с одним визитом**.
- Один визит может содержать задачи из **разных** заявок (разные serialNumber или разные типы оборудования).
- Заявка ИСЖ объекта + заявка на конкретное оборудование могут быть связаны с одним и тем же визитом.

### 2.5. Групповое климатическое оборудование (`group_climate`)

Для задач типа `group_climate` (сплит-системы с внутренним + наружным блоком):
- Проверка serialNumber ведётся по **всем единицам оборудования** в группе (`TaskEquipmentItem` → `ObjectEquipment.serialNumber`).
- Если хотя бы одна единица в группе имеет `serialNumber` и `equipmentTypeCode`, совпадающие с заявкой → связь устанавливается.

## 4. Изменения импорта заявок

### 4.1. Парсинг Excel

Добавить в `RequestRow` поле `serialNumber`. В `parseRequestsExcel` добавить поиск колонки:

```typescript
const serialNumber = findCol(['серийный №', 'серийный номер', 'серийник', 'serial number', 's/n']);
```

### 4.2. Нормализация serialNumber

```typescript
// Trim пробелов по краям, валидация
const normalizedSN = serialNumber?.trim() || null;
```

- Серийный номер может содержать **любые символы** (буквы, цифры, дефисы, слэши, точки и т.д.).
- **Запрещено:** ведущие и замыкающие пробелы (автоматически удаляются при импорте через `trim()`).
- Пустая строка после trim → `null`.

### 4.3. Валидация

- Если вид оборудования **не** `iszh_object`:
  - Заявка импортируется **в любом случае** (с serialNumber или без).
  - Если `serialNumber = null` → заявка импортируется, но **не привязывается** к визитам автоматически.
  - Если serialNumber указан, но оборудование с таким SN не найдено в `ObjectEquipment` → **предупреждение** (не ошибка). Заявка импортируется.
- Если вид оборудования `iszh_object` → serialNumber игнорируется (сохраняется, если есть, но не используется для привязки).

### 4.4. Валидация дубликатов serialNumber

**Двойная проверка:**

1. **В рамках файла:** если в Excel-файле есть две или более строк с одинаковым `(equipmentTypeCode, serialNumber)` → ошибка:
   > «Файл содержит две и более заявок на одно и то же оборудование (serialNumber: XXX).»

2. **В рамках отчётного периода в БД:** если в БД уже есть импортированная заявка с тем же `(equipmentTypeCode, serialNumber)` и пересекающимся периодом → ошибка:
   > «Заявка на оборудование с серийным номером XXX уже существует в данном отчётном периоде (заявка № YYY).»

- Для ИСЖ объекта проверка дубликатов по serialNumber **не применяется** (serialNumber игнорируется).
- Проверка периода: `NOT (existing.deadline < new.startDate OR existing.startDate > new.deadline)`.

### 4.5. Сохранение

При создании `ImportedRequest` записывать `serialNumber` из файла (после trim).

### 4.6. Автопривязка при импорте заявки

После создания `ImportedRequest` (для не-ИСЖ с serialNumber) — **автоматически искать существующие визиты** с подходящими задачами:

```typescript
// Поиск визитов с задачей по (addressId, equipmentTypeCode, serialNumber, период)
const matchingVisits = await prisma.visit.findMany({
  where: {
    addressId: request.matchedAddressId,
    contractId: request.contractId || undefined, // null → пропускаем проверку
    dateStart: { gte: request.startDate, lte: request.deadline },
    isDeleted: false,
    status: { not: 'awaiting_assignment' }, // только реальные визиты
    tasks: {
      some: {
        equipmentType: { code: request.equipmentTypeCode },
        // Проверка serialNumber: task.serialNumber или objectEquipment.serialNumber
        OR: [
          { serialNumber: request.serialNumber },
          { objectEquipment: { serialNumber: request.serialNumber } },
        ],
      },
    },
    // Для group_climate — проверка через TaskEquipmentItem
    // (отдельный запрос или JOIN)
  },
});

// Если найден визит — создать VisitRequest
if (matchingVisits.length > 0) {
  const visit = matchingVisits[0]; // первый подходящий
  await prisma.visitRequest.create({
    data: { visitId: visit.id, importedRequestId: request.id },
  });
  await prisma.importedRequest.update({
    where: { id: request.id },
    data: { visitId: visit.id },
  });
}
```

**Для `group_climate`:** перебрать `TaskEquipmentItem` → `ObjectEquipment`, найти совпадение по `(equipmentTypeCode, serialNumber)`.

## 5. Изменения логики автопривязки

### 5.1. При создании визита (`POST /api/visits`)

**ИСЖ объекта** — без изменений:
```
findMany({ matchedAddressId, equipmentType: { code: 'iszh_object' }, startDate ≤ visitDate ≤ deadline })
```

**Не-ИСЖ** — новая логика:
```typescript
// Для каждой задачи в визите с serialNumber:
const taskSN = task.serialNumber || task.objectEquipment?.serialNumber;
if (taskSN) {
  findMany({
    matchedAddressId: visit.addressId,
    contractId: visit.contractId,
    equipmentTypeCode: task.equipmentTypeCode,
    serialNumber: taskSN,
    startDate: { lte: visitDate },
    deadline: { gte: visitDate },
    // Заявка ещё не привязана к другому визиту
    visitRequests: { none: {} },
  });
}
```

### 5.2. При добавлении задачи в визит (`POST /api/visits/:visitId/tasks`)

Аналогично — при добавлении задачи с `serialNumber` искать заявки:
- `matchedAddressId = адрес визита`
- `contractId = договор визита`
- `equipmentTypeCode = тип оборудования задачи`
- `serialNumber = serialNumber задачи` (из `task.serialNumber` или `task.objectEquipment.serialNumber`)
- `startDate ≤ visitDate ≤ deadline`
- Заявка не привязана к другому визиту (`visitRequests: { none: {} }`)

**Для `group_climate`:** перебрать `TaskEquipmentItem` → `ObjectEquipment`, найти совпадение по `(equipmentTypeCode, serialNumber)` с заявкой.

### 5.3. При завершении визита (`POST /api/visits/:id/complete`)

Аналогично — автопривязка оставшихся непривязанных заявок по serialNumber задач.

### 5.4. Для ИСЖ объекта — без изменений

Привязка по-прежнему работает по `(addressId, contractId, период)`. Серийный номер не проверяется.

## 6. Редактирование serialNumber для существующих заявок

### 6.1. API endpoint

Добавить `PATCH /api/requests/:id` для обновления `serialNumber`:

```typescript
// PUT /api/requests/:id/serial-number
const schema = z.object({
  serialNumber: z.string().trim().nullable(),
});
```

- Доступ: admin, tm.
- После обновления serialNumber — **пересчитать привязки** (алгоритм ниже).

### 6.2. Алгоритм пересчёта привязок при изменении serialNumber

1. **Разорвать текущую связь** `VisitRequest` (если есть).
2. **Вернуть заявку на виртуальный визит** (`awaiting_assignment`):
   - Создать виртуальный визит (если текущий визит не является виртуальным).
   - Обновить `importedRequest.visitId` на виртуальный визит.
3. **Поискать визит** с новым serialNumber:
   - Условия: `addressId`, `contractId` (или null), `period`, `equipmentTypeCode`, `serialNumber`.
   - Если найден — создать новую связь `VisitRequest`.
   - Если не найден — заявка остаётся непривязанной (статус «Не назначена»).
4. **Логировать** действие в `RequestAssignmentLog`.

### 6.3. UI: страница заявок

- В таблице заявок добавить колонку «Серийный №».
- В деталях заявки — поле для редактирования serialNumber (для не-ИСЖ заявок).
- После сохранения — показать результат привязки (найдена/не найдена).

## 7. Обработка существующих данных

### 7.1. ИСЖ объекта — без изменений

Все существующие связи ИСЖ заявок с визитами остаются. Логика не меняется.

### 7.2. Не-ИСЖ заявки — разрыв существующих связей и пересчёт

Для всех существующих заявок, где `equipmentTypeCode != 'iszh_object'`:

1. **Разорвать** все связи `VisitRequest` с такими заявками.
2. **Очистить** `ImportedRequest.visitId` (вернуть на виртуальный визит `awaiting_assignment`).
3. **Установить** `serialNumber = null` (если не был заполнен ранее).
4. Статус заявки → «Не назначена».
5. **Пересчитать привязки:** для заявок, у которых serialNumber уже известен (не null) — попытаться автоматически привязать к существующему визиту (по алгоритму из раздела 4.6).

**Скрипт миграции данных:**

```sql
-- 0. БЭКАП (обязательно!)
CREATE TABLE imported_requests_backup AS SELECT * FROM imported_requests;
CREATE TABLE visit_requests_backup AS SELECT * FROM visit_requests;

-- 1. Разорвать VisitRequest для не-ИСЖ заявок
DELETE FROM visit_requests
WHERE imported_request_id IN (
  SELECT id FROM imported_requests
  WHERE equipment_type_code != 'iszh_object'
  OR equipment_type_code IS NULL
);

-- 2. Вернуть не-ИСЖ заявки на виртуальные визиты
UPDATE imported_requests
SET visit_id = NULL
WHERE (equipment_type_code != 'iszh_object' OR equipment_type_code IS NULL)
AND visit_id IS NOT NULL;

-- 3. Для заявок с serialNumber — пересчёт привязок (TypeScript-скрипт)
-- См. scripts/recalculate-request-bindings.ts
```

> **Важно:** перед выполнением скрипта — **бэкап таблиц** `imported_requests` и `visit_requests`.

### 7.3. Скрипт пересчёта привязок

Создать скрипт `scripts/recalculate-request-bindings.ts`:

```typescript
// Для каждой не-ИСЖ заявки с serialNumber != null:
// 1. Поискать визит по (addressId, contractId, period, equipmentTypeCode, serialNumber)
// 2. Если найден — создать VisitRequest + обновить visitId
// 3. Логировать результат
```

Скрипт запускается после миграции данных. Результаты логируются для аудита.

### 7.3. Пересчёт привязок после появления serialNumber

После того как для заявки указан serialNumber (через UI или повторный импорт):
- Система автоматически ищет визит с подходящей задачей (по адресу, договору, периоду, serialNumber).
- Если найден — создаётся связь `VisitRequest`.
- Если не найден — заявка остаётся непривязанной до появления подходящего визита.

## 8. Изменения статусов заявок

### 8.1. Текущие статусы (не меняются)

| Статус заявки | Условие |
|---|---|
| Не назначена | Нет связанного визита или визит в статусе `awaiting_assignment` |
| Назначена | Визит в статусе `planned` |
| В работе | Визит в статусе `in_progress` |
| Завершена | Визит в статусе `completed` / `sent` / `corrected_by_tm` |

### 8.2. Удаление задачи из визита

При удалении задачи, к которой привязана заявка:
1. Удалить связь `VisitRequest`.
2. Вернуть заявку на виртуальный визит (`awaiting_assignment`).
3. Статус заявки → «Не назначена».

> **Примечание:** текущая логика уже делает это корректно. Изменение не требуется.

### 8.3. Удаление визита

При удалении визита:
1. Для каждой связанной заявки через `VisitRequest`:
   - Удалить связь `VisitRequest`.
   - Создать виртуальный визит (`awaiting_assignment`).
   - Перенести заявку на виртуальный визит.
   - Статус заявки → «Не назначена».

> **Примечание:** текущая логика уже делает это корректно. Изменение не требуется.

## 13. Примечания

- **Язык интерфейса:** русский.
- **Индексация:** добавить индекс `@@index([serialNumber])` для производительности.
- **Audit:** все изменения привязок логируются в `RequestAssignmentLog`.
- **Бэкап:** перед миграцией данных — обязательный бэкап `imported_requests` и `visit_requests`.
- **Глобальная уникальность serialNumber:** сохраняется правило — serialNumber уникален для ВСЕГО типа оборудования (не только в рамках объекта). См. `@@unique([equipmentTypeCode, serialNumber])` в `ObjectEquipment`.

## 14. Решённые вопросы

| # | Вопрос | Решение |
|---|---|---|
| 1 | Заявки без serialNumber на конкретное оборудование | Импортируются, но НЕ привязываются автоматически. Ждут указания serialNumber. |
| 2 | Формат serialNumber в Excel | Столбец «Серийный №». Любые символы. Trim пробелов по краям. |
| 3 | Дубликаты serialNumber в периоде | Двойная валидация: в файле (ошибка) и в БД (ошибка с указанием существующей заявки). |
| 4 | ИСЖ + конкретное оборудование в одном визите | Разрешено. Визит связан с обеими заявками. |
| 5 | group_climate | Привязка по любой единице в группе, совпадающей по `(equipmentTypeCode, serialNumber)`. |
| 6 | Существующие не-ИСЖ связи | Разорвать. Заявки вернутся в статус «Не назначена». Связи восстановятся при указании serialNumber + пересчёт для заявок с известным SN. |
| 7 | Редактирование serialNumber | Добавить API + UI для ТМ/админа. Алгоритм пересчёта: разорвать → виртуальный визит → поиск нового визита → привязка или «Не назначена». |
| 8 | Автопривязка при импорте заявки | После создания ImportedRequest — поиск существующих визитов с подходящими задачами. Если найден — автоматическая привязка. |
| 9 | contractId = null у визита | Если visit.contractId = null (у ТМ нет договора) — проверка договора пропускается, привязка работает. |
| 10 | Миграция завершённых визитов | Разорвать связи → пересчитать привязки для заявок с известным serialNumber (скрипт recalculate-request-bindings.ts). |
