### 6.5. Справочник сезонов

| Период | Значение |
|--------|----------|
| 01.04 – 31.10 | Лето |
| 01.11 – 31.03 | Зима |

**Алгоритм определения:**
```javascript
function determineSeason(date) {
  const d = new Date(date);
  const month = d.getMonth() + 1; // 1..12
  const day = d.getDate();
  
  // Лето: 1 апреля – 31 октября
  if ((month > 4 && month < 10) || 
      (month === 4 && day >= 1) || 
      (month === 10 && day <= 31)) {
    return 'Лето';
  }
  return 'Зима';
}
```

### 6.6. Привязка «Объект-Оборудование» (object_equipment)

Модуль хранит информацию о том, какое оборудование физически установлено на каждом объекте (адресе). Используется для автозаполнения чек-листа инженера при создании визита.

**Структура таблицы:**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Первичный ключ |
| address_id | UUID | FK на справочник адресов |
| equipment_type_code | VARCHAR(50) | Код вида оборудования |
| room_type_code | VARCHAR(50) | Код типа помещения (**опционально**, может быть NULL) |
| brand | VARCHAR(200) | Марка оборудования (опционально) |
| model | VARCHAR(200) | Модель оборудования (опционально) |
| serial_number | VARCHAR(200) | Серийный номер (опционально) |
| location_description | TEXT | Описание расположения на объекте (опционально) |
| is_outdoor_unit | BOOLEAN | Признак наружного блока кондиционера (false по умолчанию) |
| is_active | BOOLEAN | Активна ли привязка (true по умолчанию) |
| room_confirmed_at | TIMESTAMP | Дата первичного уточнения помещения инженером (опционально) |
| room_confirmed_by | UUID | FK на пользователя, уточнившего помещение (опционально) |
| confirmation_status | VARCHAR(20) | Статус подтверждения: `confirmed` (создано админом/импортом) или `pending` (создано инженером, ждёт подтверждения). По умолчанию `confirmed` |
| created_by | UUID | FK на пользователя, создавшего запись (опционально, для отслеживания) |
| pending_until | TIMESTAMP | Дата истечения TTL для pending-записей. NULL для confirmed |
| created_at | TIMESTAMP | Дата создания |
| updated_at | TIMESTAMP | Дата обновления |

**Уникальные ограничения:**
- `(address_id, equipment_type_code, serial_number)` — одна и та же единица оборудования с серийным номером не может быть привязана к объекту дважды
- `(address_id, equipment_type_code, location_description)` — для записей без серийного номера уникальность обеспечивается по описанию расположения

**Поведение при добавлении оборудования в визит:**
- При нажатии кнопки «+ Добавить оборудование» открывается модальное окно с двумя вкладками: «📍 Уровень помещения», «➕ Добавить новое»
- Оборудование распределяется на основании наличия `room_type_code` в записи `object_equipment`:
  - Записи с указанным `room_type_code` → вкладка «Уровень помещения» (группируются по помещению)
  - Записи без `room_type_code` → доступны в блоке «Перенести из других помещений / уровня объекта» при выборе любого помещения
- Отображаются только активные записи `object_equipment` для данного `address_id`, отфильтрованные по специализации инженера
- Записи, уже добавленные в текущий визит (через поле `object_equipment_id` в таблице `tasks`), **исключаются** из списка — это предотвращает дубликаты
- Список помещений для вкладки «Уровень помещения» загружается через `GET /api/refs/object-equipment/rooms?address_id=...&exclude_visit_id=...`
- Для записей без указанного помещения (`room_type_code = NULL`) отображается метка «⚠️ Помещение не указано»
- При выборе таких записей появляется inline-список для выбора типа помещения из справочника
- Кнопка «Добавить» неактивна, пока для всех отмеченных единиц без помещения не выбран тип
- При добавлении: для оборудования без помещения вызывается `PATCH /api/refs/object-equipment/:id/room` — помещение сохраняется в `object_equipment` с заполнением `room_confirmed_at` и `room_confirmed_by`
- Инженер отмечает галочками нужные позиции и нажимает «Добавить» — для каждой создаётся задача с предзаполненными полями
- Если все записи уже добавлены, соответствующее помещение показывает сообщение «Всё оборудование уже добавлено»
- На вкладке «➕ Добавить новое» инженер может добавить оборудование вручную (не из привязки)
- Новые строки, добавленные вручную, не сохраняются в `object_equipment` автоматически (для этого инженер отмечает чекбокс «Предложить добавить в привязку объекта»)

### 6.7. Предложения оборудования (equipment_proposals)

Модуль хранит предложения инженеров о добавлении нового оборудования в привязку «Объект-Оборудование». Предложения создаются, когда инженер обнаруживает на объекте оборудование, которое ещё не привязано.

**Структура таблицы:**

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Первичный ключ |
| address_id | UUID | FK на справочник адресов |
| equipment_type_code | VARCHAR(50) | Код вида оборудования |
| room_type_code | VARCHAR(50) | Код типа помещения (опционально) |
| brand | VARCHAR(100) | Марка оборудования |
| model | VARCHAR(100) | Модель оборудования |
| serial_number | VARCHAR(100) | Серийный номер |
| location_description | TEXT | Описание расположения |
| proposed_by_id | UUID | FK на пользователя (инженер), предложившего оборудование |
| status | VARCHAR(20) | Статус предложения: `pending`, `approved`, `rejected`, `expired` |
| request_type | VARCHAR(20) | Тип запроса: `new_equipment` (новое оборудование), `room_change` (перенос в другое помещение), `brand_change` (смена бренда/модели). По умолчанию `new_equipment` |
| old_room_type_code | VARCHAR(50) | Код помещения, откуда переносится оборудование (для `room_change`) |
| rejection_reason | TEXT | Причина отклонения администратором (опционально) |
| pending_until | TIMESTAMP | Дата автоматического истечения (TTL, 30 дней). NULL для рассмотренных записей |
| object_equipment_id | UUID | FK на `object_equipment` (для переноса — ссылка на переносимую запись) |
| reviewed_by_id | UUID | FK на пользователя (администратор), рассмотревшего предложение (опционально) |
| reviewed_at | TIMESTAMP | Дата рассмотрения |
| created_at | TIMESTAMP | Дата создания предложения |
| updated_at | TIMESTAMP | Дата обновления |

**Индексы:**
- `(request_type)` — фильтрация по типу запроса
- `(pending_until)` — cron-обработка истёкших
- `(object_equipment_id, status)` WHERE `status = 'pending'` — частичный индекс для защиты от конфликтующих переносов

**Жизненный цикл:**
1. Инженер добавляет оборудование в визит и отмечает чекбокс «Предложить добавить в привязку объекта» → создаётся запись со статусом `pending`
2. Администратор видит предложение в списке `pending`-предложений
3. Администратор утверждает → статус меняется на `approved`, запись автоматически копируется в `object_equipment` с `is_active = true`. Данные `brand`, `model`, `serialNumber` из proposal синхронизируются в задачу визита (если администратор редактировал эти поля при модерации — в задачу попадают изменённые значения)
4. Администратор отклоняет → статус меняется на `rejected`, указывается причина в `review_comment`

### 6.8. Маппинг специализаций

Каждый инженер имеет одну или несколько специализаций, определяющих набор обслуживаемого оборудования.

| Специализация | Поле в БД | Коды оборудования | Описание |
|:-------------:|-----------|-------------------|----------|
| **ВиК** | `specialization_vik` | ~~vent~~ (деактивирован), teplozavesa, pritochnaya, pritochno-vytyzhnaya, vytyzhnaya, vrv_vn, vrv_nar, mssvn, mssnar, splitvn, splitnar, cond_mobile | Вентиляция и кондиционирование (12 активных + 1 деактивированный) |
| **ИСЖ** | `specialization_iszh` | rsch, schetchik_gvs, schetchik_hvs, schetchik_electroshc, seti_vodosnab, teplovye_seti, itp, boiler_gas, boiler_liquid, boiler_solid, boiler_elec, meter_gas, sololift, barrier_roller, door_auto, coffee, purifier, cooler, aquarium, bubble_panel | Инженерные сети и здания (20 типов) |
| **ГПМ** | `specialization_gpm` | lift_pass, lift_cargo, lift_cargo_pass, lift_invalid | Грузоподъёмные механизмы (4 типа) |
| **ДГУ** | `specialization_dgu` | dgu, mkgu | Дизель-генераторные установки (2 типа) |
| **ИБП** | `specialization_ibp` | ibp | Источники бесперебойного питания (1 тип) |

**Правила:**
- Значения по умолчанию при создании инженера: `specialization_vik = false`, `specialization_iszh = true`
- Инженер может изменить свою специализацию через ЛК (страница `/profile`)
- ТМ/Администратор могут изменить специализацию подчинённого инженера
- Если ни одна специализация не выбрана — показывается блокирующий экран (SpecializationGate)
- Задачи в визите фильтруются по специализации инженера
- Оборудование объекта фильтруется по специализации при автозаполнении
- Специализация инженера отображается в PDF-отчёте

### 6.11. Голосовой ввод (Speech-to-Text)

Функция голосового ввода текста в поле «Дополнительные рекомендации» на странице параметров задачи. Использует Web Speech API (нативный браузерный API, без сторонних сервисов).

**Реализация:**
- Кнопка микрофона (40×40px) размещена справа от лейбла «Дополнительные рекомендации»
- Механика: клик — начало записи, повторный клик — остановка
- Распознанный текст добавляется в конец существующего текста через пробел
- Язык распознавания: `ru-RU`
- Непрерывный режим (`continuous = true`) для длинных рекомендаций

**Состояния кнопки:**
- **Ожидание** — серый микрофон на светлой подложке
- **Запись** — красный микрофон с пульсацией и обводкой
- **Ошибка** — красный перечёркнутый микрофон с тултипом причины
- **Недоступно** — полупрозрачный микрофон (офлайн-режим)

**Офлайн-режим:** Web Speech API требует интернет-соединение. При отсутствии сети кнопка становится неактивной с тултипом.

**Совместимость:** Chrome/Edge (Android, Desktop), Safari 14.5+ (iOS).

**Применение:** Функция доступна на двух страницах:
- **TaskPage** — страница индивидуальной задачи
- **GroupTaskPage** — страница групповой задачи (климатическое оборудование)

**Логика вставки текста:**
- Текст вставляется в позицию курсора или в конец существующего текста (если курсор не установлен)
- Если в поле уже есть текст, надиктованный текст добавляется через пробел
- Промежуточные результаты (`interim results`) отображаются курсивом; финальный результат заменяет курсивный текст обычным
- Автосохранение приостанавливается на время записи и возобновляется после остановки

**Таймаут тишины:** Автоматическая остановка записи через 5 секунд тишины (fallback, если инженер забыл остановить вручную).

**Безопасность и приватность:**
- Данные с микрофона не отправляются на бэкенд приложения — они обрабатываются браузером и сервисами ОС (Google/Apple), в приложение возвращается только итоговый текст
- При первом использовании отображается предупреждение: *«Голосовой ввод использует сервисы распознавания речи вашего браузера (Google/Apple). Не диктуйте конфиденциальную информацию.»* (флаг в `localStorage`)

**User Stories:**

| ID | User Story |
|---|---|
| US-VOICE-01 | **Как** инженер, *я хочу* нажать на иконку микрофона и надиктовать текст, *чтобы* быстро заполнить поле без клавиатуры |
| US-VOICE-02 | **Как** инженер, *я хочу* видеть текст в реальном времени по мере диктовки, *чтобы* контролировать корректность распознавания |
| US-VOICE-03 | **Как** инженер, *я хочу*, чтобы при отсутствии интернета иконка была неактивна, *чтобы* не тратить время на недоступную функцию |
| US-VOICE-04 | **Как** инженер, *я хочу*, чтобы надиктованный текст добавлялся к уже введённому, *чтобы* комбинировать способы ввода |
| US-VOICE-05 | **Как** инженер, *я хочу* вручную остановить запись повторным нажатием, *чтобы* работать в шумных помещениях |
| US-VOICE-06 | **Как** инженер, *я хочу* чтобы функция работала на TaskPage и GroupTaskPage |

**Критерии приёмки:**

| № | Критерий |

### 6.13. Модерация привязки оборудования к помещениям

Механизм гибкого управления привязкой оборудования к помещениям с модерацией и TTL.

**Концепция:** Инженер может переносить оборудование между помещениями и добавлять новое оборудование прямо из визита. Изменения вступают в силу немедленно, но требуют подтверждения администратором в течение 30 дней (TTL).

**Статусы записей:**

| Статус | Описание | TTL |
|--------|----------|-----|
| `confirmed` | Подтверждено (создано админом/импортом или подтверждено после модерации) | Бессрочно |
| `pending` | Добавлено инженером, ждёт подтверждения | 30 дней |
| `rejected` | Отклонено администратором или отменено инженером | — |
| `expired` | Не подтверждено в срок, деактивировано cron-задачей | — |

**Сценарии:**

**А. Перенос оборудования между помещениями:**
1. Инженер выбирает помещение в модалке добавления оборудования
2. Видит секцию «Оборудование из других помещений» с кнопкой «Перенести»
3. При нажатии «Перенести» — создаётся `equipment_proposal` с `request_type = 'room_change'`, `object_equipment.roomTypeCode` обновляется немедленно
4. Администратор подтверждает или отклоняет (при отклонении — откат `roomTypeCode`)

**Б. Добавление нового оборудования:**
1. Инженер заполняет форму (вид, помещение, изготовитель, модель, SN)
2. Может добавить нового изготовителя или модель (создаются со статусом `pending`)
3. Создаётся `equipment_proposal` со статусом `pending` и `pending_until = NOW() + 30 дней`
4. Администратор подтверждает (создаётся `object_equipment`) или отклоняет

**В. Модерация (администратор):**
- Дашборд с фильтрами: тип запроса, объект, инженер, истекающие скоро
- Массовые действия: подтвердить/отклонить несколько записей
- Отклонение с указанием причины (опционально)
- **Отображение серийного номера:** серийный номер отображается для всех видов оборудования; если номер отсутствует — показывается текст "не указан"
- **Редактирование серийного номера:** администратор может отредактировать серийный номер для любого proposal (кнопка ✏️ рядом с номером, inline-редактирование); при изменении автоматически обновляется связанный `object_equipment`
- **Отображение изготовителя и модели:** поля «Изготовитель» (brand) и «Модель» (model) отображаются всегда (ранее скрывались при отсутствии данных). Администратор может отредактировать эти поля inline (кнопка ✏️ рядом со значением, аналогично серийному номеру); при сохранении обновляется связанный `object_equipment` и задача визита
- **Просмотр фото приборов учёта:** для приборов учёта (счётчики ХВС, ГВС, э/э, газа) доступна кнопка "Фото прибора учёта", открывающая модальное окно с превью и возможностью скачивания фото из задач визита; если фото отсутствуют — показывается соответствующее сообщение

**Г. Автоматическое удаление (cron, ежедневно в 03:00):**
- Помечает истёкшие proposals как `expired`
- Откатывает `room_change` (восстанавливает `roomTypeCode`)
- Деактивирует `new_equipment` (`is_active = FALSE`)
- Создаёт уведомления инженерам (без дублей)

**Д. Уведомления:**
- Колокольчик в header (badge с количеством непрочитанных)
- Типы: `proposal_created`, `proposal_approved`, `proposal_rejected`, `proposal_expiring_soon`, `proposal_expired`
- Получатели: администраторы + ТМ привязанных объектов

**Е. Сводная таблица новых и расширенных API-эндпоинтов:**

| Метод | Путь | Статус | Описание |
|-------|------|--------|----------|
| POST | `/api/proposals/room-change` | Новый | Предложение переноса оборудования между помещениями |
| PATCH | `/api/proposals/:id` | Новый | Редактирование своего pending-proposal (инженер) |
| DELETE | `/api/proposals/:id` | Новый | Отмена своего pending-proposal (soft: статус → rejected) |
| GET | `/api/proposals/my` | Новый | Список своих proposals (инженер) |
| PUT | `/api/proposals/admin/batch` | Новый | Массовое одобрение/отклонение (админ) |
| GET | `/api/refs/object-equipment/other-rooms` | Новый | Оборудование из других помещений объекта (с фильтрацией по специализации инженера) |
| POST | `/api/internal/cron/process-expired-proposals` | Новый | Cron-обработка истёкших proposals (ежедневно 03:00) |
| GET | `/api/proposals/admin` | Расширен | + фильтры `request_type`, `address_id`, `engineer_id`, `expiring_soon` |
| PUT | `/api/proposals/admin/:id/approve` | Расширен | + логика для `room_change` и `new_equipment` |
| PUT | `/api/proposals/admin/:id/reject` | Расширен | + поле `reason`, откат `room_change` |
| POST | `/api/proposals` | Расширен | + поля `newManufacturer`, `newModel`, `pending_until`, `taskId` (связь proposal с задачей для точного поиска фото) |
| PATCH | `/api/proposals/:id` | Расширен | Администратор может редактировать любые proposals (не только свои); при изменении `serialNumber` обновляется `object_equipment` |
| GET | `/api/proposals/:id/meter-photos` | Новый/Расширен | Получение фото прибора учёта: поиск по `taskId` → `objectEquipmentId` → fallback по адресу (только для админа) |
| POST | `/api/photos/check-duplicate` | Новый | Проверка дубликата фото по SHA-256 хешу — возвращает информацию о существующем фото (визит, адрес, инженер, оборудование) |

**Жизненный цикл записи `object_equipment` при переносе:**
1. При переносе: `roomTypeCode` обновляется немедленно, `confirmation_status = 'pending'`, `pending_until = NOW() + 30 дней`
2. При одобрении: `confirmation_status = 'confirmed'`, `pending_until = NULL`
3. При отклонении: `roomTypeCode` откатывается к `old_room_type_code`, `confirmation_status = 'confirmed'`
4. При истечении (cron): аналогично отклонению — откат `roomTypeCode`

**Файлы реализации:**
- `server/prisma/schema.prisma` — расширение `EquipmentProposal`, `ObjectEquipment`, модель `Notification`
- `server/src/routes/proposals.ts` — API модерации (9 эндпоинтов)
- `server/src/routes/notifications.ts` — API уведомлений
- `server/src/routes/refs.ts` — `GET /object-equipment/other-rooms`
- `server/src/services/cron.ts` — cron-задача обработки TTL
- `client/src/pages/admin/AdminProposals.tsx` — дашборд модерации
- `client/src/components/NotificationBell.tsx` — компонент уведомлений
- `client/src/pages/VisitPage.tsx` — секция переноса оборудования

### 6.14. Адаптивная вёрстка и мобильная оптимизация

Адаптация интерфейсов всех ролей (Инженер, ТМ, Администратор) под смартфоны, планшеты и ПК. Обеспечивает отсутствие горизонтальной прокрутки на экранах от 320px до 1920px+.

#### 6.14.1. Система breakpoints

| Тип устройства | Ширина экрана | Основной интерфейс | Навигация |
|---|---|---|---|
| **Смартфон (Mobile)** | < 768 px | Карточный вид, одноколоночная вёрстка | Нижняя панель (Bottom Navigation) |
| **Планшет (Tablet)** | 768–991 px | Гибридный вид (таблицы/карточки), двухколоночная вёрстка | Боковая панель (Sidebar) |
| **ПК (Desktop)** | ≥ 992 px | Таблицы, многоколоночные дашборды | Боковая панель (Sidebar) |

Определение устройства: `Grid.useBreakpoint()` из Ant Design (JS) и CSS media queries (стили).

#### 6.14.2. PWA-адаптация

- **Viewport meta:** `viewport-fit=cover` для Safe Area на iPhone, `user-scalable=no` для предотвращения случайного масштабирования
- **Манифест:** `display: standalone`, `orientation: portrait`
- **Safe Area CSS:** отступы `env(safe-area-inset-top)` / `env(safe-area-inset-bottom)` для фиксированных элементов (Header, Bottom Navigation)
- **Service Worker:** CSS-файлы кэшируются через Workbox precaching; обновление — через `skipWaiting` + `clientsClaim`

#### 6.14.3. Оптимизация интерфейса Инженера (Mobile First)

**Страница визита (VisitPage):** на мобильных таблица задач трансформируется в список карточек с группировкой по комнатам. Каждая карточка содержит: название типа оборудования, адрес + модель, иконку фото-прогресса, статус-иконку, кнопку overflow-меню (⋮).

**TaskPage:** форма адаптируется вертикально (label над полем), поля группируются в сворачиваемые секции (Accordion). На мобильных `<Select>` из antd заменяется на `Picker` из antd-mobile (Bottom Sheet).

**GroupTaskPage:** на мобильных — вкладки (Tabs) для переключения между единицами оборудования вместо таблицы. Общие поля — вверху страницы.

**Bottom Navigation** (только Инженер, < 768px): 4 вкладки — Визиты, Заявки, Отчёты, Профиль. Высота 56px + safe area. При фокусе на поле ввода — скрывается (определение через `visualViewport` API + iOS fallback через `resize`).

**Фотофиксация:** кнопки «Камера» и «Галерея» располагаются вертикально на всю ширину. Превью — сетка 2×2. iOS PWA fallback: диалог выбора вместо `capture="environment"`.

#### 6.14.4. Оптимизация интерфейса ТМ

- Дашборд и списки визитов: на мобильных — карточки вместо таблиц, фильтры выносятся в Drawer (открывается по иконке воронки)
- Назначение инженера: full-screen modal на смартфоне
- Цветные бейджи специализаций: ВиК (синий), ИСЖ (зелёный), ГПМ (оранжевый), ДГУ (фиолетовый), ИБП (красный)

#### 6.14.5. Оптимизация интерфейса Администратора

- Таблицы справочников: на смартфонах трансформируются в аккордеоны/карточки
- Массовый импорт: на тач-устройствах скрыт Drag-and-Drop, только кнопка «Выбрать файл»

#### 6.14.6. Технические требования

- **Touch Targets:** минимальный размер кликабельных элементов — 40×40 px на мобильных
- **Типографика:** масштабирование через Ant Design токены (`fontSize`, `fontSizeLG`, `fontSizeSM`), не CSS `clamp()`
- **Отступы:** padding карточек на мобильных — 16px (вместо 24px на десктопе)
- **Клавиатура:** при фокусе на input/textarea Bottom Navigation скрывается (`visualViewport` API)
- **inputmode:** `decimal` для температур, `numeric` для кодов, `tel` для телефонов, `email` для email
- **antd-mobile:** загружается лениво (dynamic import), чтобы не увеличивать бандл для десктопа
- **Accessibility:** все иконки-статусы с `aria-label` + сокращённый текст; контрастность ≥ 4.5:1; keyboard navigation (Tab/Enter/Escape); focus trap для модальных окон

#### 6.14.7. Критерии приёмки

### 6.15. Система уведомлений (Центр уведомлений)

Модуль внутренних уведомлений для информирования пользователей о событиях системы: предложения по оборудованию, назначение заявок, системные релизы.

#### 6.15.1. Типы уведомлений

| Тип | Код | Иконка | Описание |
|-----|-----|:------:|----------|
| Предложение создано | `proposal_created` | 📋 | Инженер предложил оборудование |
| Предложение одобрено | `proposal_approved` | ✅ | Админ утвердил предложение |
| Предложение отклонено | `proposal_rejected` | ❌ | Админ отклонил предложение |
| Предложение скоро истекает | `proposal_expiring_soon` | ⏰ | До истечения TTL осталось 3 дня |
| Предложение истекло | `proposal_expired` | ⌛ | TTL истёк, запись деактивирована |
| Оборудование удалено | `equipment_removed` | 🗑️ | Оборудование деактивировано на объекте |
| Заявка назначена | `request_assigned` | 📌 | Инженер назначен на заявку |
| Заявка снята | `request_unassigned` | 📌 | Инженер снят с заявки |
| Инженер отказался | `request_declined` | 📌 | Инженер отказался от заявки |
| Заявки импортированы | `request_imported` | 📌 | Новые заявки загружены из Excel |
| Системный релиз | `system_release` | 🚀 | Новая версия приложения (от CI/CD или админа) |

#### 6.15.2. Структура таблицы `notifications`

| Поле | Тип | Описание |
|------|-----|----------|
| id | UUID | Первичный ключ |
| user_id | UUID | FK на пользователя |
| type | VARCHAR(30) | Тип уведомления (см. таблицу выше) |
| title | VARCHAR(200) | Заголовок |
| message | TEXT | Текст уведомления |
| entity_type | VARCHAR(30) | Тип связанной сущности (`equipment_proposal`, `object_equipment`, `visit`, `system_release`) |
| entity_id | UUID | ID связанной сущности (для deep links) |
| is_read | BOOLEAN | Прочитано (false по умолчанию) |
| is_deleted | BOOLEAN | Мягкое удаление / очистка (false по умолчанию) |
| created_at | TIMESTAMP | Дата создания |

**Индексы:** `(user_id, is_deleted, is_read)` — для быстрого запроса активных непрочитанных.

#### 6.15.3. Функция «Очистить всё»

Мягкое удаление уведомлений: при нажатии «Очистить» все уведомления пользователя помечаются `is_deleted = true, is_read = true`. Требуется подтверждение в модальном окне.

**API:** `POST /api/notifications/clear-all` — возвращает `{ cleared: N }`.

#### 6.15.4. Webhook для CI/CD (системные уведомления о релизах)

**Эндпоинт:** `POST /api/system/webhook/deploy`
**Авторизация:** HMAC-подпись (заголовок `X-Webhook-Signature: sha256=<HMAC>`, `X-Webhook-Timestamp`).
**Защита:** проверка timestamp (±5 минут), защита от дубликатов по `version` (таблица `system_releases`), rate limiting (10 запросов / 15 минут).

**Логика:** при успешном деплое webhook создаёт уведомления типа `system_release` для всех активных пользователей. Переменная окружения: `WEBHOOK_SECRET`.

#### 6.15.5. Ручное создание системных уведомлений (админ-панель)

**Эндпоинт:** `POST /api/admin/system-notifications` (только `admin`).
**Интерфейс:** раздел «Системные уведомления» в админ-панели с формой создания и историей релизов.

#### 6.15.6. API уведомлений

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/notifications` | Список уведомлений (пагинация, фильтр `unread_only`) |
| PATCH | `/api/notifications/:id/read` | Пометить одно как прочитанное |
| PATCH | `/api/notifications/read-all` | Прочитать все |
| POST | `/api/notifications/clear-all` | Очистить все (soft delete) |
| POST | `/api/system/webhook/deploy` | Webhook CI/CD (HMAC) |
| POST | `/api/admin/system-notifications` | Ручное создание (админ) |

#### 6.15.7. Интерфейс Центра уведомлений

**Десктоп:** dropdown по клику на колокольчик 🔔 в шапке. Непрочитанные — жирный шрифт, цветная полоска слева (синяя — рабочие, зелёная — системные). Системные уведомления — тег `NEW FEATURE`. Кнопки «Прочитать всё» и «Очистить» внизу dropdown.

**Мобильная версия (≤768px):** fullscreen modal вместо dropdown. Кнопки расположены вертикально. Сокращённые подписи.

**Deep links:** клик по уведомлению переводит на соответствующий экран:
- `proposal_*` → `/admin/proposals`
- `request_assigned/unassigned` → `/my-requests`
- `request_declined` → `/requests`
- `system_release` → `/profile`

**Офлайн-режим:** список уведомлений кэшируется в IndexedDB (Dexie). Действия (прочитать, очистить) ставятся в очередь синхронизации.

#### 6.15.8. User Stories

| ID | User Story |
|---|---|
| US-NOTIF-01 | **Как** пользователь, *я хочу* получать уведомление о новом релизе сразу после обновления, *чтобы* знать о новых возможностях |
| US-NOTIF-02 | **Как** DevOps, *я хочу*, чтобы уведомления о релизе создавались автоматически через webhook, *чтобы* не оповещать вручную |
| US-NOTIF-03 | **Как** администратор, *я хочу* вручную создать системное уведомление (fallback если webhook не настроен) |
| US-NOTIF-04 | **Как** пользователь, *я хочу* очистить список уведомлений, *чтобы* убрать старые записи |
| US-NOTIF-05 | **Как** пользователь, *я хочу* нажимать на уведомление и переходить на соответствующий экран (deep link) |
| US-NOTIF-06 | **Как** пользователь, *я хочу* видеть Центр уведомлений на мобильном устройстве |
