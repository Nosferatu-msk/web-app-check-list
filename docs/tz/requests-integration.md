## 11. ИНТЕГРАЦИЯ ВНЕШНИХ ЗАЯВОК

### 11.1. Назначение модуля

Модуль обеспечивает импорт перечня заявок из внешнего сервиса (формат Excel) и автоматическое создание визитов на основе этих заявок. Связывает систему управления заявками заказчика с полевым исполнением работ инженерами через связь многие-ко-многим (таблица `visit_requests`): одна заявка может быть связана с несколькими визитами разных инженеров, один визит может быть связан с несколькими заявками.

Подробное ТЗ модуля: см. файл `ТЗ-интеграция-заявок.md`.

### 11.2. Основные возможности

- **Импорт Excel** — загрузка файла с заявками (№ заявки, статус, вид оборудования, код объекта, адрес)
- **Предварительная валидация** — перед импортом выполняется проверка файла с отображением списка ошибок (номер строки, № заявки, описание ошибки). Пользователь может отменить импорт или продолжить (ошибочные строки будут пропущены)
- **Автоматический маппинг** — сопоставление кода объекта и адреса со справочником адресов
- **Группировка по объекту** — несколько заявок на один объект → один визит с несколькими задачами
- **Назначение инженеров** — с валидацией специализации по виду оборудования
- **Множественное назначение** — ТМ может назначить нескольких инженеров на любую заявку
- **Статус исполнения** — отображается вместо статуса импорта: Не назначена / Назначена / В работе / Завершена. Для заявок ИСЖ объекта статус определяется агрегированно по всем связанным визитам (см. раздел 11.8.6)
- **Сортировка** — по клику на заголовки колонок: № заявки, Статус, Код, Адрес
- **Фильтрация** — по статусу исполнения и по инженеру (с поиском)
- **Периметр ТМ** — ТМ видит только заявки по своим адресам, назначенные на своих инженеров (или неназначенные)
- **Единая ширина** — все страницы ТМ/Админа имеют максимальную ширину 1400px
- **Отказ инженера** — с указанием причины и уведомлением ТМ
- **Автопривязка визитов к заявкам** — при создании визита инженером система автоматически связывает визит с назначенными заявками через таблицу `visit_requests` (связь многие-ко-многим)
- **Отчёт по номерам заявок** — формирование сводного отчёта по списку внешних номеров (данные собираются из всех визитов, связанных с заявкой)

### 11.3. Роли в модуле заявок

| Роль | Права |
|------|-------|
| **Администратор** | Импорт, просмотр всех заявок, назначение/снятие инженеров, отчёты |
| **ТМ** | Импорт, просмотр заявок своей территории, назначение инженеров своей группы, отчёты |
| **Инженер** | Просмотр назначенных заявок, уведомления, отказ от заявки |

### 11.4. Новые сущности данных

| Сущность | Описание |
|----------|----------|
| `imported_requests` | Импортированные заявки с маппингом на объекты и визиты |
| `visit_engineers` | Связь визит-инженер (множественное назначение) |
| `visit_requests` | Связь многие-ко-многим между визитами и заявками (visit_id ↔ request_id) |
| `request_assignment_log` | История назначений/снятий/отказов |

### 11.5. Новый статус визита

`awaiting_assignment` — визит создан из заявок, но инженер ещё не назначен.

### 11.8. Связь визитов и заявок (многие-ко-многим)

#### 11.8.1. Бизнес-правило заявок ИСЖ объекта

Заявка ИСЖ объекта подразумевает выполнение ТО **всего оборудования объекта**. Поскольку на объекте могут работать несколько инженеров с разной специализацией, **каждый инженер создаёт свой визит** для своего оборудования. Все визиты, созданные для одного объекта по одной заявке, связываются с этой заявкой через таблицу `visit_requests`.

Таким образом, одна заявка может быть связана с несколькими визитами (от разных инженеров), и один визит может быть связан с несколькими заявками (если на объекте несколько заявок).

#### 11.8.2. Таблица `visit_requests`

Промежуточная таблица для связи многие-ко-многим:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Первичный ключ |
| `visit_id` | UUID | Ссылка на визит (FK → visits) |
| `request_id` | UUID | Ссылка на заявку (FK → imported_requests) |
| `created_at` | TIMESTAMP | Дата создания связи |
| `created_by` | UUID | Кто создал связь (автоматически или вручную) |

Уникальный составной индекс: `(visit_id, request_id)`.

#### 11.8.3. Автопривязка заявок к визитам

Система автоматически привязывает заявки к визитам на трёх этапах: при создании визита, при завершении визита и при создании задачи.

**А. Автопривязка при создании визита (все роли):**
Когда визит создаётся на объект (независимо от роли — инженер, ТМ, администратор), система **автоматически** (без подтверждения пользователя) привязывает заявки типа «ИСЖ объекта» для данного объекта.

Логика:
1. При создании визита определяется адрес объекта
2. Ищутся **все** заявки (`imported_requests`) для данного объекта по `object_code` — заявки типа «ИСЖ объекта»
3. Фильтр по периоду действия заявки: `startDate <= visitDate <= deadline`
4. Для каждой найденной заявки создаётся запись `visit_requests`
5. Инженер добавляется в `visit_engineers` на свой визит
6. Если заявок не найдено — визит создаётся без привязки к заявкам (штатный сценарий для прямых визитов)

**Для ИСЖ объекта:** одна заявка → много визитов (разные инженеры с разными специализациями), без фильтра по статусу виртуального визита.

**Б. Автопривязка при завершении визита:**
При завершении визита (`POST /api/visits/:id/complete`) система дополнительно привязывает заявки на **конкретное оборудование** по типам задач визита.

Логика:
1. Определяются типы оборудования задач визита
2. Ищутся заявки на конкретное оборудование (не «ИСЖ объекта») с совпадающими типами
3. Фильтр по периоду: `startDate <= visitDate <= deadline`
4. **Защита от дубликатов:** если несколько заявок с одинаковым адресом и периодом — привязка только к первой
5. **Ограничение 1:1:** для конкретного оборудования одна заявка привязывается только к одному визиту (если заявка уже привязана к другому визиту — пропускается)

**В. Автопривязка при создании задачи:**
При создании задачи в визите система ищет заявки на конкретное оборудование (по `equipment_type_code`) для данного объекта и автоматически привязывает через `visit_requests`.

**Защита от дубликатов (общая):** если несколько заявок совпадают по адресу и периоду — привязка выполняется только к первой найденной заявке.

#### 11.8.4. Отображение номеров заявок в списке визитов

В списке визитов (для всех ролей) для каждого визита отображаются номера связанных заявок:
- Отображаются **первые 2 номера** заявок через запятую
- Если заявок больше двух — добавляется счётчик «+N» (где N — количество оставшихся)
- Пример: `ИСЖ-001, ИСЖ-002` или `ИСЖ-001, ИСЖ-002 +3`
- Если заявок нет — колонка пуста

#### 11.8.5. Формирование отчётов для заявок ИСЖ объекта

При формировании отчёта по номерам заявок ИСЖ объекта система собирает данные из **всех визитов**, связанных с данной заявкой через `visit_requests`. Это обеспечивает полный отчёт по объекту, даже если работы выполняли несколько инженеров.

Логика формирования:
1. По номерам заявок находятся записи `imported_requests`
2. Через `visit_requests` определяются все связанные визиты
3. Из каждого визита собираются задачи, фото и параметры
4. Данные агрегируются в единый отчёт по объекту

#### 11.8.6. Статусы заявок ИСЖ объекта

Для заявок типа «ИСЖ объекта» (`equipmentType.code = 'iszh_object'`) статус исполнения определяется **агрегированно** по всем связанным визитам через таблицу `visit_requests`, поскольку такие заявки предполагают визиты от нескольких инженеров с разными специализациями (ВИК и ИСЖ).

**Логика определения статуса:**

| Условие | Статус |
|---------|--------|
| Нет связанных визитов через `visit_requests` | **Не назначена** |
| Есть связанные визиты, но все в статусе `not_started` или `planned` | **Назначена** |
| Есть хотя бы один визит в статусе `in_progress`, ИЛИ частичное покрытие специализаций (не все завершены) | **В работе** |
| Все требуемые специализации (ВИК и ИСЖ) покрыты визитами в статусе `completed`/`sent`/`corrected_by_tm` | **Завершена** |

**Примеры:**
- Инженер ВИК создал визит (completed), инженер ИСЖ ещё не назначен → **В работе** (частичное покрытие)
- Оба инженера создали визиты, оба в статусе planned → **Назначена**
- Оба инженера завершили визиты → **Завершена**
- Один инженер в процессе (in_progress) → **В работе**

Для обычных заявок (не ИСЖ объекта) статус определяется по одному связанному визиту без агрегации.

#### 11.8.7. Уточнённые бизнес-правила связывания визитов и заявок

**А. Связь заявки с визитом определяется наличием задачи:**
Заявка считается связанной с визитом, если в визите существует задача (`tasks`) с тем же типом оборудования (`equipmentTypeId`), что и у заявки. Это является «источником истины» для определения статуса заявки.

**Б. Статус «Завершён» для не-ИСЖ заявок:**
Для заявок типа, отличного от «ИСЖ объекта», статус «Завершён» присваивается **только** при одновременном выполнении условий:
1. Заявка связана с визитом через `visit_requests`
2. В связанном визите существует задача (`tasks`) с типом оборудования, совпадающим с типом оборудования заявки (`equipmentTypeId`)
3. Визит находится в завершённом статусе (`completed` / `sent` / `corrected_by_tm`)

Если задача по типу оборудования заявки отсутствует в визите (удалена инженером или не была создана) — статус заявки возвращается в **«Не назначена»**, даже если визит завершён.

**В. ИСЖ объекта — связь с 2+ визитами:**
Заявка типа «ИСЖ объекта» может быть связана с несколькими визитами (разные инженеры/специализации). Для таких заявок статус определяется агрегированно (см. таблицу в п. 11.8.6). При этом для определения «Завершена» требуется, чтобы **каждый** связанный визит содержал задачи по типу оборудования заявки и находился в завершённом статусе.

**Г. Расширенная проверка дубликатов визитов:**
При создании визита инженером система проверяет наличие существующего визита на тот же адрес не только по `userId` визита, но и по таблице `visitEngineers`. Это предотвращает создание дубликатов, когда ТМ заранее назначил инженера через `visitEngineers`, а инженер затем создаёт визит самостоятельно.

**Д. Раздельные виртуальные визиты при удалении:**
При удалении визита, связанного с заявками, система группирует заявки по типу оборудования (`equipmentTypeId`). Для каждой группы типов оборудования создаётся **отдельный** виртуальный визит (soft-deleted), связанный только с заявками соответствующего типа. Это предотвращает смешивание типов оборудования в одном виртуальном визите и обеспечивает корректную работу статусов заявок.
