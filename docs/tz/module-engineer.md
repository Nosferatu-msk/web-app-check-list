### 4.1. Модуль «Инженер»

#### 4.1.1. Создание визита

**US-1.1 — Выбор адреса из справочника**  
*Как* инженер, *я хочу* выбирать адрес объекта из справочника с функцией поиска/автодополнения, *чтобы* избежать ошибок ввода и ускорить начало работы.

**US-1.2 — Автозаполнение даты и времени**  
*Как* инженер, *я хочу*, чтобы поля «Дата начала» и «Время начала» заполнялись автоматически текущими значениями, *чтобы* не вводить их вручную.

**US-1.3 — Автоопределение сезона**  
*Как* инженер, *я хочу*, чтобы поле «Сезон» автоматически определялось по дате визита:
- 01.04–31.10 → «Лето»
- 01.11–31.03 → «Зима»

*чтобы* исключить расхождения в отчетах.  
Поле доступно для ручного редактирования. При изменении даты — пересчет с подтверждением.

**US-1.4 — Добавление оборудования через модальное окно**
*Как* инженер, *я хочу* нажимать «+ Добавить оборудование» и выбирать нужные единицы оборудования из модального окна с тремя вкладками («Уровень помещения», «Уровень объекта» и «Добавить новое»), *чтобы* формировать состав визита пошагово, без дубликатов и визуального шума.
При первом нажатии кнопки для несохранённого визита система автоматически сохраняет визит как черновик, затем открывает модальное окно.

Вкладки модального окна:
- **«Уровень помещения»** — для оборудования с привязкой к помещению (климатическое оборудование: СС, МСС, VRV, тепловые завесы, приточные и приточно-вытяжные установки и т.д.). Инженер выбирает помещение из списка, затем видит всё оборудование в этом помещении (все чекбоксы отмечены по умолчанию) и нажимает «Добавить».
- **«Уровень объекта»** — для оборудования без привязки к помещению (сети, тепловые сети, приборы учёта, РЩ без помещения). Список с чекбоксами, все отмечены по умолчанию.
- **«Добавить новое»** — ручной ввод оборудования, которого нет в привязке объекта.

Уровень привязки определяется по наличию `roomTypeCode` в записи `object_equipment`, а не по коду типа оборудования.

**Фотофиксация (мобильные устройства):**
На странице фото задачи для каждого снимка (до/после) доступны две отдельные кнопки:
- **«Камера»** (иконка 📷) — на мобильном устройстве открывает камеру напрямую через атрибут `capture="environment"` на `<input type="file">`. На десктопе работает как обычный выбор файла.
- **«Галерея»** (иконка 🖼) — открывает галерею/файловый менеджер без атрибута `capture`, позволяя выбрать уже существующее изображение.

**Создание нового помещения inline:**
Вкладка «Добавить новое» позволяет создать новое помещение прямо в модальном окне добавления оборудования (без перехода в справочник). При создании нового помещения отображается всё оборудование объекта (из всех помещений и с уровня объекта) с кнопкой «Перенести» для переноса выбранного оборудования в созданное помещение.

**US-1.5 — Визуальный статус задач**  
*Как* инженер, *я хочу* видеть в чек-листе для каждой задачи:
- Статус: «Не начато» / «В работе» / «Выполнено»
- Прогресс фото: ⬜ / 📷 1/2 / 📷 2/2

*чтобы* понимать, что уже сделано.

**US-1.6 — Возврат к незавершенной задаче**
*Как* инженер, *я хочу* иметь возможность кликнуть на любую незавершенную задачу и продолжить её заполнение, *чтобы* не начинать работу заново.

**US-1.7 — Работа офлайн**
*Как* инженер, *я хочу* создавать визиты и загружать фото без подключения к интернету, *чтобы* работать в подвалах, серверных и других зонах без связи.
Данные сохраняются локально и автоматически синхронизируются при восстановлении соединения.

**US-1.8 — Выбор оборудования из привязки объекта через модальное окно (группировка по уровням)**
*Как* инженер, *я хочу*, чтобы при нажатии «+ Добавить оборудование» оборудование из привязки объекта (`object_equipment`) отображалось сгруппированным по уровню привязки — с помещениями и без, *чтобы* выбирать нужные позиции осознанно, без дубликатов.

Система загружает список оборудования из `object_equipment` при открытии модального окна. Уже добавленные в визит единицы скрыты из списка. При повторном открытии модалки отображаются только оставшиеся. Если всё оборудование уже добавлено — соответствующая вкладка показывает сообщение «Всё оборудование уже добавлено в визит».

**Группировка по уровням привязки:**
- **Уровень помещения** — оборудование, у которого указан `roomTypeCode` в `object_equipment`. Инженер сначала выбирает помещение из выпадающего списка, затем видит все единицы оборудования в этом помещении. Все чекбоксы отмечены по умолчанию. После нажатия «Добавить» выбранные единицы добавляются в визит.
- **Уровень объекта** — оборудование без привязки к помещению (`roomTypeCode` отсутствует). Отображается плоским списком с чекбоксами, все отмечены по умолчанию.

**Уточнение помещения:**
Для единиц оборудования, у которых не указан тип помещения, отображается метка «⚠️ Помещение не указано». При выборе такого оборудования появляется inline-список для выбора типа помещения из справочника. После добавления визита выбранное помещение сохраняется в `object_equipment` (поля `room_confirmed_at`, `room_confirmed_by`) и используется во всех последующих визитах.

**Новый API-эндпоинт:**
`GET /api/refs/object-equipment/rooms?address_id=...&exclude_visit_id=...` — возвращает список помещений с количеством оборудования для текущего объекта (исключая уже добавленные в указанный визит). Для инженеров — с фильтрацией по специализации (учитываются только помещения, содержащие оборудование доступных типов).

**US-1.9 — Предложение добавить оборудование в привязку объекта**
*Как* инженер, *я хочу* отметить чекбоксом «Предложить добавить в привязку объекта» при добавлении оборудования, *чтобы* предложить администратору закрепить обнаруженное оборудование за данным объектом для будущих визитов.
Предложение сохраняется со статусом `pending` и становится доступным администратору для утверждения или отклонения.

**US-GROUP-01 — Группировка оборудования по уровню помещения**
*Как* инженер, *я хочу* выбирать оборудование с привязкой к помещению, предварительно выбирая нужное помещение из списка, *чтобы* быстро находить оборудование в конкретных помещениях объекта.
На вкладке «📍 Уровень помещения» инженер видит выпадающий список помещений (полученный через `GET /api/refs/object-equipment/rooms`). После выбора помещения отображается чекбокс-лист всех единиц оборудования в этом помещении. Все чекбоксы отмечены по умолчанию. Уровень привязки определяется по наличию `roomTypeCode` в записи `object_equipment`.

**US-GROUP-02 — Группировка оборудования по уровню объекта**
*Как* инженер, *я хочу* видеть оборудование без привязки к помещению отдельным списком, *чтобы* добавлять его в визит без необходимости указывать помещение.
На вкладке «🏠 Уровень объекта» отображается плоский чекбокс-лист единиц оборудования из `object_equipment`, у которых `roomTypeCode` отсутствует (сети, тепловые сети, приборы учёта, РЩ без помещения). Все чекбоксы отмечены по умолчанию.

**US-METER-01 — Автозаполнение полей счётчиков из справочника объекта или данных задачи**
*Как* инженер, *я хочу*, чтобы при открытии задачи-счётчика (Прибор учёта э/э, ХВС, ГВС) поля «Модель счётчика» и «Номер счётчика» автоматически заполнялись из данных привязки (`object_equipment`) или из полей задачи (`brand`, `model`, `serialNumber`), *чтобы* не вводить повторяющиеся данные вручную.
Логика автозаполнения:
- «Модель счётчика» = `brand` + " " + `model` (конкатенация; если `brand` пуст — только `model`)
- «Номер счётчика» = `serial_number`
- Источ данных: сначала `object_equipment` (если задача привязана), иначе — собственные поля задачи `brand`/`model`/`serialNumber` (для нового оборудования на модерации)
Поля остаются редактируемыми после автозаполнения. Рядом с автозаполненными полями отображается иконка 📋 с тултипом «Автозаполнено из справочника объекта».

#### 4.1.6. Группировка климатического оборудования в единый чек-лист

**US-GROUP-NEW-01 — Групповой чек-лист для климата в помещении**
*Как* инженер ВиК, *я хочу*, чтобы при добавлении климатического оборудования в помещении формировался один групповой чек-лист, *чтобы* не заполнять одинаковые параметры (температура помещения, заключение) для каждой единицы отдельно.
Система создаёт одну задачу типа `group_climate` на все внутренние блоки климатического оборудования (СС, МСС, VRV) в помещении. Общие параметры (температура, заключение, рекомендации) заполняются один раз. Для каждой единицы оборудования инженер указывает индивидуальный статус (ОК/Не ОК) и загружает фото ДО/ПОСЛЕ.

**US-GROUP-NEW-02 — Групповой чек-лист для наружных блоков**
*Как* инженер, *я хочу*, чтобы наружные блоки кондиционеров (splitnar, mssnar, vrv_nar) группировались в отдельную задачу по уровню объекта (здания), *чтобы* не привязывать их к конкретному помещению.
Наружные блоки определяются по полю `is_outdoor_unit = true` в `object_equipment`. Все наружные блоки объекта формируют одну групповую задачу.

**US-GROUP-NEW-03 — Индивидуальные статусы и фото для каждой единицы**
*Как* инженер, *я хочу* для каждой единицы в групповом чек-листе указывать индивидуальный статус (ОК/Не ОК) и загружать 2 фото (до/после), *чтобы* фиксировать состояние каждого кондиционера отдельно.

**US-GROUP-NEW-04 — Добавление и удаление единиц в групповой задаче**
*Как* инженер, *я хочу* иметь возможность добавлять и удалять единицы оборудования в групповом чек-листе, *чтобы* гибко формировать состав работ.

**US-GROUP-NEW-05 — Валидация и сохранение групповой задачи**
*Как* система, *я хочу* разрешать сохранение групповой задачи с частичным заполнением, *чтобы* инженер мог сохранить прогресс и вернуться к незавершённым единицам позже.
Логика сохранения:
- Инженер может нажать «Сохранить» в любой момент — общие параметры и заполненные данные единиц сохраняются
- Статус задачи определяется автоматически:
  - `in_progress` («В работе») — если хотя бы одна единица не имеет статуса или фото
  - `completed` («Выполнено») — если все единицы имеют статус и оба фото (ДО и ПОСЛЕ)
- При сохранении неполной задачи отображается сообщение: «Сохранено. Не завершено единиц: N»
- Если хотя бы одна единица имеет статус «Не ОК», поле «Дополнительные рекомендации» становится обязательным

**US-GROUP-NEW-06 — Единообразие структуры при одной единице**
*Как* система, *я хочу* даже при наличии только одной единицы климатического оборудования в помещении формировать групповую задачу, *чтобы* обеспечить единообразие структуры данных.

**Принцип группировки задач:**

| Тип задачи | Оборудование | Уровень | Формирование |
|------------|-------------|---------|--------------|
| **Групповая (климат)** | Внутренние блоки СС, МСС, VRV | Помещение | Один чек-лист на все единицы в помещении |
| **Групповая (наружные)** | Наружные блоки СС, МСС, VRV | Объект | Один чек-лист на все наружные блоки объекта |
| **Индивидуальная** | Счётчики, РЩ/ГРЩ, сети, вентиляция | По единице | Отдельный чек-лист на каждую единицу |

#### 4.1.2. Заполнение параметров

**US-2.1 — Быстрый ввод рекомендаций**  
*Как* инженер, *я хочу* отмечать галочками типовые рекомендации из справочника (с фильтрацией по виду оборудования), *чтобы* не печатать текст на телефоне в полевых условиях.

**US-2.2 — Условная обязательность**  
*Как* система, *я хочу* делать поле «Дополнительные рекомендации» обязательным только при выборе заключения «Исправно, есть замечания» или «Неисправно», *чтобы* инженер описывал проблему, но не тратил время, если всё в норме.

**US-2.3 — Безопасное редактирование**  
*Как* инженер, *я хочу*, чтобы кнопка «Сбросить» очищала **только текущую задачу**, а не весь визит, *чтобы* случайное нажатие не уничтожило уже проделанную работу.

#### 4.1.3. Фотофиксация

**US-3.1 — Фото ДО и ПОСЛЕ за один проход**  
*Как* инженер, *я хочу* на Странице 5 сразу загружать оба фото (до и после работ), *чтобы* зафиксировать результат без возврата в чек-лист.

**US-3.2 — Разное количество фото**
*Как* система, *я хочу* требовать:
- 2 фото (ДО/ПОСЛЕ) — для климатического оборудования (СС, МСС, VRV, тепловая завеса, приточная установка, приточно-вытяжная установка, вытяжная установка)
- 1 фото (ДО) — для остального оборудования (РЩ, счетчики, сети)

*чтобы* логика соответствовала технологическим требованиям.

**US-3.3 — Защита персональных данных (152-ФЗ)**  
*Как* система, *я хочу* показывать предупреждение при первом фото в клиентских зонах:
```
⚠️ ВНИМАНИЕ!
Убедитесь, что в кадр не попали:
• Лица посетителей
• Персональные данные на мониторах
• Банковские карты и документы
[Понятно, сделать фото]
```

#### 4.1.4. Завершение и отчет

**US-4.1 — Формирование отчета**  
*Как* инженер, *я хочу* по кнопке «Завершить визит» получить PDF-отчет и ZIP-архив с фото и Excel-таблицей оборудования, *чтобы* отправить результат заказчику.

**US-4.2 — Маркировка фотографий**  
*Как* система, *я хочу* автоматически именовать файлы по шаблону:
```
{№}_{тип_оборудования}_{помещение}_{moment}.jpg
```
Примеры:
- `01_rsch_server_before.jpg`
- `02_splitvn_server_before.jpg`
- `02_splitvn_server_after.jpg`

**US-4.3 — Отправка по email**  
*Как* инженер, *я хочу* после формирования отчета отправить ZIP-архив (PDF + фото + Excel) на email заказчика (предзаполненный из справочника), *чтобы* не скачивать файл и не пересылать вручную.

**US-4.4 — Резервное скачивание**
*Как* инженер, *я хочу* иметь возможность скачать ZIP-архив (PDF + фото + Excel) на устройство, *чтобы* переслать его вручную при недоступности email.

**US-4.5 — Валидация обязательных полей задач при завершении визита**
*Как* система, *я хочу* при завершении визита проверять наличие обязательных параметров в задачах, *чтобы* отчёт содержал полные данные и исключал пустые показания.

**Единая конфигурация обязательных параметров:**
- Конфигурация `REQUIRED_PARAMS_CONFIG` вынесена в `shared/types/params.ts` и используется как сервером, так и клиентом — единый источник истины.
- Покрывает 25+ типов оборудования: счётчики (`schetchik_electroshc`, `schetchik_hvs`, `schetchik_gvs`, `meter_gas`), вентиляция (`teplozavesa`, `pritochnaya`, `pritochno-vytyzhnaya`, `vytyzhnaya`), климат внутренние (`splitvn`, `mssvn`, `vrv_vn`), климат наружные (`splitnar`, `mssnar`, `vrv_nar`), котлы (`boiler_gas`, `boiler_liquid`, `boiler_solid`, `boiler_elec`), ИБП (`ibp`), мобильный кондиционер (`cond_mobile`), вытяжная установка (`vytyzhnaya`).

Правила серверной валидации при завершении визита (`POST /api/visits/:id/complete`):
- **Приборы учёта** (коды: `schetchik_electroshc`, `schetchik_hvs`, `schetchik_gvs`, `meter_gas`): обязательны поля `model` (модель счётчика), `serial_number` (серийный номер), `readings` (показания). Пустые значения блокируют завершение.
- **Климатическое оборудование** (коды: `splitvn`, `mssvn`, `vrv_vn`): обязательно поле `room_temperature` (температура помещения) для внутренних блоков.
- **Вентиляционные установки** (коды: `teplozavesa`, `pritochnaya`, `pritochno-vytyzhnaya`, `vytyzhnaya`): обязательны поля `temperature_before` / `temperature_after`.
- **Котлы** (коды: `boiler_gas`, `boiler_liquid`, `boiler_solid`, `boiler_elec`): обязательные параметры согласно `REQUIRED_PARAMS_CONFIG`.
- **ИБП** (`ibp`), **мобильный кондиционер** (`cond_mobile`): обязательные параметры согласно `REQUIRED_PARAMS_CONFIG`.
- При обнаружении незаполненных обязательных полей сервер возвращает HTTP 422 с перечнем задач и конкретных полей, которые необходимо заполнить.
- Клиентская сторона: при нажатии «Завершить визит» (`handleComplete`) выполняется предварительная проверка — клиент проверяет **ВСЕ** required параметры из shared-конфигурации, а также проверяет задачи со статусом `not_started` перед завершением. При наличии ошибок отображаются информативные сообщения с указанием задачи и недостающих полей.

**US-4.6 — Антифрод-проверка текстовых данных**
*Как* система, *я хочу* отклонять мусорные данные в текстовых и числовых полях задач, *чтобы* предотвратить намеренное или случайное заполнение некорректными значениями.
Правила антифрод-валидации (серверная сторона):
- Текстовые поля (`model`, `serial_number`, `brand`, `additional_recommendations`): отклоняются значения, состоящие только из пробелов, точек, спецсимволов или их комбинаций (например `"...."`, `"   "`, `"!!!"`, `"@#$%"`).
- Поля `brand`, `model`, `serialNumber` не могут начинаться со спецсимволов или пробелов (первый символ — буква или цифра).
- **Блок-лист placeholder-значений:** поля `brand`, `model`, `serialNumber` не могут содержать слова-заглушки: «нет», «нет данных», «неизвестно», «не заполнено», «отсутствует», «нет информации», «н/д», «n/a», «null», «none», «unknown». Проверка регистронезависимая, с проверкой вхождения подстроки (ловит «нет123», «Нет_2222», «N/A»).
- **Формат модели:** поле `model` должно содержать и буквы, и цифры одновременно (например, «Меркурий 230», «SC-125A»). Только буквы или только цифры — отклоняется.
- **Детектор копипаста:** если все три поля (`brand`, `model`, `serialNumber`) содержат одинаковое значение — отклоняется (например, «Меркурий / Меркурий / Меркурий»).
- При обнаружении мусорных данных сервер возвращает HTTP 422 с указанием поля и причины отклонения.
- Клиентская валидация: те же правила применяются мгновенно в форме добавления оборудования (красное сообщение под полем).

**US-4.7 — Валидация показаний приборов учёта**
*Как* система, *я хочу* проверять корректность числовых показаний счётчиков, *чтобы* исключить ввод заведомо неверных данных.
Правила валидации поля `readings`:
- Значение должно быть числом (допускается разделитель «.» или «,»).
- Целая часть — не более 9 цифр, дробная часть — не более 4 цифр.
- Значение не может начинаться с `0` (кроме значения `0` и десятичных дробей вида `0.xxx`).
- Разделитель дробной части «,» автоматически нормализуется в «.» при сохранении.
- Отрицательные значения запрещены.
- При некорректном значении сервер возвращает HTTP 422 с описанием ошибки.

**US-4.8 — Клиентская валидация числовых полей в форме задачи**
*Как* инженер, *я хочу* получать мгновенную обратную связь при вводе числовых значений, *чтобы* исправлять ошибки до отправки данных на сервер.
Правила клиентской валидации:
- Числовые поля (`readings`, `room_temperature`, `temperature_before`, `temperature_after`, `cooling_capacity_kw`) принимают как точку, так и запятую в качестве разделителя дробной части.
- Запятая автоматически нормализуется в точку в реальном времени (при вводе).
- Ограничения: целая часть ≤ 9 цифр, дробная часть ≤ 4 цифры.
- При выходе за границы — визуальная подсветка поля и tooltip с описанием ограничения.
- Проверка при завершении визита: если в задачах есть незаполненные обязательные поля, отображается список ошибок с навигацией к соответствующей задаче.

#### 4.1.5. Работа в полевых условиях

**US-5.1 — Офлайн-режим**  
*Как* инженер, *я хочу*, чтобы приложение работало без интернета (подвалы, серверные, тепловые узлы), *чтобы* не прерывать работу из-за отсутствия связи.

**US-5.2 — Автосинхронизация**  
*Как* система, *я хочу* при появлении сети автоматически отправлять накопленные данные и фото, *чтобы* отчет был доступен без моих действий.

**US-5.3 — Автосохранение**
*Как* система, *я хочу* автоматически сохранять данные каждые 30 секунд и предупреждать при закрытии с несохраненными данными.
Реализовано: автосохранение срабатывает по таймеру (интервал 30 секунд), при переключении между задачами и перед формированием отчёта. В интерфейсе отображается визуальный индикатор состояния: «Сохранено» / «Сохранение...» / «Не сохранено». При попытке закрыть страницу с несохранёнными данными — предупреждение `beforeunload`.

**US-5.4 — Автообновление приложения**
*Как* система, *я хочу* при деплое новой версии автоматически предлагать пользователю обновить приложение, *чтобы* пользователь всегда работал с актуальной версией без необходимости вручную очищать кэш.
При обнаружении новой версии внизу экрана появляется баннер «Доступна новая версия приложения» с кнопками «Обновить» и «Закрыть». Нажатие «Обновить» перезагружает страницу с новой версией.
На мобильных устройствах баннер адаптирован: тёмный фон (`#1a1a2e`), белая кнопка «Обновить» с синим текстом, вертикальная раскладка (текст сверху, кнопки снизу по центру), увеличенный размер шрифта и отступов.

**US-5.5 — Автообновление данных при возврате**
*Как* система, *я хочу* при возврате пользователя на вкладку автоматически обновлять данные (визиты, справочники), *чтобы* пользователь видел актуальную информацию без ручного обновления страницы.
Синхронизация данных запускается при событии `visibilitychange` (переход на вкладку). Оборудование в модальном окне загружается с сервера без кэширования при каждом открытии.

### 4.5. Модуль «Специализация»

**US-SPEC-01 — Инженер выбирает специализацию в ЛК**
*Как* инженер, *я хочу* выбирать свою специализацию (ВиК, ИСЖ, ГПМ, ДГУ, ИБП) на странице профиля в личном кабинете, *чтобы* система фильтровала задачи и оборудование по моему профилю.
Инженер может выбрать любую комбинацию из 5 доступных специализаций. Изменения вступают в силу немедленно.

**US-SPEC-02 — ТМ изменяет специализацию подчинённого инженера**
*Как* ТМ (или администратор), *я хочу* изменять специализацию закреплённого за мной инженера, *чтобы* управлять распределением задач в группе.
ТМ видит список своих инженеров с текущими специализациями и может переключать чекбоксы ВиК/ИСЖ/ГПМ/ДГУ/ИБП.

**US-SPEC-03 — Специализация по умолчанию при создании инженера**
*Как* система, *я хочу* при создании нового инженера устанавливать специализацию ИСЖ по умолчанию (остальные — false), *чтобы* инженер сразу мог работать с базовым оборудованием без дополнительной настройки.
Значения по умолчанию: `specialization_iszh = true`, остальные `specialization_*` = false.

**US-SPEC-04 — Блокирующий экран при отсутствии специализации**
*Как* система, *я хочу* показывать блокирующий экран (SpecializationGate), если у инженера не выбрана ни одна специализация, *чтобы* предотвратить создание визитов без профильной специализации.
Экран содержит 5 чекбоксов выбора специализации (ВиК, ИСЖ, ГПМ, ДГУ, ИБП) и кнопку «Сохранить». Доступ к основному интерфейсу заблокирован до выбора хотя бы одной специализации.

**Маппинг специализаций и оборудования:**

| Специализация | Коды оборудования |
|:-------------:|-------------------|
| **ВиК** (Вентиляция и кондиционирование) | ~~vent~~ (деактивирован), teplozavesa, pritochnaya, pritochno-vytyzhnaya, vytyzhnaya, vrv_vn, vrv_nar, mssvn, mssnar, splitvn, splitnar, cond_mobile |
| **ИСЖ** (Инженерные сети и здания) | rsch, schetchik_gvs, schetchik_hvs, schetchik_electroshc, seti_vodosnab, teplovye_seti, itp, boiler_gas, boiler_liquid, boiler_solid, boiler_elec, meter_gas, sololift, barrier_roller, door_auto, coffee, purifier, cooler, aquarium, bubble_panel |
| **ГПМ** (Грузоподъёмные механизмы) | lift_pass, lift_cargo, lift_cargo_pass, lift_invalid |
| **ДГУ** (Дизель-генераторные установки) | dgu, mkgu |
| **ИБП** (Источники бесперебойного питания) | ibp |

> **Примечание:** Вид оборудования `vent` («Вентиляционная установка») деактивирован и скрыт из интерфейса. Вместо него используются 4 подвида: `teplozavesa` (Тепловая завеса), `pritochnaya` (Приточная установка), `pritochno-vytyzhnaya` (Приточно-вытяжная установка), `vytyzhnaya` (Вытяжная установка). Запись `vent` сохранена в базе данных для обратной совместимости с ранее созданными задачами. Все 4 новых вида используют ту же форму параметров, что и старый `vent` (Страница 4.3), и относятся к специализации ВиК.

**Новое поле `specialization_req` в таблице `equipment_types`:**

| Поле | Тип | Описание |
|------|-----|----------|
| specialization_req | TEXT (nullable) | Требуемая специализация: `vik` (ВиК), `iszh` (ИСЖ), `gpm` (ГПМ), `dgu` (ДГУ) или `ibp` (ИБП). Если NULL — оборудование доступно всем специализациям |

### 4.6. Модуль «Личный кабинет»

**US-LK-01 — Инженер добавляет объекты в Избранное**
*Как* инженер (или ТМ), *я хочу* добавлять объекты в список избранных (⭐), *чтобы* быстро находить часто посещаемые объекты.
Избранные объекты отображаются на странице профиля с возможностью быстрого перехода. Максимум 20 объектов.

**US-LK-02 — Избранное доступно офлайн**
*Как* инженер, *я хочу*, чтобы список избранных объектов был доступен без интернета (синхронизация с IndexedDB), *чтобы* пользоваться избранным в полевых условиях.

**US-LK-03 — Предупреждение при отсутствии профильного оборудования**
*Как* система, *я хочу* показывать предупреждение, если на избранном объекте нет оборудования специализации инженера, *чтобы* инженер заранее знал, что визит может быть непродуктивным.

**US-LK-04 — ТМ видит красный индикатор при неисправностях на закреплённых объектах**
*Как* ТМ, *я хочу* видеть красный индикатор (⚠️) рядом с закреплёнными за мной объектами в профиле, на которых есть неисправности в последних визитах, *чтобы* оперативно реагировать на проблемы.

**US-LK-05 — Админ видит системную информацию в ЛК**
*Как* администратор, *я хочу* видеть в личном кабинете быстрые ссылки на справочники и системную информацию, *чтобы* быстро навигировать по административным функциям.
