**Дата:** 16.10.2026  
**Статус:** Проект  
**Инициатива:** Предложение инженеров — при повторном визите на объект в другом отчётном периоде не вводить задачи и оборудование вручную

---

## 1. Описание проблемы

Инженеры регулярно посещают одни и те же объекты в каждом отчётном периоде (например, по заявке ИСЖ). При каждом визите им приходится вручную:
- Добавлять все задачи (типы оборудования, помещения)
- Привязывать оборудование (бренд, модель, серийный номер)
- Заполнять параметры (температуры, показания счётчиков)

При этом структура задач (набор оборудования, типы, помещения) от периода к периоду не меняется — меняются только измеряемые значения (температуры, показания) и фотофиксация.

## 2. Решение

Добавить кнопку **«Клонировать»** на странице завершённого визита, которая создаёт новый визит в текущем периоде с полной копией структуры задач и оборудования, но с очищенными измеряемыми параметрами.

## 3. Функциональные требования

### 3.1. Кнопка «Клонировать»

**Где размещается:**
- На странице детального визита (`VisitPage.tsx`) — в **dropdown-меню (⋮)** в шапке визита, рядом с NotificationBell и TorchButton
- На странице списка визитов (`VisitListPage.tsx`) — в меню действий карточки визита (мобильный: overflow-меню ⋮, десктоп: иконочная кнопка `CopyOutlined`)

**Расположение на VisitPage (dropdown ⋮):**
- Кнопка `⋮` (`EllipsisOutlined`, 18px) размещается в заголовке страницы после `TorchButton`
- При нажатии открывается dropdown-меню с пунктами:
  - «Клонировать» (иконка `CopyOutlined`, цвет `#0F766E`) — для завершённых визитов
  - «Удалить визит» (иконка `DeleteOutlined`, цвет `#DC2626`) — переносится из текущего расположения
- Dropdown используется и на десктопе, и на мобильном (единый паттерн)

**Доступность:**
- Пункт «Клонировать» виден только для визитов в статусах: `completed`, `sent`, `sent_by_engineer`, `sent_by_tm`, `corrected_by_tm`
- Пункт виден:
  - Инженеру — для своих визитов и визитов коллег из своей команды (с учётом специализации, см. раздел 3.2)
  - ТМ — для визитов своих инженеров
  - Админу — для любых визитов
- Пункт скрыт для удалённых визитов (`isDeleted = true`)
- Пункт скрыт для визитов в статусе `awaiting_assignment` (нет инженера-исполнителя)

**Визуальное оформление:**
- Иконка в dropdown: `CopyOutlined` (Ant Design)
- Текст: «Клонировать»
- Цвет текста: `#0F766E` (colorPrimary)
- На мобильном: тот же dropdown ⋮, что и на десктопе

### 3.2. Клонирование визитов коллег и проверка специализации

Инженер может клонировать визиты коллег из своей команды (видимость визитов команды реализована 07.10.2026). При этом:

**Правила:**
1. **Инженер клонирует свой визит:**
   - Все задачи копируются без фильтрации
   - `engineerName` = ФИО инженера из исходного визита
   - `userId` = ID инженера из исходного визита

2. **Инженер клонирует визит коллеги:**
   - `engineerName` = ФИО инженера, который клонирует (текущий пользователь)
   - `userId` = ID инженера, который клонирует (текущий пользователь)
   - **Фильтрация задач по специализации:**
     - У каждого типа оборудования (`EquipmentType`) есть поле `specializationReq` (vik, iszh, gpm, dgu, ibp)
     - У инженера есть флаги специализации: `specializationVik`, `specializationIszh`, `specializationGpm`, `specializationDgu`, `specializationIbp`
     - Копируются только задачи, где `equipmentType.specializationReq` соответствует специализации инженера
     - Если у задачи `specializationReq = null` — задача копируется (универсальная)
     - Если у инженера нет ни одной специализации (все флаги `false`) — копируются все задачи (fallback), в `AuditLog` записывается предупреждение: `"engineer has no specialization, all tasks copied"`

3. **ТМ клонирует визит инженера:**
   - `engineerName` = ФИО инженера из исходного визита (не меняется)
   - `userId` = ID инженера из исходного визита
   - `assignedById` = ID ТМ, выполнившего клонирование
   - Статус: `planned` (визит назначен инженеру)
   - Все задачи копируются без фильтрации
   - Если исходный визит имел `visitEngineers` (мульти-специалистный визит) — все инженеры копируются в новый визит с сохранением `isPrimary`

4. **Админ клонирует любой визит:**
   - Аналогично ТМ, но без проверки привязки к команде

**Пример (инженер):**
- Инженер 1 (специализация ВИК) клонирует визит коллеги Инженера 2 (специализация ИСЖ):
  - Копируются только задачи с `specializationReq = 'vik'` или `null`
  - Задачи с `specializationReq = 'iszh'` НЕ копируются
  - Новый визит создаётся с `userId` и `engineerName` Инженера 1

**Пример (ТМ):**
- ТМ клонирует мульти-специалистный визит инженера (`isMultiSpecialist = true`, 3 `visitEngineers`):
  - Новый визит создаётся с `userId` и `engineerName` инженера из исходного визита
  - Все 3 `visitEngineers` копируются в новый визит с сохранением `isPrimary`
  - Все задачи копируются без фильтрации
  - Статус: `planned`

### 3.3. Алгоритм клонирования

#### 3.3.1. Создание нового визита

| Поле | Значение в клоне | Источник |
|---|---|---|
| `addressId` | **Копия** | Из исходного визита |
| `userId` | **Зависит** | См. раздел 3.2 (инженер свой/коллега/ТМ/админ) |
| `engineerName` | **Зависит** | См. раздел 3.2 (инженер свой/коллега/ТМ/админ) |
| `contractId` | **Авто** | Определяется из `tm_objects` (актуальный договор на текущую дату) |
| `dateStart` | **Текущая дата** | `NOW()` — дата и время нажатия кнопки «Клонировать». **Не редактируется** (DatePicker disabled) |
| `timeStart` | **Текущее время** | Текущее время (МСК) |
| `season` | **Авто** | Определяется автоматически от `dateStart` (лето: апрель–сентябрь, зима: октябрь–март) |
| `status` | `not_started` или `planned` | `not_started` если инженер клонирует, `planned` если ТМ/админ |
| `isMultiSpecialist` | **Зависит** | `false` если инженер клонирует, копия из исходного если ТМ/админ |
| Все audit-поля | Не копируются | `assignedById` (кроме ТМ), `sentByEngineerAt`, `sentByTmAt`, `tmCorrected`, `editingEngineerId` и т.д. |

**Важно:** `dateStart` фиксируется в момент создания визита (как при обычном создании, так и при клонировании). Пользователь не может изменить дату визита — DatePicker всегда disabled.

#### 3.3.2. Клонирование задач

Для каждой задачи исходного визита создаётся копия (с учётом фильтрации по специализации, см. раздел 3.2):

| Поле | Значение в клоне | Комментарий |
|---|---|---|
| `equipmentTypeId` | **Копия** | Тип оборудования |
| `taskType` | **Копия** | `individual` или `group_climate` |
| `roomTypeId` | **Копия** | Тип помещения |
| `roomTypeCode` | **Копия** | Код помещения |
| `objectEquipmentId` | **Копия** | Привязка к конкретной единице оборудования |
| `brand` | **Копия** | Из исходной задачи |
| `model` | **Копия** | Из исходной задачи |
| `serialNumber` | **Копия** | Из исходной задачи |
| `comment` | `null` | **Очищается** |
| `sortOrder` | **Копия** | Сохраняется порядок |
| `status` | `not_started` | **Сбрасывается** |
| `parameters` | `null` | **Очищается** (температуры, показания и т.д.) |
| `selectedRecommendationIds` | `[]` | **Очищается** |
| `additionalRecommendations` | `null` | **Очищается** |
| `conclusion` | `null` | **Очищается** |
| `externalRequestId` | `null` | Не копируется |

#### 3.3.3. Клонирование TaskEquipmentItem (для group_climate)

Для задач типа `group_climate` копируются элементы оборудования:

| Поле | Значение в клоне |
|---|---|
| `objectEquipmentId` | **Копия** |
| `sortOrder` | **Копия** |
| `status` | `null` (**очищается**) |

#### 3.3.4. Фотографии

**НЕ копируются.** Инженер должен сделать новые фотографии при текущем визите. Это осознанное решение:
- Фотографии привязаны к конкретному моменту времени
- Антифрод-система (pHash, GPS, timestamp) проверяет актуальность фото
- Копирование старых фото нарушило бы целостность верификации

#### 3.3.5. Привязка к заявкам (VisitRequest)

**Автоматическая** — эндпоинт `POST /api/visits/:id/clone` должен **внутри себя** реализовать логику автопривязки заявок (скопировать из существующего кода создания визита/задач):

1. **После создания визита** (аналог `autoAssignRequests: true`):
   - Ищутся заявки ИСЖ объекта (`iszh_object`) по `addressId`
   - Фильтр по периоду: `startDate <= currentDate <= deadline`
   - Создаются связи `VisitRequest`

2. **После создания каждой задачи** (аналог автопривязки по `serialNumber`):
   - Для каждой задачи ищется заявка с совпадающим `equipmentTypeCode` + `serialNumber`
   - На том же адресе, в активном периоде
   - Создаётся связь `VisitRequest`

**Важно:** 
- Логика автопривязки должна быть **вынесена в отдельную функцию** (чтобы не дублировать код из `POST /api/visits` и `POST /api/visits/:visitId/tasks`)
- Все операции выполняются в одной транзакции

## 4. Проверки и ограничения

### 4.1. Защита от дубликатов

Перед клонированием сервер проверяет:
- Если у инженера (который клонирует) уже есть **активный** визит (`not_started`, `planned`, `in_progress`) по этому адресу **с начала текущего месяца** — **запретить клонирование**
- Проверка: `WHERE addressId = ? AND userId = ? AND status IN ('not_started', 'planned', 'in_progress') AND dateStart >= DATE_TRUNC('month', CURRENT_DATE)`
- Ответ: `409 Conflict` с сообщением «У вас уже есть активный визит по этому адресу в текущем месяце. Перейдите в существующий визит или завершите его перед клонированием.»
- Тело ответа:
  ```json
  {
    "error": "ACTIVE_VISIT_EXISTS",
    "message": "У вас уже есть активный визит по этому адресу в текущем месяце",
    "existingVisitId": "uuid-существующего-визита"
  }
  ```

### 4.2. Проверка исходного визита

- Исходный визит должен существовать и не быть удалённым (`isDeleted = false`)
- Исходный визит должен быть в статусе `completed`, `sent`, `sent_by_engineer`, `sent_by_tm` или `corrected_by_tm`
- Исходный визит НЕ должен быть в статусе `awaiting_assignment` (нет инженера-исполнителя)
- Проверка доступа:
  - Инженер может клонировать свои визиты (`userId === req.userId`)
  - Инженер может клонировать визиты коллег из своей команды:
    1. Получить ID инженеров команды через `getTeamEngineerIds(tmId)`
    2. Проверить: исходный визит имеет `userId` из этого списка ИЛИ визит имеет `visitEngineer` с `engineerId` из этого списка
    3. Если да — доступ разрешён
  - ТМ может клонировать визиты своих инженеров (через `tmEngineer`)
  - Админ может клонировать любые визиты
- Проверка блокировки редактирования:
  - Если исходный визит заблокирован другим инженером (`editingEngineerId !== null && editingEngineerId !== req.userId`) — отказать с сообщением «Визит сейчас редактируется другим инженером»
  - Ответ: `423 Locked`

### 4.3. Проверка доступа к адресу

- Адрес должен быть закреплён за ТМ текущего инженера (стандартная проверка через `tm_objects`)
- Если адрес более не доступен инженеру — отказать с понятным сообщением

### 4.4. Транзакционность

Вся операция клонирования (визит + задачи + TaskEquipmentItem + привязка заявок) должна выполняться в **одной транзакции Prisma**. При ошибке на любом шаге — откат всех изменений.

## 5. API

### 5.1. Новый эндпоинт

```
POST /api/visits/:id/clone
```

**Параметры URL:**
- `id` — UUID исходного визита

**Тело запроса:** (пустое или отсутствует)

**Ответ (201 Created):**
```json
{
  "id": "uuid-нового-визита",
  "sourceVisitId": "uuid-исходного-визита",
  "tasksCount": 12,
  "message": "Визит успешно клонирован. Создано 12 задач."
}
```

**Ошибки:**
- `400` — исходный визит не в завершённом статусе
- `403` — нет доступа к визиту или адресу
- `404` — исходный визит не найден
- `409` — уже есть активный визит по этому адресу в текущем месяце
- `423` — визит заблокирован другим инженером

### 5.2. Логирование

В `AuditLog` записывается действие:
```
action: "visit_cloned"
entityType: "visit"
entityId: id нового визита
oldValue: { sourceVisitId: "..." }
newValue: { tasksCount: 12 }
```

## 6. Клиентская часть

### 6.1. Поток действий пользователя

1. Инженер открывает завершённый визит
2. Нажимает кнопку `⋮` в шапке визита (рядом с NotificationBell)
3. В dropdown-меню выбирает пункт «Клонировать»
4. Появляется модальное окно подтверждения:
   ```
   Клонирование визита

   Будет создан новый визит на адрес: [полный адрес]
   с [N] задачами из визита от [дата исходного визита].

   ⚠️ Измеряемые параметры и фотографии нужно заполнить заново.

   Дата нового визита: [текущая дата] (сезон: [зима/лето])

   [Отмена]  [Клонировать]
   ```
5. После подтверждения — вызов API `POST /api/visits/:id/clone`
6. При успехе — переход на страницу нового визита (`/visit/{newId}`)
7. При ошибке 409 — показать сообщение о существующем активном визите

- Альтернативно: пункт отображается, но при нажатии показывается toast «Клонирование доступно только онлайн»

## 8. Граничные случаи

### 8.1. Исходный визит содержит задачи с equipment_proposals

Если к задачам исходного визита привязаны `EquipmentProposal` (предложения по оборудованию):
- Предложения **НЕ** копируются в новый визит
- Это корректно — proposals привязаны к конкретному визиту и периоду

### 8.2. Оборудование было удалено с объекта

Если `objectEquipmentId` задачи ссылается на оборудование, которое было деактивировано (`isActive = false`):
- Задача всё равно создаётся с этой привязкой (оборудование физически остаётся в БД)
- При следующем редактировании задачи инженер увидит, что оборудование неактивно

### 8.3. Изменение справочников

Если тип оборудования или тип помещения был деактивирован между исходным и клонированным визитом:
- Задача создаётся с существующими `equipmentTypeId` / `roomTypeId` (ссылка не проверяется на `isActive`)
- Это допустимо — данные уже существуют в системе

### 8.4. Клонирование визита ТМ ✅ Решено

ТМ **может** клонировать визиты своих инженеров с теми же правилами:
- Новый визит создаётся с `userId` инженера из исходного визита (не меняется)
- `engineerName` = ФИО инженера из исходного визита (не меняется)
- `assignedById` = ID ТМ, выполнившего клонирование
- Статус: `planned` (визит назначен инженеру)
- Проверка доступа: ТМ имеет доступ к адресу через `tm_objects`
- Все задачи копируются без фильтрации по специализации
- **VisitEngineers:** если исходный визит имел `visitEngineers` (мульти-специалистный визит) — все инженеры копируются в новый визит с сохранением `isPrimary`

### 8.5. Множественное клонирование

Инженер может клонировать один и тот же визит несколько раз (например, если случайно создал лишний). Ограничение — только через проверку активного визита (п. 4.1).

## 13. Изменение: дата визита фиксирована (для всех визитов)

**Дата:** 16.10.2026  
**Решение Анны:** Дата визита (`dateStart`) должна фиксироваться в момент создания визита и быть недоступной для редактирования. Это касается как обычного создания визита, так и клонирования.

**Что меняется:**

### 13.1. Обычное создание визита (`POST /api/visits`)

**Было:** Инженер мог выбрать дату через DatePicker при создании визита.  
**Стало:** `dateStart` = `NOW()` (текущая дата и время). DatePicker **заблокирован** (disabled).

**Сервер:**
- Игнорировать `dateStart` из тела запроса (если передан)
- Всегда устанавливать `dateStart = NOW()`
- `timeStart` = текущее время (МСК)

**Клиент (VisitPage.tsx):**
- DatePicker для `dateStart` — `disabled={true}`
- Показывать текущую дату как текст (не редактируемое поле)
- Подпись: «Дата визита: [текущая дата]»

### 13.2. Клонирование визита (`POST /api/visits/:id/clone`)

**Было:** (см. раздел 3.3.1)  
**Стало:** Аналогично — `dateStart = NOW()`, не редактируется.

### 13.3. Обоснование

- Инженер приезжает на объект **сегодня** — дата визита = сегодня
- Нет смысла позволять выбирать дату — визит всегда совершается в момент создания
- Упрощает UX — меньше полей для заполнения
- Исключает ошибки (инженер случайно выбрал не ту дату)

### 13.4. Влияние на существующий функционал

| Функция | Влияние | Статус |
|---|---|---|
| Сезон (лето/зима) | Определяется автоматически от `dateStart` | ✅ OK |
| Проверка дубликатов (текущий месяц) | `dateStart` всегда в текущем месяце | ✅ OK |
| Автопривязка заявок (период) | `startDate <= NOW() <= deadline` | ✅ OK |
| Отчёты по дате визита | Дата = дата фактического визита | ✅ OK |
| Редактирование завершённого визита | Дата не меняется (заблокирована) | ✅ OK |

| Файл | Изменение |
|---|---|
| `server/src/routes/visits.ts` | POST `/api/visits` — игнорировать `dateStart` из body, всегда `NOW()` |
| `client/src/pages/VisitPage.tsx` | DatePicker `disabled={true}`, показать дату как текст |
