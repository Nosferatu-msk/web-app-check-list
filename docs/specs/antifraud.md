## 22. АНТИФРОД-СИСТЕМА ВЕРИФИКАЦИИ ФОТО

> Раздел добавлен 17.09.2026. Цель — снижение фрода и человеческого фактора при фотофиксации.

### 22.1. Общие принципы

Система верификации работает по принципу **серверного пост-анализа**: проверки выполняются асинхронно после загрузки фото и **не блокируют** работу инженера. Результаты отображаются только для ТМ и администратора на отдельной странице «Аналитика визитов».

**Уровни проверок:**
1. **Клиентский** (существующий): SHA-256 хеш — глобальная проверка дубликатов через API + жёсткий блок в рамках визита (HTTP 409)
2. **Серверный** (новый): pHash, timestamp, GPS, источник фото — асинхронный анализ после загрузки

**Ключевое правило:** инженер не видит проверок и не блокируется. Все дополнительные проверки — для ТМ и админа.

### 22.2. Модель данных

#### 22.2.1. Новые поля в таблице `photos`

| Поле | Тип | Описание |
|------|-----|----------|
| `phash` | TEXT, nullable | Перцептический хэш (64-бит, hex-строка) |
| `captured_at` | TIMESTAMP, nullable | Дата/время съёмки (от клиента) |
| `gps_lat` | FLOAT, nullable | Широта (опционально) |
| `gps_lng` | FLOAT, nullable | Долгота (опционально) |
| `photo_source` | TEXT, nullable | Источник: `camera`, `gallery`, `unknown` |
| `verification_status` | TEXT, default `'pending'` | Статус: `pending`, `clean`, `warning`, `suspicious` |
| `verification_details` | JSONB, nullable | Результаты проверок (массив объектов) |

**Миграция:** `add_verification_fields_to_photos`

#### 22.2.2. Новая таблица `visit_anomalies`

Универсальная таблица для хранения отклонений любого типа.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID, PK | Идентификатор |
| `visit_id` | UUID, FK → visits | Визит |
| `photo_id` | UUID, FK → photos, nullable | Связанное фото |
| `type` | TEXT | Тип отклонения (enum-like) |
| `severity` | TEXT | `critical` или `warning` |
| `details` | JSONB | Детали проверки |
| `status` | TEXT, default `'open'` | `open`, `confirmed`, `dismissed` |
| `reviewed_by` | UUID, FK → users, nullable | Кто проверил |
| `reviewed_at` | TIMESTAMP, nullable | Когда проверил |
| `created_at` | TIMESTAMP | Дата создания |

**Индексы:** `visit_id`, `type`, `status`, составной `(visit_id, status)`.

**Типы отклонений:**

| Значение `type` | Описание | Severity |
|---|---|---|
| `photo_phash_match` | Визуальное сходство с другим фото (pHash) | `critical` |
| `photo_timestamp_mismatch` | Фото сделано вне окна визита | `critical` |
| `photo_gps_mismatch` | GPS не совпадает с адресом объекта | `warning` |
| `photo_gallery_source` | Фото загружено из галереи (не камера) | `warning` |
| `photo_no_gps` | GPS-координаты недоступны | `warning` |

### 22.3. Серверные проверки

#### 22.3.1. pHash (перцептический хэш)

**Алгоритм:**
1. Сервер получает загруженное фото
2. Через `sharp` (уже в зависимостях): уменьшить до 32×32, grayscale
3. DCT (дискретное косинусное преобразование) → 64-битный хэш
4. Сохранить `phash` в БД
5. Найти последние 30 фото по тому же оборудованию (`task_equipment_item_id` или `task_id`)
6. Вычислить расстояние Хэмминга с каждым
7. Пороговые значения:
   - **0–4**: `critical` — фото визуально идентично (кроп, поворот, цветокоррекция)
   - **5–10**: `warning` — фото очень похоже (тот же ракурс)
   - **>10**: норма

**Хранение:** 8 байт на фото (hex-строка 16 символов). При 100 000 фото — ~1.6 МБ.

**Производительность:** DCT для 32×32 — микросекунды. Сравнение с 30 записями — мгновенно.

**Дополнительные проверки pHash:**
- **Cross-visit:** сравнение с фото того же equipmentTypeId из других визитов (за 30 дней)
- **Same-visit:** сравнение с фото того же moment внутри текущего визита
- **Cross-moment (ДО/ПОСЛЕ):** сравнение before-фото с after-фото того же оборудования в том же визите — обнаруживает, когда инженер загрузил одно фото как ДО и ПОСЛЕ (scope: `same_visit_cross_moment`)

**Эндпоинт сравнения:** `GET /api/photos/:id/duplicates` — поиск всех фото с похожим pHash по всей БД (без фильтра по оборудованию и moment), возвращает список дубликатов с метаданными.

#### 22.3.2. Timestamp

**Логика:**
1. Клиент передаёт `capturedAt` (Date.now() при съёмке через камеру, file.lastModified для галереи)
2. Сервер сравнивает с окном визита: `[visit.startedAt - 30мин, visit.completedAt + 5мин]`
3. Если `capturedAt` вне окна → `critical` отклонение `photo_timestamp_mismatch`

#### 22.3.3. GPS (опциональный)

**Логика:**
1. Клиент передаёт `gpsLat`/`gpsLng` если доступны (через `navigator.geolocation`)
2. Сервер вычисляет расстояние (Haversine formula) до координат адреса объекта
3. Порог: **500 метров**
4. Если расстояние > 500м → `warning` отклонение `photo_gps_mismatch`
5. Если GPS недоступен → `warning` отклонение `photo_no_gps` (информационное)

**Важно:** GPS — опциональный сигнал. Отсутствие GPS не блокирует загрузку.

#### 22.3.4. Источник фото

**Логика:**
1. Клиент определяет источник: `camera` (съёмка через камеру) или `gallery` (выбор из галереи)
2. Передаёт `photoSource` при загрузке
3. Если `gallery` → `warning` отклонение `photo_gallery_source`

### 22.4. Клиентская часть

#### 22.4.1. Передача дополнительных данных при загрузке

При загрузке фото клиент передаёт через FormData:
- `capturedAt` — ISO-строка (Date.now() или file.lastModified)
- `gpsLat`, `gpsLng` — координаты (если доступны)
- `photoSource` — `camera` | `gallery`

**Захват GPS:** при нажатии кнопки камеры запрашивать `navigator.geolocation.getCurrentPosition()` с таймаутом 5 секунд. Если не успело — отправить без координат.

**Определение источника:** если файл получен через `<input capture="environment">` — источник `camera`. Если через обычный `<input>` без `capture` — `gallery`.

#### 22.4.2. Инженер не видит проверок

Все проверки прозрачны для инженера. Никаких бейджей, предупреждений или блокировок на стороне инженера (кроме существующей проверки SHA-256 дубликатов).

### 22.5. API-контракты

#### 22.5.1. Аналитика визитов (ТМ и Админ)

| Метод | Путь | Описание | Роль |
|-------|------|----------|------|
| `GET` | `/api/analytics/visits` | Список визитов с отклонениями (пагинация, фильтры) | `tm`, `admin` |
| `GET` | `/api/analytics/visits/:id` | Детали визита с отклонениями | `tm`, `admin` |
| `PATCH` | `/api/analytics/anomalies/:id` | Обновить статус отклонения | `tm`, `admin` |
| `PATCH` | `/api/analytics/anomalies/batch` | Массовое обновление статусов | `tm`, `admin` |
| `POST` | `/api/analytics/visits/:id/reshoot` | Запросить пересъёмку (удалить фото) | `tm`, `admin` |
| `POST` | `/api/analytics/visits/:id/confirm` | Подтвердить визит | `tm`, `admin` |

**Параметры `GET /api/analytics/visits`:**
- `period` — период (7d, 30d, 90d, custom)
- `engineerId` — фильтр по инженеру (ТМ видит только своих)
- `type` — тип отклонения
- `severity` — критичность (critical, warning)
- `status` — статус отклонения (open, confirmed, dismissed)
- `search` — поиск по инженеру или адресу
- `page`, `pageSize` — пагинация

**Ответ `GET /api/analytics/visits`:**
```json
{
  "data": [
    {
      "visitId": "uuid",
      "visitCode": "RU/77/423",
      "date": "2026-09-15",
      "engineer": { "id": "uuid", "name": "Петров А.С." },
      "address": { "id": "uuid", "fullAddress": "ТЦ «Аврора», ул. Ленина 42" },
      "visitStatus": "completed",
      "anomalyCount": { "critical": 2, "warning": 1 },
      "reviewStatus": "open"
    }
  ],
  "total": 7,
  "summary": {
    "totalVisits": 89,
    "visitsWithAnomalies": 7,
    "criticalCount": 7,
    "warningCount": 12
  }
}
```

#### 22.5.2. Запрос пересъёмки

**`POST /api/analytics/visits/:id/reshoot`**

Тело запроса:
```json
{
  "anomalyIds": ["uuid1", "uuid2"]
}
```

Логика:
1. Найти указанные отклонения
2. Удалить связанные фото (по `photo_id`)
3. Обновить статусы задач: если в задаче нет фото → статус `not_started`
4. Если все задачи визита без фото или `not_started` → статус визита → `in_progress`
5. Если визит влияет на заявку (через `visit_requests`) → обновить статус заявки
6. Пометить отклонения как `confirmed` (обработаны)
7. Записать в `audit_log`

#### 22.5.3. Подтверждение визита

**`POST /api/analytics/visits/:id/confirm`**

Логика:
1. Пометить все `open` отклонения визита как `dismissed`
2. Записать в `audit_log`

### 22.6. Страница «Аналитика визитов»

#### 22.6.1. Навигация

- **ТМ:** пункт «Аналитика» в нижней навигации (между «Визиты» и «Отчёты»)
- **Админ:** пункт «Аналитика визитов» в боковом меню (группа «Система»)

#### 22.6.2. Scope данных

- **ТМ:** только визиты своих инженеров (через `tm_engineers`)
- **Админ:** все визиты

#### 22.6.3. Список визитов

**Элементы:**
- KPI-карточки: всего визитов, критические, предупреждения, без отклонений
- Фильтры: поиск (инженер/адрес), период, инженер, тип отклонения, статус
- Карточки визитов с левой цветной полоской (красная = critical, жёлтая = warning), бейджами счётчиков отклонений
- Код объекта (тег), дата, ФИО инженера

#### 22.6.4. Детали визита

**Элементы:**
- Заголовок: код визита, адрес, инженер, дата, статус
- Чекбоксы для выбора отклонений + «Выбрать все»
- Карточки отклонений с превью фото, деталями проверок, кнопкой «Сравнить»
- Действия: «Запросить пересъёмку» (активна при выбранных отклонениях), «Подтвердить визит»

#### 22.6.5. Модальное окно сравнения дубликатов

При клике «Сравнение» в карточке отклонения pHash — модальное окно `DuplicatePhotosModal` со списком всех дубликатов (фото с pHash-расстоянием ≤ 10 за последние 30 дней). Для каждого дубликата отображаются: миниатюра фото, код объекта, тип оборудования, ФИО инженера, дата визита, момент (ДО/ПОСЛЕ), процент сходства и расстояние Хэмминга. Текущее фото выделено. Консистентность: из любого визита при открытии модалки показываются одни и те же дубликаты. API: `GET /api/photos/:id/duplicates`.

#### 22.6.6. Адаптация

- **Десктоп:** `maxWidth: 1400px` (единый стандарт)
- **Мобильный:** chip-фильтры с горизонтальной прокруткой, компактные карточки, кнопки действий на всю ширину

### 22.7. Бизнес-логика: запрос пересъёмки

**Сценарий:**
1. ТМ/Админ выбирает отклонения (конкретные или все)
2. Нажимает «Запросить пересъёмку»
3. Сервер:
   - Удаляет аномальные фото (физически + из БД)
   - Проверяет задачи: если в задаче нет фото → статус задачи `not_started`
   - Проверяет визит: если есть задачи без фото → статус визита `in_progress`
   - Проверяет заявки: если визит связан с заявкой через `visit_requests` → статус заявки `awaiting_assignment` (или предыдущий открытый статус)
   - Помечает отклонения как `confirmed`
   - Записывает в `audit_log`: кто, когда, какие фото удалены

### 22.8. Расширяемость

Таблица `visit_anomalies` спроектирована для добавления новых типов проверок без изменения схемы:
- Новые проверки = новые значения `type`
- Детали хранятся в JSONB `details`
- Страница аналитики автоматически отображает новые типы

**Планируемые будущие проверки:**
- Сравнение pHash «ДО» vs «ПОСЛЕ» (если идентичны — отклонение)
- Анализ мета-данных файла (разрешение исходника, camera vs gallery по EXIF)
- ELA (Error Level Analysis) — обнаружение повторного сжатия
