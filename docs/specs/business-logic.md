### 6.1. Создание визита

1. Инженер выбирает адрес из справочника (поиск с автодополнением)
2. Поля «Дата начала» и «Время начала» заполняются автоматически (текущие дата/время)
3. Поле «Сезон» вычисляется автоматически по дате:
   - Апрель (1+) – Октябрь (31) → «Лето»
   - Ноябрь (1) – Март (31) → «Зима»
4. При изменении даты — пересчёт сезона с подтверждением пользователя

### 6.2. Управление задачами

1. Кнопка «+ Добавить оборудование» → модальное окно:
   - Вид оборудования (dropdown из справочника)
   - Тип помещения (dropdown из справочника)
   - Местоположение / Назначение (текстовое поле, необязательно)
2. Новая задача получает статус «Не начато»
3. Клик на задачу → переход на страницу параметров (4.x)
4. Статус задачи меняется на «В работе» при первом редактировании
5. Статус «Выполнено» — после сохранения параметров с заключением

### 6.3. Условная обязательность

- Поле «Дополнительные рекомендации» обязательно ТОЛЬКО при:
  - Заключение = «Исправно, есть замечания» ИЛИ
  - Заключение = «Неисправно»
- Валидация при сохранении задачи

### 6.4. Фотофиксация

1. Количество фото определяется типом оборудования:
   - `photos_required = 2` (СС, МСС, VRV, вентиляция): фото ДО + фото ПОСЛЕ
   - `photos_required = 1` (РЩ, счётчики, сети): только фото ДО
2. Для оборудования с 1 фото — поле «Фото ПОСЛЕ» скрыто
3. Предупреждение 152-ФЗ — при первом фото в помещениях с типами:
   - Клиентский зал, Зона самообслуживания, Касса, Санузел, Крыльцо
4. Фото сохраняются в файловое хранилище, метаданные — в БД

### 6.5. Завершение визита

1. Кнопка «Завершить визит» активна при наличии ≥1 выполненной задачи
2. При завершении:
   - Заполняется `time_end`
   - Статус визита → `completed`
   - Генерируется PDF-отчёт
   - Формируется ZIP-архив (PDF + фото + Excel-таблица оборудования)
3. Переход на страницу отправки отчёта (Страница 6)

### 6.5.1. Валидация обязательных полей задач при завершении визита

При вызове `POST /api/visits/:id/complete` сервер выполняет проверку обязательных параметров для всех задач визита со статусом `completed`. Конфигурация обязательных параметров (`REQUIRED_PARAMS_CONFIG`) вынесена в `shared/types/params.ts` и используется как сервером, так и клиентом — единый источник истины.

**Обязательные поля по типам оборудования (из `REQUIRED_PARAMS_CONFIG`):**

| Код оборудования | Обязательные поля | Тип значения |
|------------------|-------------------|--------------|
| `schetchik_electroshc` | `readings` | число |
| `schetchik_hvs` | `readings` | число |
| `schetchik_gvs` | `readings` | число |
| `meter_gas` | `readings` | число |
| `splitvn`, `mssvn`, `vrv_vn` | `room_temperature` | число (°C) |
| `splitnar`, `mssnar`, `vrv_nar` | — (только общие обязательные) | — |
| `teplozavesa`, `pritochnaya`, `pritochno-vytyzhnaya`, `vytyzhnaya` | `temperature_before`, `temperature_after` | число (°C) |
| `boiler_gas`, `boiler_liquid`, `boiler_solid`, `boiler_elec` | согласно `REQUIRED_PARAMS_CONFIG` | — |
| `ibp` | согласно `REQUIRED_PARAMS_CONFIG` | — |
| `cond_mobile` | согласно `REQUIRED_PARAMS_CONFIG` | — |

**Важно:** Поля `brand`, `model`, `serialNumber` **НЕ входят** в `REQUIRED_PARAMS_CONFIG`, так как хранятся в отдельных полях задачи (не в JSONB `parameters`). Их обязательность проверяется:
- **Клиентская валидация:** `VisitPage.tsx` (handleComplete) — проверяет brand/model/serialNumber для всех типов оборудования (кроме `group_climate`)
- **Серверная валидация:** `visits.ts` (POST /:id/complete) — через `validateTaskFields` (проверка формата) + клиентская проверка обязательности

**Клиентская валидация (`handleComplete`):** перед вызовом API клиент проверяет:
1. **ВСЕ** required параметры из `REQUIRED_PARAMS_CONFIG` (readings, temperature и т.д.)
2. **brand/model/serialNumber** для всех типов оборудования (кроме `group_climate`)
3. Задачи со статусом `not_started` — они блокируют завершение визита

**Ответ при ошибке валидации (HTTP 422):**
```json
{
  "error": "Не заполнены обязательные поля задач",
  "details": [
    {
      "taskId": "uuid",
      "taskNumber": 2,
      "equipmentName": "Прибор учёта э/э",
      "missingFields": ["readings"]
    }
  ]
}
```

### 6.5.2. Антифрод-проверка текстовых данных

Серверная валидация текстовых полей задач выполняется при создании задачи (`POST /api/visits/:visitId/tasks`), сохранении задачи (`PUT /api/visits/:visitId/tasks/:id`) и при завершении визита (`POST /api/visits/:id/complete`).

**Правила:**

1. **Мусорные данные:** значения, состоящие исключительно из пробелов, точек, спецсимволов или их комбинаций, отклоняются.
   - Примеры отклонённых значений: `"...."`, `"   "`, `"!!!"`, `"@#$%"`, `"- - -"`
   - Проверка: регулярное выражение `^[\s\.\,\;\:\!\@\#\$\%\^\&\*\(\)\-\+\=\<\>\?\~]+$`
   - Применяется к полям: `brand`, `model`, `serialNumber`, `additionalRecommendations`

2. **Запрет старта со спецсимвола:** поля `brand`, `model`, `serialNumber` не могут начинаться со спецсимвола или пробела.
   - Первый символ должен быть буквой (в т.ч. кириллицей) или цифрой
   - Проверка: регулярное выражение `/^[\p{L}\p{N}]/u` (Unicode)

3. **Блок-лист placeholder-значений:** поля `brand`, `model`, `serialNumber` не могут содержать слова-заглушки и одиночные спецсимволы.
   - Блок-лист слов: `нет`, `нет данных`, `неизвестно`, `не заполнено`, `отсутствует`, `нет информации`, `н/д`, `n/a`, `null`, `none`, `unknown`, `no data`, `not filled`
   - Блок-лист спецсимволов: `.` (точка), `-` (дефис), `_` (подчёркивание), `/`, `\` — одиночные или повторяющиеся
   - Проверка регистронезависимая, с нормализацией `_`, `-`, пробелов → единый пробел
   - Проверяется вхождение подстроки: `нет123`, `Нет_2222`, `N/A` — все отклоняются
   - Функция: `containsPlaceholder(value)` в `server/src/utils/validation.ts`

4. **Формат модели:** поле `model` должно содержать и буквы, и цифры одновременно.
   - Примеры корректных: `Меркурий 230`, `SC-125A`, `MXM80RV`
   - Примеры некорректных: `Кондиционер` (только буквы), `12345` (только цифры)
   - Функция: `isModelFormatValid(value)` в `server/src/utils/validation.ts`

5. **Детектор копипаста:** все три поля (`brand`, `model`, `serialNumber`) не могут быть одинаковыми.
   - Сравнение регистронезависимое, с trim()
   - Пример отклонённого: `Меркурий / Меркурий / Меркурий`
   - Функция: `areFieldsIdentical(brand, model, serialNumber)` в `server/src/utils/validation.ts`

6. **Ответ при ошибке (HTTP 422):**
```json
{
  "error": "Некорректное значение поля",
  "field": "model",
  "reason": "Модель должна содержать и буквы, и цифры (например, Меркурий 230, SC-125A)"
}
```

7. **Клиентская валидация:** те же правила применяются мгновенно в форме добавления оборудования на странице визита (VisitPage.tsx). Поля `brand`, `model`, `serialNumber` имеют cross-field валидаторы с `dependencies` — при изменении любого поля перепроверяются все три.

### 6.5.3. Валидация показаний приборов учёта

Поле `readings` (в `parameters` задач-счётчиков) проходит строгую числовую валидацию.

**Правила валидации:**

| Правило | Описание | Пример |
|---------|----------|--------|
| Числовой формат | Допускаются цифры, разделители «.» или «,» | `12345.67`, `12345,67` |
| Целая часть | Не более 9 цифр | `999999999` — ОК, `1234567890` — ошибка |
| Дробная часть | Не более 4 цифр | `1.2345` — ОК, `1.23456` — ошибка |
| Запрет лидирующего нуля | Не может начинаться с `0` (кроме `0` и `0.xxx`) | `0123` — ошибка, `0.5` — ОК, `0` — ОК |
| Нормализация | Запятая заменяется на точку перед сохранением | `12345,67` → `12345.67` |
| Неотрицательность | Отрицательные значения запрещены | `-100` — ошибка |

**Ответ при ошибке (HTTP 422):**
```json
{
  "error": "Некорректные показания прибора учёта",
  "field": "readings",
  "reason": "Целая часть не должна начинаться с нуля",
  "value": "012345"
}
```

### 6.5.4. Клиентская валидация числовых полей

На стороне клиента (React-компоненты формы задачи) реализована валидация числовых полей в реальном времени:

1. **Приём ввода:** числовые поля (`readings`, `room_temperature`, `temperature_before`, `temperature_after`, `cooling_capacity_kw`) принимают как точку, так и запятую.
2. **Нормализация:** при вводе запятая автоматически заменяется на точку (через обработчик `onChange`).
3. **Ограничения:** целая часть ≤ 9 цифр, дробная часть ≤ 4 цифры — при превышении ввод блокируется.
4. **Визуальная обратная связь:** при некорректном значении поле подсвечивается красной рамкой, отображается tooltip с описанием ограничения.
5. **Проверка при завершении визита:** перед вызовом `POST /api/visits/:id/complete` клиент выполняет обход всех задач и проверяет наличие незаполненных обязательных полей. При обнаружении — отображается модальное окно со списком ошибок и кнопками перехода к соответствующим задачам.

### 6.6. Маркировка фотографий

**Шаблон имени файла:**
```
{№}_{equipment_code}_{room_code}_{moment}.jpg
```

- `{№}` — порядковый номер задачи в визите (01, 02, 03...)
- `{equipment_code}` — код типа оборудования из справочника
- `{room_code}` — код типа помещения из справочника
- `{moment}` — `before` или `after`

**Примеры:**
- `01_rsch_server_before.jpg`
- `02_splitvn_server_before.jpg`
- `02_splitvn_server_after.jpg`

### 6.7. Формирование PDF-отчёта

**Структура документа** (согласно `Шаблон акта.md`):

1. Заголовок: «Акты выполненных работ»
2. Общий блок:
   - Адрес объекта
   - Дата проведения
   - Время начала / окончания
   - Сезон
   - Инженер (ФИО из профиля)
   - **Номер договора** (если есть привязка к договору)
   - **Номера заявок** (список номеров связанных заявок из `visit_requests` и `importedRequests`)
   - **Статус визита** (человекочитаемый: «Выполнено», «Отправлено» и т.д.)
3. Для каждой задачи:
   - Номер и вид оборудования + местоположение
   - **Brand / model / serialNumber** — отображаются для индивидуальных задач (ранее только для групповых)
   - Местоположение (тип помещения)
   - Контролируемые параметры (список)
   - Фотофиксация (встроенные изображения)
   - **Подсветка некорректных полей:** если `brand`, `model` или `serialNumber` содержат некорректные данные (антифрод-проверка), поле выделяется красным фоном (`#fff1f0`)
   - **pHash-предупреждения:** под фото с отклонением `photo_phash_match` — красная пометка «Дубликат»
   - Заключение
   - Рекомендации (выбранные + дополнительные)
4. Подпись инженера

**Исключение виртуальных визитов:** визиты без `userId` (виртуальные, статус `awaiting_assignment`) исключены из отчётов — они не содержат реальных данных работ.

**Технические требования:**
- Формат: PDF/A-1b
- Страница: A4
- Шрифт: Arial / Roboto, 11pt
- Фото: 150 DPI, встроенные в PDF
- Имя файла: `OTCHET_{street}_{house}_{date}.pdf`

### 6.7.1. Отчёт по заявкам (сводный отчёт по договору)

**Endpoint:** `POST /api/reports/requests-generate`

**Назначение:** Формирование PDF-отчёта по всем заявкам договора за указанный период. Используется территориальными менеджерами и администраторами для анализа выполнения заявок.

**Структура PDF-документа:**

**Лист 1 — Титульный:**
- Название: «ОТЧЁТ ПО ЗАЯВКАМ»
- Период: дата создания или дата закрытия заявок (настраивается)
- Дата формирования: дд.мм.гггг
- Сформировал: ФИО пользователя, роль

**Лист 2 — Сводные KPI:**
8 карточек с показателями:
1. **Общее количество заявок** за период
2. **Завершены** — заявки со статусом «Завершена»
3. **В работе** — заявки со статусом «В работе»
4. **Не начаты** — заявки без визитов или со статусом «Не начата»
5. **SLA** — % выполнения заявок в срок: `(закрытые в срок / общее количество заявок) × 100%`
6. **Количество совершённых визитов** — визиты в статусах «Завершён», «Отправлен», «Откорректирован ТМ», «В работе»
7. **Количество выполненных задач** — задачи с заполненным `conclusion` (ok, ok_with_notes, faulty)
8. **Количество обслуженных объектов** — уникальные адреса визитов

**Лист 3.n — Детализация по заявкам** (по одному листу на заявку с визитами):
- Заголовок: «Заявка: {номер} ({адрес})»
- Для каждого визита:
  - Дата визита, инженер (ФИО), статус (цвет: зелёный/оранжевый/красный)
  - Количество задач, количество замечаний
  - Задачи:
    - Наименование вида оборудования + помещение
    - Изготовитель, модель, серийный номер
    - Для климатического оборудования (group_climate) — таблица единиц оборудования (№, вид, изготовитель, модель, сер.№, статус)
    - Параметры: все поля из `task.parameters`, незаполненные → «не заполнено» красным
    - Фотофиксация: превью + имя файла; дубликат (антифрод) → красная рамка + «Дубликат»
    - Заключение (цветной бейдж)
    - Рекомендации (список или «Нет»)

**Последний лист — Заявки без визитов** (одна таблица):
| № | Номер заявки | Адрес | Статус |
|---|---|---|---|
| 1 | IS0140282788 | RU/77/561 | Не начата |

**Порядок листов:** завершённые заявки → в работе → не начатые (таблица).

**Ключевые бизнес-правила:**

1. **Заявка ИСЖ объекта** (`equipmentTypeCode = 'iszh_object'`) означает обслуживание ВСЕГО оборудования объекта. Статус определяется по агрегированному статусу всех визитов (через `visit_requests`), без проверки `hasMatchingTask`.

2. **Фильтрация ТМ:** ТМ видит все заявки своего договора (не только назначенные инженерам). ТМ может создавать визиты самостоятельно.

3. **Расчёт SLA:** `(заявки, закрытые в срок / общее количество заявок) × 100%`. Незавершённые заявки уменьшают SLA.

4. **Дубликаты фото:** проверяются через `VisitAnomaly` (типы: `duplicate` и `photo_phash_match` с `severity = 'critical'`).

5. **Заявки без визитов** собираются в одну таблицу (не отдельные листы) для экономии места.

**Технические требования:**
- Формат: PDF/A-1b
- Страница: A4
- Шрифт: Arial / Roboto, 11pt
- Фото: 150 DPI, встроенные в JPEG, конвертируются через `sharp`
- Упрощённый режим: при >1000 фото превью заменяются текстовыми ссылками
- Имя файла: `Отчет-по-заявкам-{timestamp}.pdf`

**Реализация:**
- Генератор HTML: `server/src/services/requestsReport.ts`
- Endpoint: `server/src/routes/reports.ts` — `POST /api/reports/requests-generate`
- Клиент: `client/src/api/client.ts` — `generateRequestsReport()`
- UI: `client/src/pages/SummaryReportPage.tsx` — режим «По договору и периоду»

### 6.8. Формирование ZIP-архива

```
OTCHET_{street}_{house}_{date}.zip
├── OTCHET_{street}_{house}_{date}.pdf
├── OTCHET_{street}_{house}_{date}.xlsx
└── Photos/
    ├── 01_rsch_server_before.jpg
    ├── 02_splitvn_server_before.jpg
    ├── 02_splitvn_server_after.jpg
    └── ...
```

**Excel-таблица оборудования** (`.xlsx`):

| Колонка | Описание |
|---------|----------|
| Код объекта | Код объекта из справочника адресов |
| Вид оборудования | Наименование типа оборудования |
| Серийный номер | Серийный номер единицы оборудования |
| Изготовитель | Марка (бренд) оборудования |
| Модель | Модель оборудования |
| Показания | Показания прибора учёта (только для `schetchik_electroshc`, `schetchik_gvs`, `schetchik_hvs`) |

- Для групповых задач (климатическое оборудование) каждая единица — отдельная строка.
- Для индивидуальных задач каждая задача — одна строка.
- Колонка «Показания» заполняется только для счётчиков; для остальных типов — пустая.
- Библиотека генерации: `exceljs`.

### 6.9. Отправка email

- **Протокол:** SMTP / SMTPS
- **Кому:** `customer_email` из справочника адресов
- **Тема:** `Акт выполненных работ: {full_address} от {dd.mm.yyyy}`
- **Тело письма:** Шаблон с краткой сводкой (адрес, дата, кол-во задач)
- **Вложение:** ZIP-архив (до 25 МБ)
- **Резерв:** При недоступности email — кнопка «Скачать»

### 6.10. Офлайн-режим

1. **Service Worker** кэширует:
   - Статические ресурсы (HTML, CSS, JS, иконки)
   - API-ответы справочников
2. **IndexedDB** хранит:
   - Текущие визиты и задачи
   - Очередь изменений (pending mutations)
   - Загруженные фото (до синхронизации)
3. **Автосохранение:** каждые 30 секунд (хук `useAutoSave`)
4. **Автосинхронизация:** при появлении сети — отправка накопленных данных
5. **Предупреждение:** при закрытии вкладки с несохранёнными данными (`beforeunload`)

**Обновление PWA:**
- `registerType: 'prompt'` — при обнаружении новой версии показывается баннер «Доступна новая версия приложения» с кнопкой «Обновить»
- Хук `usePWAUpdate` + компонент `PWAUpdateBanner` — отслеживают обновление Service Worker

**Автообновление данных:**
- При событии `visibilitychange` (возврат на вкладку) запускается синхронизация данных
- Список визитов (`VisitListPage`) перезагружается при каждом возврате на вкладку
- Запросы оборудования объекта (`/refs/object-equipment`) включают `_t=timestamp` для обхода кэша Workbox — данные всегда загружаются с сервера при открытии модального окна

### 6.11. Сброс задачи

- Кнопка «Сбросить задачу» очищает ТОЛЬКО текущую задачу
- Сбрасываются: параметры, рекомендации, фото, заключение
- Статус задачи → «Не начато»
- Остальные задачи визита не затрагиваются

### 6.12. Офлайн-режим

**Локальное хранилище (Dexie / IndexedDB):**
- Таблицы: visits, tasks, photos, syncQueue, cachedRefs
- Каждая запись имеет флаг `dirty` (требует синхронизации)
- Фото хранятся как Blob

**Синхронизация:**
1. При восстановлении связи — `processSyncQueue()` обрабатывает очередь
2. Каждая операция воспроизводится на сервере (create → POST, update → PUT, delete → DELETE)
3. При успехе — запись удаляется из очереди, `dirty = false`
4. При ошибке — retry до 5 раз, затем исключение из очереди
5. После push — `pullVisitsFromServer()` обновляет данные с сервера

**Стратегии кэширования (Workbox):**
| Ресурс | Стратегия | TTL |
|--------|-----------|-----|
| Изображения | CacheFirst | 30 дней |
| /api/refs/* | StaleWhileRevalidate | 1 день |
| /api/* (прочее) | NetworkFirst (timeout 3с) | 7 дней |
