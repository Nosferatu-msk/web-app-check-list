## 15. ПРИНЯТЫЕ РЕШЕНИЯ (уточнения к ТЗ)

> Ниже зафиксированы решения по вопросам, отсутствующим в исходном техническом задании.

### 15.1. Технологический стек ✅
- **Frontend:** React 18+ / TypeScript, Zustand, Ant Design Mobile / Vant, Workbox
- **Backend:** Node.js / Express, Prisma ORM, Nodemailer
- **Генерация ZIP:** JSZip (на клиенте); Excel-таблица — `exceljs`

### 15.2. Источник данных инженера ✅
ФИО инженера **вводятся вручную** при создании визита (поле в форме визита). В последующих визитах поле автозаполняется последним использованным значением.

### 15.3. Время окончания визита ✅
`time_end` заполняется **автоматически** при нажатии «Завершить визит» (текущее серверное время).

### 15.4. История визитов ✅
Инженер видит **список своих визитов** с возможностью:
- Просмотра деталей визита
- **Повторного скачивания** PDF + ZIP отчёта (ZIP содержит PDF, фото и Excel-таблицу оборудования)
- Фильтрации по дате и статусу

### 15.5. Удаление визитов ✅
Инженер может удалить визит в **любом статусе** (в работе, завершён, отправлен). При удалении удаляются все связанные задачи и фото.

**Раздельные виртуальные визиты при удалении:** если удаляемый визит связан с заявками через `visit_requests`, система группирует заявки по типу оборудования (`equipmentTypeId`). Для каждой группы создаётся **отдельный** виртуальный визит (soft-deleted), связанный только с заявками соответствующего типа оборудования. Это предотвращает смешивание типов оборудования в одном виртуальном визите и обеспечивает корректный пересчёт статусов заявок.

### 15.6. Восстановление пароля ✅
Механизм **сброса по email**: пользователь запрашивает сброс → получает письмо со ссылкой → устанавливает новый пароль. Ссылка действительна 1 час.

### 15.7. SMTP-конфигурация ✅
На этапе разработки — **Ethereal Email** (тестовый SMTP). В production — будет настроен реальный SMTP-сервер (конфигурация через .env).

### 15.8. Хранилище фотографий ✅
**Локальная файловая система** сервера (директория `uploads/`). В дальнейшем планируется миграция на S3-совместимое хранилище. Максимальный размер фото: 10 МБ, максимальное разрешение: 4032×3024 (авто-ресайз при загрузке).

### 15.9. Нумерация задач в фото ✅
Порядковый номер `{№}` — номер задачи в рамках визита. При удалении задачи **номера пересчитываются** для оставшихся задач.

### 15.10. Редактирование завершённого визита ✅
Завершённый визит **можно редактировать**. При повторном сохранении PDF перегенерируется автоматически.

### 15.11. Конфликты синхронизации ✅
Стратегия **«последняя запись побеждает»** (last-write-wins) с timestamp. При конфликте справочников — приоритет у серверной версии.

### 15.12. Уведомления ✅
Push-уведомления **не требуются**. Статусы отображаются в интерфейсе.

### 15.13. Логирование и аудит ✅
**Полный журнал аудита** — таблица `audit_log`:
- id, user_id, action, entity_type, entity_id, old_value, new_value, created_at
- Логируются: вход/выход, создание/редактирование/удаление визитов, задач, справочников

### 15.14. Резервное копирование ✅
Ежедневный бэкап PostgreSQL (pg_dump) + архив директории uploads. Срок хранения: 30 дней.

### 15.15. Домен и SSL ✅
- **Домен:** checkonout.ru (привязан к IP 31.128.38.54)
- **SSL:** Let's Encrypt, сертификат получен через Certbot, автообновление
- **HTTPS:** Nginx слушает 443, HTTP (80) → редирект 301 на HTTPS
- **Хостинг:** Beget VPS, 14 ГБ диск, 1.9 ГБ RAM + 2 ГБ swap

### 15.16. Отправка по email — исключена из UI ✅
Функционал отправки отчёта по email **удалён из пользовательского интерфейса** по решению заказчика. Вместо него реализовано **скачивание ZIP-архива** (PDF + фото + Excel-таблица оборудования) на устройство инженера. Серверный эндпоинт `POST /api/reports/:id/report/send` сохранён для будущего использования.

### 15.17. Формат PDF ✅
Генерируется **стандартный PDF** через Puppeteer (HTML → PDF). Формат PDF/A-1b (из ТЗ) не реализован — Puppeteer не поддерживает PDF/A из коробки. Для долгосрочного архивирования достаточно обычного PDF с встроенными шрифтами.

### 15.18. Источник фото — камера и галерея ✅
На экране фотофиксации доступны **две кнопки**: «Камера» (с `capture="environment"`) и «Галерея» (без `capture`). Пользователь сам выбирает способ получения изображения.

### 15.19. Предупреждение 152-ФЗ — при каждом входе ✅
Предупреждение показывается **каждый раз** при входе на экран фотофиксации в клиентской зоне (без ограничения по sessionStorage).

### 15.20. Автосохранение параметров при переходе к фото ✅
При нажатии кнопки «Фото» в TaskPage параметры **автоматически сохраняются** на сервер перед переходом к PhotoPage. Это предотвращает потерю данных, если пользователь не нажал «Сохранить» явно.

### 15.21. Тема оформления — стандартная светлая ✅
Используется стандартная светлая тема Ant Design (без `darkAlgorithm`). Оптимальна для чтения на мобильных устройствах при любом освещении.

### 15.22. Серверное обновление задач — частичное ✅
Серверный эндпоинт `PUT /tasks/:id` обновляет **только переданные поля** (проверка `!== undefined`). Это предотвращает случайное обнуление `conclusion` и `parameters` при обновлении статуса из PhotoPage.

### 15.23. Адаптивный дизайн админ-панели ✅
Админ-панель адаптирована под все размеры экранов:
- **Мобильные (< 768px):** навигация через Drawer (гамбургер-меню), таблицы с горизонтальной прокруткой, формы на всю ширину, модальные окна адаптированы
- **Планшеты (768–1199px):** боковое меню (Sider), адаптивный контент
- **Десктоп (≥ 1200px):** полноценный Sider, контент с максимальной шириной

Поддерживаемые устройства: iPhone 13–17, Samsung Galaxy, Xiaomi, POCO, OnePlus, iPad, ПК (1920×1080+).

### 15.24. Роль «Территориальный менеджер» (ТМ) ✅
- ТМ видит визиты только своих инженеров (через таблицу tm_engineers + команду tm_team_member)
- ТМ может создавать визиты с назначением на инженера (статус planned)
- **Поле «Инженер» при создании визита** — `<Select>` с выпадающим списком инженеров из привязок ТМ (включая команду). Первая опция: «Без инженера (визит под собой)» — визит создаётся с `userId` самого ТМ
- **Автоподстановка `contractId`** — при создании визита ТМ автоматически определяется договор из `tm_objects` по адресу (аналогично инженеру)
- ТМ может переназначать визиты между своими инженерами
- ТМ может редактировать, отправлять отчёты, удалять визиты своих инженеров
- ТМ не имеет доступа к справочникам (админ-панели)
- Soft delete: визит помечается is_deleted=true, скрывается из списка

### 15.25. Новые статусы визитов ✅
- planned — ТМ назначил визит инженеру
- not_started — Инженер создал визит, работы не начаты
- sent_by_engineer — Отправлено инженером
- sent_by_tm — Отправлено ТМ
- corrected_by_tm — ТМ внёс корректировки в завершённый визит

### 15.26. Офлайн-режим
- Dexie.js (IndexedDB) для локального хранения визитов, задач, фото
- Очередь мутаций (syncQueue) с автоматической синхронизацией при reconnect
- Workbox NetworkFirst для API (timeout 3с) — кэширует ответы для офлайн-чтения
- Фото хранятся как Blob в IndexedDB до загрузки на сервер

### 15.27. Массовый импорт CSV
- 7 типов импорта: адреса, оборудование, помещения, рекомендации, пользователи, привязки ТМ
- Автоопределение разделителя (`,` / `;`)
- Обработка дубликатов (пропуск), отчёты об ошибках
- Временный пароль `Welcome2026!` для импортированных пользователей

### 15.28. Привязка «Объект-Оборудование»
- Таблица object_equipment: конкретные единицы оборудования на объекте
- Поле object_code в addresses (формат RU/77/001)
- Поле `room_type_code` — **опционально** (nullable). Оборудование может быть привязано к объекту без указания помещения
- При импорте object-equipment (CSV/XLSX) поле room_type не обязательно — пустое значение → `room_type_code = NULL`
- При создании визита таблица работ **пустая** — оборудование добавляется через модальное окно
- Модальное окно «Добавление оборудования» имеет две вкладки:
  - «Уровень помещения» — выбор помещения, добавление оборудования из него, перенос из других помещений и с уровня объекта
  - «Добавить новое» — форма для добавления оборудования вручную (не из привязки)
- Для оборудования без помещения отображается метка «⚠️ Помещение не указано»
- При выборе такого оборудования появляется inline Select для выбора помещения из справочника
- Кнопка «Добавить» неактивна, пока для всех отмеченных единиц без помещения не выбран тип
- При добавлении: вызов `PATCH /api/refs/object-equipment/:id/room` сохраняет помещение в `object_equipment` (room_confirmed_at, room_confirmed_by)
- Поле `object_equipment_id` в таблице `tasks` связывает задачу с конкретной записью привязки (для фильтрации дубликатов)
- При повторном открытии модалки уже добавленные единицы скрыты из списка
- Если всё оборудование добавлено — вкладка показывает «Всё оборудование уже добавлено в визит»
- Для нового (несохранённого) визита — автосохранение черновика при первом нажатии «Добавить оборудование»
- Поддержка импорта из Excel (.xlsx) через библиотеку exceljs

### 15.29. Soft delete адресов ✅
- Поле `is_deleted` в таблице `addresses` (default: false)
- `DELETE /api/admin/addresses/:id` устанавливает `is_deleted = true` вместо физического удаления
- Все списки и поиск адресов фильтруют `is_deleted = false` по умолчанию
- Параметр `?include_deleted=true` показывает удалённые адреса
- Исторические визиты и связанные записи сохраняются

### 15.30. Профиль ТМ ✅
- ТМ видит **закреплённые объекты** (из `tm_objects`) вместо избранных
- `GET /api/profile/objects` — возвращает список объектов с индикатором неисправностей
- Список объектов содержит **клиентскую пагинацию** (по 10/20/50 на странице) с отображением «1–10 из N» и счётчиком общего количества
- ТМ может **создавать инженеров** с автоматической привязкой: `POST /api/profile/engineers`
- Новый инженер получает временный пароль `Welcome2026!` на email

### 15.31. Аутентификация — специализация ✅
- `/auth/login` и `/auth/me` возвращают поля `specializationVik`, `specializationIszh`, `specializationGpm`, `specializationDgu`, `specializationIbp`, `mustChangePassword`
- `trust proxy = 1` для корректной работы rate-limiter за nginx

### 15.32. Избранное — совместимость форматов ✅
- `POST /profile/favorites` принимает `{ addressId }` (UUID) или `{ objectCode }` (строка)
- Сервер резолвит `objectCode` из `addresses` при передаче `addressId`
- `DELETE /profile/favorites/*` — wildcard-маршрут для object_code со слешами (RU/77/001)

### 15.33. Новые виды оборудования (ВиК) и специализация ✅
- Добавлены 4 новых вида оборудования: `teplozavesa` (тепловая завеса), `pritochnaya` (приточная установка), `pritochno-vytyzhnaya` (приточно-вытяжная установка), `vytyzhnaya` (вытяжная установка)
- Все новые виды: `photos_required=2`, `specialization_req=vik`
- Вид `vent` (вентиляционная установка) деактивирован (`is_active=false`) — заменён новыми видами
- Итого в справочнике: 17 записей, 16 активных
- В таблицу `equipment_types` добавлено поле `specialization_req` (TEXT, nullable) — указывает требуемую специализацию (`vik` / `iszh`)
- Эндпоинт `GET /api/refs/object-equipment` поддерживает параметры `binding_level` и `room_type_code` для фильтрации
- Новый эндпоинт `GET /api/refs/object-equipment/rooms` — сводка по помещениям объекта (код, название, количество единиц оборудования)
- Автозаполнение полей `model` и `serial_number` для счётчиков (`schetchik_electroshc`, `schetchik_hvs`, `schetchik_gvs`) при создании задачи из привязки объекта

### 15.34. Модуль интеграции внешних заявок ✅
- **Импорт Excel** — `POST /api/requests/import` принимает `.xlsx` файл с колонками: № заявки, Статус, Вид оборудования, Код объекта, Адрес
- **Предварительная валидация** — `POST /api/requests/import?mode=validate` выполняет проверку файла без создания записей, возвращает список ошибок (номер строки, № заявки, описание). Фронтенд показывает модальное окно с таблицей ошибок перед импортом
- **Парсинг и маппинг** — поиск вида оборудования по `name` в `equipment_types` (регистронезависимо), поиск объекта по `object_code` (приоритет) или по нормализованному адресу
- **Вид оборудования "ИСЖ объекта"** — специальный вид с `specialization_req = NULL`, означает "любая специализация". При импорте не создаёт задачи, визит помечается `is_multi_specialist = TRUE`. Проверка специализации при назначении пропускается
- **Статус 'skipped'** — дубликаты заявок (уже импортированные или внутри файла) помечаются статусом `skipped`, а не `error`
- **Нормализация адреса** — утилита `addressNormalizer.ts`: удаление лишних пробелов, приведение сокращений (ул/улица, д/дом, к/корпус), lower case
- **Группировка по объекту** — несколько заявок на один `object_code` → один визит с несколькими задачами
- **Статус `awaiting_assignment`** — новый статус визита (визит создан, но инженер не назначен); `userId = NULL`
- **Таблица `imported_requests`** — хранит импортированные заявки с FK на `equipment_types`, `addresses`, `visits` (см. раздел 3.2.17)
- **Таблица `visit_requests`** — связующая таблица многие-ко-многим между визитами и заявками (visit_id + imported_request_id). Автопривязка при создании визита инженером, поддержка нескольких визитов на одну заявку «ИСЖ объекта» (см. раздел 3.2.18)
- **Таблица `visit_engineers`** — связующая таблица для множественного назначения (visit_id + engineer_id + is_primary) (см. раздел 3.2.19)
- **Таблица `request_assignment_log`** — история действий: assigned/unassigned/declined с причиной (см. раздел 3.2.20)
- **Валидация специализации** — при назначении проверяется `equipment_type.specialization_req` против булевых флагов инженера (`specialization_vik/iszh/gpm/dgu/ibp`)
- **Множественное назначение** — ТМ может назначить нескольких инженеров на любую заявку; первый назначенный становится основным (`is_primary = true`)
- **Отказ инженера** — `POST /api/requests/decline` с причиной, уведомление ТМ
- **Уведомления** — типы `request_assigned`, `request_unassigned`, `request_declined`, `request_imported`
- **Ручная привязка** — `POST /api/requests/:id/bind` для заявок со статусом `error`
- **Отчёт по заявкам** — расширен `POST /api/reports/summary-generate` типом `requests` с фильтрацией по `requestIds`. Для заявок «ИСЖ объекта» отчёт агрегирует данные из **всех** связанных визитов (через `visit_requests`), а не только из одного визита
- **Отчёт по договору** — `POST /api/reports/summary-generate` принимает `contractId`; UI содержит переключатель режима «По договору и периоду» / «Указать номера заявок», Select для выбора договора (`api.getContracts()`). Сервер находит все заявки договора за период и связанные визиты. Виртуальные визиты (без `userId`) исключены из отчёта
- **Поиск по номерам** — `POST /api/requests/search-by-numbers` для автокомплита в отчёте
- **Асинхронный импорт** — для файлов >100 строк через `import_log` со статусом `processing` + polling
- **Фронтенд (ТМ/Админ)** — страница `/requests`: таблица заявок, импорт Excel, назначение/снятие инженеров, ручная привязка, сортировка по колонкам (№ заявки, статус, код, адрес), фильтр по статусу исполнения и инженеру, пагинация по 10 записей. ТМ видит только заявки по своим адресам и своим инженерам. Все страницы ТМ/Админа: `maxWidth: 1400px`
- **Фронтенд (Инженер)** — страница `/my-requests`: список назначенных заявок с табами-фильтрами (Все/Новые/В работе/Завершённые). На мобильном — карточки (`.request-card`), на десктопе — таблица. Умные кнопки: «Начать визит»+«Отказаться» для новых заявок, «Продолжить визит» для активных, без кнопок для завершённых. Автоматическая смена статуса визита на «В работе» при первом посещении страницы визита или создании/обновлении задачи
- **API-клиент** — методы `importRequests`, `getRequests`, `assignEngineer`, `unassignEngineer`, `declineRequest`, `searchRequestsByNumbers`

### 15.35. Расширение модуля предложений по оборудованию ✅
- **Новые поля `equipment_proposals`:** `request_type` (new_equipment / room_change / brand_change), `old_room_type_code`, `rejection_reason`, `pending_until` (TTL 30 дней), `object_equipment_id` (ссылка на запись для переноса)
- **Новые поля `object_equipment`:** `confirmation_status` (confirmed / pending), `created_by`, `pending_until`
- **Перенос оборудования:** при `room_change` не создаётся новая запись `object_equipment` — обновляется `roomTypeCode` существующей записи; при отклонении — откат к `old_room_type_code`
- **TTL и cron:** ежедневная обработка истёкших proposals (`POST /api/internal/cron/process-expired-proposals`, 03:00); истёкшие записи получают статус `expired`, не удаляются физически (soft delete)
- **Массовые действия:** `PUT /api/proposals/admin/batch` — одобрение/отклонение нескольких proposals за один запрос
- **Новый статус:** `expired` — для предложений с истёкшим TTL

### 15.39. Антифрод-система верификации фото ✅
- **Принцип:** серверный пост-анализ, не блокирует инженера. Результаты — только для ТМ и админа
- **Проверки:** pHash (перцептический хэш через `sharp`), timestamp съёмки vs. окно визита, GPS (опционально, Haversine, порог 500м), источник фото (camera/gallery)
- **Модель данных:** новые поля в `photos` (phash, captured_at, gps_lat/lng, photo_source, verification_status/details) + таблица `visit_anomalies` (универсальная для любых типов проверок)
- **Страница «Аналитика визитов»:** список визитов с отклонениями (KPI, фильтры, карточки), детали с чекбоксами, действия: «Запросить пересъёмку» (удаляет фото → визит в работу) и «Подтвердить визит»
- **Запрос пересъёмки:** ТМ/админ выбирает отклонения → фото удаляются → статус задач/визита/заявки обновляется
- **EXIF НЕ используется** — iOS Safari вырезает EXIF в ~40-80% случаев. Вместо EXIF: GPS через `navigator.geolocation`, timestamp через `Date.now()`
- **Расширяемость:** `visit_anomalies` с JSONB `details` — новые проверки без изменения схемы
- **Макеты UI:** `mockups/analytics-visits.html` (4 экрана: список/детали × ПК/мобильный)
- **Решение по альтернативному ТЗ:** ORB/AKAZE (OpenCV) — не применимо (сервер 1 CPU / 1.9 ГБ RAM). OCR — не приоритет. pgvector/очереди — overkill для масштаба проекта

### 15.38. Связь визитов с заявками через VisitRequest (многие-ко-многим) ✅
- **Таблица `visit_requests`** — связующая таблица для отношения многие-ко-многим между `visits` и `imported_requests` (поля: `visit_id`, `imported_request_id`, уникальный составной ключ)
- **Бизнес-правило «ИСЖ объекта»:** заявка с видом оборудования «ИСЖ объекта» подразумевает ТО **всего** оборудования объекта. Каждый инженер (с разной специализацией) создаёт свой визит, и все визиты связываются с одной заявкой через `visit_requests`
- **Автопривязка при создании визита (все роли):** когда визит создаётся на объект (независимо от роли — инженер, ТМ, администратор), сервер автоматически ищет заявки типа «ИСЖ объекта» по `object_code` с фильтром по периоду (`startDate <= visitDate <= deadline`) и создаёт записи в `visit_requests`. Для ИСЖ объекта: одна заявка → много визитов (разные инженеры), без фильтра по статусу виртуального визита. Если среди заявок есть «ИСЖ объекта» — визит помечается `is_multi_specialist = TRUE`
- **Автопривязка при завершении визита:** при `POST /api/visits/:id/complete` система дополнительно привязывает заявки на конкретное оборудование по типам задач визита. Фильтр по периоду: `startDate <= visitDate <= deadline`. Для конкретного оборудования: одна заявка → один визит (1:1), только если заявка ещё не привязана к другому визиту. Защита от дубликатов: если несколько заявок с одинаковым адресом и периодом — привязка только к первой
- **Автопривязка при создании задачи:** при создании задачи система ищет заявки на конкретное оборудование (по `equipment_type_code`) для данного объекта и автоматически привязывает через `visit_requests`
- **Объединение заявок в API:** эндпоинты `GET /api/visits` и `GET /api/visits/:id` возвращают объединённый массив номеров заявок из двух источников — `importedRequests` (прямая привязка по `visit_id`) и `visitRequests → importedRequest` (через связующую таблицу). Дедупликация по `imported_request_id`
- **Отображение в UI:** в списке визитов показываются первые 2 номера заявок + счётчик «+N» (если их больше)
- **Отчёты для заявок ИСЖ объекта:** при формировании сводного отчёта (`type=requests`) система находит **все** визиты, связанные с заявкой через `visit_requests`, и агрегирует задачи, фото и рекомендации из каждого визита — так отчёт содержит результаты работы всех инженеров, участвовавших в ТО объекта
- **Проверка задач при вычислении статуса заявки:** функция `computeExecutionStatus` (в `server/src/routes/requests.ts`) принимает `equipmentTypeId` заявки. Для не-ИСЖ заявок статус «Завершён» требует наличия задачи по типу оборудования заявки в связанном визите. Если задача отсутствует — статус «Не назначена». Запрос визита включает `tasks: { select: { equipmentTypeId: true } }`
- **Расширенная проверка дубликатов при создании визита:** в `server/src/routes/visits.ts` при создании визита инженером поиск существующего визита на тот же адрес проверяет не только `userId`, но и `visitEngineers` — предотвращает дубликаты, когда ТМ назначил инженера через `visitEngineers`
- **Раздельные виртуальные визиты при удалении:** в `server/src/routes/visits.ts` при удалении визита заявки группируются по `equipmentTypeId`, для каждой группы создаётся отдельный виртуальный визит (вместо одного общего) — предотвращает смешивание типов оборудования
- **Отчёты по договору (UI):** переключатель режима «По договору и периоду» / «Указать номера заявок». При выборе «По договору и периоду» — Select для выбора договора (`api.getContracts()`), `contractId` передаётся в `summary-generate`, сервер находит все заявки договора за период и связанные визиты

### 15.40. Команды ТМ (группировка территориальных менеджеров) ✅

### 15.42. Синхронизация brand/model из proposal в задачу визита при модерации ✅
- **Одиночный approve (`PUT /api/proposals/admin/:id/approve`):** после одобрения данные `brand`, `model`, `serialNumber` из proposal записываются в связанную задачу визита (`server/src/routes/proposals.ts`)
- **Batch approve (`PUT /api/proposals/admin/batch`):** аналогичная синхронизация выполняется для каждого proposal в массиве
- **Ранее:** изменения админа при модерации попадали только в `object_equipment`, но не в `task` — данные рассинхронизировались
- **Исправление:** при approve в задачу визита записываются финальные значения brand/model/serialNumber (с учётом возможных изменений админа)
