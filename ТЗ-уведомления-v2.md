## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Назначение
Настоящее ТЗ описывает **расширение** существующего модуля уведомлений в приложении «Цифровой чек-лист инженера». Базовый функционал (колокольчик, список уведомлений, маркировка прочитанных, автообновление) уже реализован. Данное ТЗ добавляет:

- Системные уведомления о релизах (новый тип `system_release`).
- Функцию «Очистить» (мягкое удаление уведомлений).
- Webhook-интеграцию с CI/CD для автоматического оповещения о деплое.
- Ручное создание системных уведомлений через админ-панель.
- Мобильную адаптацию Центра уведомлений.

### 1.2. Текущее состояние (что уже реализовано)

| Компонент | Статус | Описание |
|-----------|:------:|----------|
| Таблица `notifications` в БД | ✅ | Модель `Notification`: `id`, `userId`, `type`, `title`, `message`, `entityType`, `entityId`, `isRead`, `createdAt` |
| API: список уведомлений | ✅ | `GET /api/notifications?limit=&offset=&unread_only=` с пагинацией |
| API: отметить прочитанным | ✅ | `PATCH /api/notifications/:id/read` |
| API: «Прочитать всё» | ✅ | `PATCH /api/notifications/read-all` |
| Колокольчик с бейджем | ✅ | Компонент `NotificationBell` с автообновлением каждые 60 сек |
| Выпадающий список | ✅ | Dropdown с карточками уведомлений, иконками по типам |
| 10 типов рабочих уведомлений | ✅ | `proposal_created`, `proposal_approved`, `proposal_rejected`, `proposal_expiring_soon`, `proposal_expired`, `equipment_removed`, `request_assigned`, `request_unassigned`, `request_declined`, `request_imported` |

### 1.3. Цели доработки
- Информировать **всех пользователей** о выходе новых версий приложения сразу после успешного деплоя.
- Предоставить возможность **очистки** списка уведомлений (мягкое удаление).
- Обеспечить корректное отображение Центра уведомлений на **мобильных устройствах**.
- Предоставить администратору инструмент **ручного создания** системных уведомлений (fallback).

## 3. ИЗМЕНЕНИЯ В СТРУКТУРЕ БАЗЫ ДАННЫХ

### 3.1. Миграция: добавление поля `is_deleted`

Таблица `notifications` уже существует. Необходимо добавить одно поле для поддержки функции «Очистить»:

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|:-----------:|
| `is_deleted` | BOOLEAN | Флаг очистки (soft delete) | DEFAULT FALSE |

**SQL-миграция:**
```sql
ALTER TABLE notifications ADD COLUMN is_deleted BOOLEAN NOT NULL DEFAULT FALSE;
CREATE INDEX idx_notifications_user_active ON notifications(user_id, is_deleted, is_read);
```

**Prisma-модель (обновление):**
```prisma
model Notification {
  // ... существующие поля ...
  isDeleted  Boolean  @default(false) @map("is_deleted")

  @@index([userId, isDeleted, isRead])
}
```

### 3.2. Таблица `system_releases` (история релизов)

Для хранения информации о деплоях и предотвращения дубликатов:

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|:-----------:|
| `id` | UUID | Первичный ключ | PK |
| `version` | VARCHAR(50) | Версия (например, `v2.4.0`) | NOT NULL, UNIQUE |
| `release_notes` | TEXT | Текст релиза | NOT NULL |
| `deployed_at` | TIMESTAMP | Дата деплоя | DEFAULT NOW() |
| `deployed_by` | VARCHAR(50) | Источник: `ci_webhook` или `admin_manual` | |
| `admin_id` | UUID | ID админа (если создано вручную) | FK -> users.id, nullable |
| `notification_count` | INT | Сколько уведомлений создано | DEFAULT 0 |

## 4. API ЭНДПОИНТЫ

### 4.1. Существующие эндпоинты (без изменений)

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/api/notifications` | Список уведомлений (с пагинацией) |
| `PATCH` | `/api/notifications/:id/read` | Отметить одно как прочитанное |
| `PATCH` | `/api/notifications/read-all` | Прочитать все |

### 4.2. Модификация: фильтр `is_deleted`

Во всех существующих эндпоинтах добавить условие `WHERE is_deleted = FALSE` — удалённые уведомления не возвращаются.

**GET /api/notifications** — обновить `where`:
```typescript
const where: any = { userId: req.userId, isDeleted: false };
```

**PATCH /api/notifications/read-all** — обновить `where`:
```typescript
where: { userId: req.userId, isRead: false, isDeleted: false }
```

### 4.3. Новый эндпоинт: «Очистить всё»

**Запрос:** `POST /api/notifications/clear-all`  
**Авторизация:** `authMiddleware`  
**Логика:**
```typescript
const result = await prisma.notification.updateMany({
  where: { userId: req.userId, isDeleted: false },
  data: { isDeleted: true, isRead: true },
});
res.json({ cleared: result.count });
```
**Примечание:** При очистке уведомления также помечаются как прочитанные (`isRead: true`), чтобы при восстановлении они не всплывали как непрочитанные.

### 4.4. Новый эндпоинт: Webhook для CI/CD

**Запрос:** `POST /api/system/webhook/deploy`  
**Авторизация:** HMAC-подпись (без `authMiddleware` — вызывается из CI/CD)

**Заголовки:**
```
X-Webhook-Signature: sha256=<HMAC>
X-Webhook-Timestamp: <unix_timestamp>
```

**Тело запроса:**
```json
{
  "version": "v2.4.0",
  "release_notes": "Добавлен модуль массового импорта заявок из Excel и новая специализация ГПМ."
}
```

**Логика:**
1. Проверка HMAC-подписи (секрет хранится в `WEBHOOK_SECRET` в `.env`).
2. Проверка timestamp (защита от replay-атак: ±5 минут от текущего времени).
3. Проверка дубликата: если `version` уже есть в `system_releases` — вернуть `200 OK` с `{ skipped: true, reason: "already_deployed" }`.
4. Запись в `system_releases`.
5. Массовое создание уведомлений через `prisma.notification.createMany()`:
   ```typescript
   const users = await prisma.user.findMany({
     where: { isActive: true },
     select: { id: true },
   });
   
   await prisma.notification.createMany({
     data: users.map(u => ({
       userId: u.id,
       type: 'system_release',
       title: `Вышел новый релиз ${version}`,
       message: release_notes,
       entityType: 'system_release',
       entityId: version,
     })),
   });
   ```
6. Обновление `notification_count` в `system_releases`.

**Rate limiting:** Не более 10 запросов за 15 минут (защита от злоупотреблений).

**Ответ:**
```json
{ "success": true, "version": "v2.4.0", "notifications_created": 42 }
```

**Переменные окружения (добавить в `.env`):**
```
WEBHOOK_SECRET=<секретный_ключ_для_подписи>
```

### 4.5. Новый эндпоинт: ручное создание системного уведомления

**Запрос:** `POST /api/admin/system-notifications`  
**Авторизация:** `authMiddleware` + `adminOnly`

**Тело запроса:**
```json
{
  "title": "Обновление системы",
  "message": "Добавлена функция голосового ввода в поле рекомендаций.",
  "version": "v2.5.0"
}
```

**Логика:**
1. Валидация входных данных (Zod).
2. Запись в `system_releases` (`deployed_by: 'admin_manual'`, `admin_id: req.userId`).
3. Массовое создание уведомлений через `createMany()` (аналогично webhook).
4. Проверка дубликатов по `version` (если указан).

**Ответ:**
```json
{ "success": true, "notifications_created": 42 }
```

### 5.6. Офлайн-режим

- Список уведомлений кэшируется в IndexedDB (Dexie) при каждой загрузке.

- Действия (прочитать, очистить) ставятся в очередь синхронизации и выполняются при восстановлении соединения.
- Бейдж на колокольчике показывает последнее известное значение.

## 8. КРИТЕРИИ ПРИЕМКИ (Acceptance Criteria)

| № | Критерий | Метод проверки |
|---|----------|----------------|
| **1** | При вызове webhook деплоя всем активным пользователям создаются уведомления типа `system_release`. | Тест API с валидным HMAC payload. Проверка БД. |
| **2** | Повторный вызов webhook с той же версией не создаёт дубликаты. | Тест API: два вызова с `v2.4.0` — второй возвращает `skipped: true`. |
| **3** | Непрочитанные системные уведомления выделяются зелёной полоской и тегом `NEW FEATURE`. | Визуальная проверка UI. |

## 10. ТЕХНИЧЕСКИЕ ЗАМЕТКИ ДЛЯ РАЗРАБОТЧИКОВ

### 10.1. Массовая рассылка без очереди задач

Для реалистичного масштаба системы (50–200 пользователей) **не требуется** подключать BullMQ или аналоги. Используется `prisma.notification.createMany()` — батчевая вставка выполняется за миллисекунды:

```typescript
await prisma.notification.createMany({
  data: users.map(u => ({
    userId: u.id,
    type: 'system_release',
    title: `Вышел новый релиз ${version}`,
    message: release_notes,
    entityType: 'system_release',
    entityId: version,
  })),
});
```

Если количество пользователей превысит 1000 — рассмотреть переход на фоновую очередь (BullMQ).

### 10.2. Защита от дубликатов

При webhook-вызове:
1. Проверка `system_releases` по `version` — если уже есть, не создавать уведомления.
2. Уникальный индекс на `system_releases.version`.

### 10.3. HMAC-подпись webhook

```typescript
import crypto from 'crypto';

function verifyWebhookSignature(payload: string, signature: string, timestamp: string): boolean {
  const maxAge = 5 * 60; // 5 минут
  if (Math.abs(Date.now() / 1000 - parseInt(timestamp)) > maxAge) {
    return false;
  }
  const expected = crypto
    .createHmac('sha256', process.env.WEBHOOK_SECRET!)
    .update(`${timestamp}.${payload}`)
    .digest('hex');
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
}
```

### 10.4. CI/CD конфигурация (GitHub Actions)

Пример шага в `.github/workflows/deploy.yml`:

```yaml
- name: Notify application about deploy
  if: success()
  run: |
    PAYLOAD='{"version":"${{ github.ref_name }}","release_notes":"${{ github.event.head_commit.message }}"}'
    SIGNATURE=$(echo -n "${TIMESTAMP}.${PAYLOAD}" | openssl dgst -sha256 -hmac "${{ secrets.WEBHOOK_SECRET }}" | cut -d' ' -f2)
    curl -X POST https://checklist.example.com/api/system/webhook/deploy \
      -H "Content-Type: application/json" \
      -H "X-Webhook-Signature: sha256=${SIGNATURE}" \
      -H "X-Webhook-Timestamp: ${TIMESTAMP}" \
      -d "${PAYLOAD}"
```

### 10.5. Очистка мёртвого типа

Тип `equipment_removed` определён в `NotificationType`, но нигде не создаётся. Рекомендуется:
- Либо добавить триггер создания (при деактивации `object_equipment` администратором).
- Либо удалить из `NotificationType` и `TYPE_ICONS`, если функционал не планируется.

### 10.6. Обновление бейджа

Текущий polling каждые 60 секунд — адекватное решение. Для будущего улучшения можно рассмотреть Server-Sent Events (SSE), но это потребует новой зависимости (`express-sse` или кастомная реализация). На данном этапе polling достаточно.

### 10.7. Совместимость с PWA (Workbox)

API `/api/notifications` уже кэшируется через стратегию `NetworkFirst` (настроено в `sw.ts`). Новые эндпоинты (`clear-all`, `webhook/deploy`) кэшированию не подлежат — только `NetworkFirst` или без кэша.
