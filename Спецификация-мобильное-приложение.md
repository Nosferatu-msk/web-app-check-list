**Статус:** Черновик (обновлён по итогам ревью)

## 1. ОБЗОР

Мобильное приложение на **React Native (Expo)** — дополнительный клиент для существующего сервиса «Цифровой чек-лист инженера». Работает с тем же REST API, что и PWA. PWA продолжает функционировать для администраторов и как fallback.

### 1.1. Цели
- Решить проблемы PWA:
  - Service Worker eviction → потеря сессии и локальных данных
  - Ненадёжные push-уведомления (особенно на iOS Safari)
  - Неточная геолокация через Web API
  - Повторные логины при потере сессии в условиях отсутствия интернета
- Обеспечить полноценную офлайн-работу для инженеров в местах без связи (подвалы, серверные, удалённые объекты)
- Публикация в Google Play для удобного распространения на рабочие устройства
- Нативный доступ к камере (фонарик, фокус, зум), GPS, биометрии

### 1.2. Не цели
- Замена PWA — PWA продолжает работать параллельно
- Мобильное приложение для администратора — админ работает на ПК через веб
- Изменение серверного API — используется существующий REST API (кроме batch-sync и версионирования)

### 1.3. Мотивация (почему не PWA)

| Проблема PWA | Решение в нативном приложении |
|---|---|
| Service Worker eviction — браузер чистит кэш → потеря сессии и данных | SQLite + нативное хранилище — данные никогда не будут удалены |
| Push-уведомления работают нестабильно | FCM (Firebase Cloud Messaging) — надёжная доставка |
| Геолокация через Web API менее точна, работает только при активной вкладке | Нативный GPS — высокая точность |
| Сессия теряется при eviction → инженер логинится заново в подвале без интернета | Биометрия (отпечаток/лицо) + PIN-fallback + refresh token в Secure Storage |
| Камера через `<input type="file">` — нет контроля фокуса, фонарика | Нативная камера — полный контроль, фонарик, фокус |

| OTA-обновления | **EAS Update** | Обновления JS-бандла без публикации в Google Play |
| Crash reporting | **Sentry** | Ошибки, производительность, crash-free rate |

## 5. ЭКРАНЫ ПРИЛОЖЕНИЯ

### 5.0. Общие UI-требования

**Touch targets:**
- Все интерактивные элементы (кнопки, чекбоксы, radio, иконки) — **минимум 48dp × 48dp** (стандарт Android)
- Карточки визитов — кликабельны целиком (не только кнопка внутри)
- Расстояние между интерактивными элементами — минимум 8dp

**Формы и ввод данных:**
- Каждый input — с **видимым лейблом** над полем (placeholder — не замена лейблу)
- Числовые поля (температура, давление, ток, показания) — `keyboardType="numeric"`
- Email-поля — `keyboardType="email-address"`
- Телефон — `keyboardType="phone-pad"`
- Валидация — при потере фокуса (не при submit), мгновенная обратная связь
- Группы полей — с заголовками секций

**Загрузка контента:**
- Skeleton loading при ожидании > 300 мс
- Не показывать skeleton при ожидании < 200 мс (избегать мерцания)
- Skeleton повторяет форму контента (карточки визитов → скелет карточек)
- Pull-to-refresh — отключён на экранах с горизонтальным скроллом и вложенными ScrollView

**Empty states:**
- Каждый экран с данными описывает пустое состояние с CTA-кнопкой
- «Нет визитов» → «+ Создать первый визит»
- «Нет заявок» → текст «Заявки появятся здесь после назначения»
- «Нет интернета» → текст «Работайте офлайн — данные синхронизируются при появлении сети»

**Тёмная тема:**
- Автопереключение по системной настройке (useColorScheme)
- Ручной override в профиле (Светлая / Тёмная / Как в системе)
- Палитра тёмной темы:

| Токен | Светлая | Тёмная |
|---|---|---|
| Background | #F8FAFC | #0F172A |
| Surface/Card | #FFFFFF | #1E293B |
| Text Primary | #0F172A | #F8FAFC |
| Text Secondary | #64748B | #94A3B8 |
| Border | #E2E8F0 | #334155 |
| Primary | #0F766E | #14B8A6 |
| Status badges | без изменений (контраст ≥ 4.5:1 в обеих темах) |

**Контраст и доступность:**
- Текст на бейджах статусов — контраст ≥ 4.5:1 (WCAG AA)
- Индикатор GPS-точности (цвет) — дублировать текстом (расстояние в метрах)
- Все иконки — с accessibilityLabel для screen readers

### 5.1. Авторизация
- Экран логина (логин/пароль) — аналог PWA LoginPage
- После первого входа — предложение включить **биометрию** (отпечаток/Face Unlock)
- **PIN-fallback:** если биометрия недоступна (грязные руки, перчатки) — вход по PIN-коду (4-6 цифр)
- PIN хранится в Secure Store (не в SQLite)
- Refresh token в `expo-secure-store` (не удаляется при очистке кэша, в отличие от PWA)
- Автоматическое обновление access token через interceptor
- При повторном запуске — вход по биометрии или PIN без ввода пароля
- **Auto-lock:** блокировка приложения через **5 минут** неактивности ( AppState → background/inactive)
- При auto-lock — экран разблокировки (биометрия или PIN), не экран логина

### 5.2. Главный экран (Инженер ТО)
- Список визитов с табами: **Активные** / **Завершённые**
- Карточка визита:
  - Адрес (крупно)
  - Дата и время
  - Статус (цветной бейдж: not_started / in_progress / completed)
  - Прогресс: «N/M задач выполнено» (прогресс-бар)
  - Специализация (цветной тег: ВиК, ИСЖ, ГПМ...)
- Кнопка «+ Новый визит» → выбор адреса из справочника (с поиском)
- Pull-to-refresh (с ограничениями из §5.0)
- Skeleton loading при первой загрузке (по правилам из §5.0)
- Сортировка: по дате (новые сверху), по статусу
- **Бейджи на табах:** количество визитов в каждой вкладке (аналог PWA)

### 5.3. Визит (детальная страница)
- Метаданные визита:
  - Адрес (крупно)
  - Дата, время, сезон (Лето/Зима — автоопределение)
  - Инженер (ФИО)
  - GPS-координаты (ссылка на карту)
  - Статус
- Список задач по оборудованию:
  - Для каждой задачи: тип оборудования, помещение, статус, прогресс параметров
  - Цветовая индикация: серый (not_started), синий (in_progress), зелёный (completed)
- Кнопка «+ Добавить оборудование» → выбор типа + помещения
- Кнопка «Завершить визит» (с валидацией обязательных полей и фото)
- Кнопка «Сформировать отчёт» (для completed визитов)
- **Индикатор синхронизации:** «Сохранено локально» / «Синхронизировано» / «Ошибка синхронизации»

### 5.4. Задача (параметры оборудования)
- Форма параметров — аналог страниц 4.1–4.13 из ТЗ
- 13 типов форм в зависимости от типа оборудования:
  1. РЩ/ГРЩ — электрические параметры
  2. Вентиляционная установка — температура, давление, расход
  3. Внутренний блок VRV — режим, температура, ошибки
  4. Внутренний блок МСС — аналогично VRV
  5. Внутренний блок СС — аналогично
  6. Наружный блок VRV — температура, давление, ток
  7. Наружный блок МСС — аналогично
  8. Наружный блок СС — аналогично
  9. Прибор учёта ГВС — показания счётчика
  10. Прибор учёта ХВС — показания счётчика
  11. Прибор учёта э/э — показания счётчика
  12. Сети водоснабжения — давление, температура, утечки
  13. Тепловые сети — давление, температура, утечки
- Авто-сохранение в SQLite каждые 30 секунд (как в PWA)
- Индикатор «Сохранено локально» / «Синхронизировано»
- Заключение: «Исправно, замечаний нет» / «Исправно, есть замечания» / «Неисправно»
- Дополнительные рекомендации (обязательны при замечаниях/неисправности)
- **Валидация:** числовые поля — только цифры, с допустимым диапазоном (указать в ТЗ для каждого типа)

### 5.5. Камера / Фото

**Фото предназначены для AI-распознавания (агент анализирует состояние оборудования), не для визуального осмотра человеком.** Качество — минимально необходимое для надёжного распознавания.

**Параметры съёмки:**
- Разрешение: **1280px** по длинной стороне (масштабирование после съёмки)
- Качество JPEG: **0.6–0.7** (AI-модели устойчивы к артефактам сжатия)
- Размер файла: **~100-200 КБ** (vs 3-5 МБ в полном качестве — ускорение загрузки в 15-25×)
- Формат: JPEG (не PNG)
- Сжатие применяется **сразу после съёмки**, до сохранения в File System. Исходник не хранится.

**Нативная камера:**
- Переключение фронтальная/тыловая (по умолчанию тыловая)
- Фонарик (toggle) — аналог TorchButton из PWA
- Зум (pinch-to-zoom)
- Фокус по тапу
- **Важно:** не запрашивать разрешение на камеру при загрузке экрана — только при первом нажатии кнопки съёмки (см. опыт PWA с iOS)

**Галерея как fallback:**
- Кнопка «Выбрать из галереи» — только если камера недоступна (нет разрешения, сломана)
- Предупреждение при выборе из галереи: «Фото должно быть сделано сегодня»
- Проверка EXIF-даты: если фото старше 24 часов — предупреждение

**Предпросмотр фото с возможностью переснять**

**Before/After пары:**
- Для большинства типов оборудования: 2 фото (до и после)
- Для некоторых типов (РЩ/ГРЩ, счётчики): только 1 фото (before)

**Предупреждение 152-ФЗ** при первом использовании камеры. Флаг согласия хранится в Secure Store. При переустановке приложения — показывать снова.

**Именование фото по шаблону:** `{№}_{equipment_code}_{room_code}_{moment}.jpg`
- Пример: `01_rsch_server_before.jpg`

**Хранение:** фото в File System + привязка к задаче в SQLite

**Обработка ошибок камеры:**
- Камера занята другим приложением → «Камера недоступна. Выберите фото из галереи или закройте другое приложение»
- Нет разрешения на камеру → запрос разрешения + кнопка «Открыть настройки»
- Нет места на устройстве (< 50 МБ) → «Недостаточно места для сохранения фото»
- Сбой съёмки → «Не удалось сделать фото. Попробуйте ещё раз»

### 5.6. Геолокация
- При создании визита — автоматический запрос GPS-координат
- Отображение:
  - Адрес (текстом)
  - Координаты: широта, долгота
  - Точность в метрах
- Индикатор точности:
  - 🟢 Зелёный: < 50 м
  - 🟡 Жёлтый: 50–200 м
  - 🔴 Красный: > 200 м (предупреждение)
- Координаты сохраняются в визит и отправляются на сервер
- Кнопка «Обновить координаты» (повторный запрос GPS)

### 5.7. Отчёты
- Просмотр сгенерированных PDF-отчётов (react-native-pdf)
- Кнопка «Сформировать отчёт» → запрос к серверу → получение PDF + ZIP с фото
- Офлайн-просмотр ранее сгенерированных отчётов (кэш в File System)
- Поделиться (Android Share API):
  - Отправка ZIP по email (адрес из справочника)
  - Сохранение в Downloads
- Структура отчёта — аналогично PWA (Шаблон акта.md)

### 5.8. Офлайн-режим
- Индикатор онлайн/оффлайн в шапке (аналог SyncBanner из PWA)
- Все данные кешируются в SQLite:
  - Справочники (адреса, оборудование, типы помещений) — при первом получении
  - Визиты и задачи — при открытии
  - Фото — при съёмке
- **Стратегия кеширования справочников:**
  - Адреса — только назначенные инженеру (не все ~500)
  - Оборудование — только для назначенных адресов (не все ~12000)
  - Delta-синхронизация: `GET /api/refs/equipment?updated_since=<дата>` — только изменения
- Очередь мутаций (Outbox):
  - Создание визита
  - Сохранение параметров задачи
  - Загрузка фото
  - Обновление статуса
- **Индикатор прогресса синхронизации:**
  - Количество элементов в очереди: «3 из 12 синхронизировано»
  - Прогресс загрузки фото (особенно важно при большом количестве)
  - Возможность отменить синхронизацию
- При появлении сети — автоматическая синхронизация очереди (аналог PWA sync.ts)
- **Разрешение конфликтов:**
  - Last-write-wins для параметров задач — **с пометкой конфликта** если timestamp расхождения < 60 сек (ручное разрешение)
  - Server-wins для статусов и назначений
  - Merge для задач в визите
- Уведомление «Данные синхронизированы» после успешной синхронизации
- Retry при ошибке (до 5 попыток, как в PWA)

### 5.9. Push-уведомления
- FCM (Firebase Cloud Messaging) для надёжной доставки
- Типы уведомлений:
  - Назначение на заявку/визит
  - Изменение статуса заявки
  - Напоминание о незавершённых визитах
  - Отклонение отчёта ТМ/Админом
- Настройка: вкл/выкл, звук, вибрация
- Тап по уведомлению → переход к соответствующему визиту/заявке (deep link)

**In-app уведомления (внутри приложения):**
- Баннер «Новая заявка назначена» при активном использовании
- Тост «Визит сохранён локально» при сохранении в офлайн
- Предупреждение «N визитов не синхронизированы» при длительном офлайн

### 5.10. Заявки (Мои заявки)
- Список заявок инженера (аналог MyRequestsPage из PWA)
- Табы по статусу: Все / Новые / В работе / Завершённые
- Карточка заявки:
  - № заявки
  - Адрес
  - Вид оборудования
  - Статус исполнения (executionStatus)
  - Кнопки действий (Начать визит / Продолжить визит)
- Мобильные карточки (аналог .request-card из PWA)

## 6. ОФЛАЙН-АРХИТЕКТУРА (ДЕТАЛЬНО)

```
┌─────────────────────────────────────────────────────┐
│                  Sync Engine                         │
├─────────────────────────────────────────────────────┤
│  Outbox (очередь исходящих мутаций)                  │
│  ├── Мутация 1: POST /api/visits (создание визита)   │
│  ├── Мутация 2: PUT /api/visits/:id/tasks/:id        │
│  ├── Мутация 3: POST /api/photos (загрузка фото)     │
│  └── ...                                             │
├─────────────────────────────────────────────────────┤
│  Inbox (очередь входящих обновлений)                 │
│  ├── Обновление статуса заявки                       │
│  ├── Назначение нового визита                        │
│  └── Изменение справочников                          │
├─────────────────────────────────────────────────────┤
│  Conflict Resolver                                   │
│  ├── Last-write-wins: параметры задачи               │
│  │   (с пометкой при расхождении timestamp < 60 сек) │
│  ├── Server-wins: статусы, назначения                │
│  └── Merge: задачи в визите                          │
├─────────────────────────────────────────────────────┤
│  Sync Triggers                                       │
│  ├── При появлении сети (NetInfo listener)            │
│  ├── Каждые 60 секунд (как в PWA)                    │
│  ├── При возвращении в приложение (AppState)         │
│  └── Вручную (pull-to-refresh)                       │
├─────────────────────────────────────────────────────┤
│  Guarantees                                          │
│  ├── Идемпотентность: каждая мутация — idempotency   │
│  │   key (client-generated UUID). Повторная отправка │
│  │   не создаёт дубликат на сервере                  │
│  ├── Order: мутации отправляются в порядке created_at│
│  ├── Dedup: если мутация с тем же id уже отправлена  │
│  │   и получена — не отправлять повторно             │
│  └── Retry: до 5 попыток с exponential backoff       │
└─────────────────────────────────────────────────────┘
```

### Протокол синхронизации

**Сценарий 1: Создание визита в офлайн**
```
1. Инженер создаёт визит → записывается в SQLite (dirty=1)
2. Мутация добавляется в sync_queue (action=create, entity_type=visit)
3. При появлении сети → sync engine отправляет POST /api/sync/batch
4. Сервер обрабатывает, возвращает server_id
5. SQLite обновляется: id=server_id, dirty=0
6. Мутация помечается completed в sync_queue
```

**Сценарий 2: Обновление параметров в офлайн**
```
1. Инженер меняет параметр → SQLite обновляется (dirty=1)
2. Мутация в sync_queue (action=update, entity_type=task, payload={parameters})
3. При sync → PUT /api/visits/:id/tasks/:id через batch
4. Если сервер вернул 409 (конфликт) → пометить конфликт, показать инженеру
5. Инженер разрешает конфликт вручную (выбрать свою версию / серверную / merges)
```

**Сценарий 3: Загрузка фото в офлайн**
```
1. Фото сжато → сохранено в File System + записано в photos table (uploaded=0)
2. Мутация в sync_queue (action=create, entity_type=photo)
3. При sync → POST /api/photos (multipart) через batch
4. После успешной загрузки → uploaded=1, server_id обновлён
5. Файл в File System можно удалить (опционально, если сервер — source of truth)
```

**Идемпотентность:**
- Каждая мутация получает `client_mutation_id` (UUID) при создании
- Сервер проверяет: если мутация с таким id уже обработана — возвращает кэшированный результат
- Предотвращает дубликаты при повторной отправке (retry, двойное нажатие)

CREATE TABLE visits (

-- Задачи
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  visit_id TEXT NOT NULL,        -- FK к visits
  equipment_id TEXT NOT NULL,
  equipment_type TEXT NOT NULL,
  room_id TEXT,
  room_type TEXT,
  status TEXT NOT NULL,          -- not_started / in_progress / completed
  parameters TEXT,               -- JSON с параметрами (зависят от типа оборудования)
  parameters_version INTEGER DEFAULT 1,  -- версия схемы параметров (для миграции формата)
  conclusion TEXT,               -- Исправно, замечаний нет / ...
  recommendations TEXT,          -- Дополнительные рекомендации
  created_at TEXT,
  updated_at TEXT,
  dirty INTEGER DEFAULT 0,
  sync_error TEXT                -- текст ошибки последней синхронизации
);

-- Фото
CREATE TABLE photos (
  id TEXT PRIMARY KEY,
  task_id TEXT NOT NULL,         -- FK к tasks
  moment TEXT NOT NULL,          -- before / after
  file_path TEXT NOT NULL,       -- Путь к файлу в File System
  file_name TEXT NOT NULL,       -- Имя по шаблону: 01_rsch_server_before.jpg
  uploaded INTEGER DEFAULT 0,    -- 1 = загружено на сервер
  server_id TEXT,                -- ID с сервера
  created_at TEXT
);

-- Справочники (кешируются с сервера, delta-синхронизация)
CREATE TABLE cached_addresses (
  id TEXT PRIMARY KEY,
  full_address TEXT NOT NULL,
  city TEXT,
  street TEXT,
  house TEXT,
  building TEXT
);

CREATE TABLE cached_equipment (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  code TEXT NOT NULL,
  photo_code TEXT NOT NULL,

);

CREATE TABLE cached_rooms (
  id TEXT PRIMARY KEY,
  address_id TEXT NOT NULL,
  name TEXT NOT NULL,

);

CREATE TABLE cached_equipment_types (
  id TEXT PRIMARY KEY,

  code TEXT NOT NULL,
  specialization TEXT            -- виК, исж, гпм...
);

CREATE TABLE cached_room_types (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL
);

-- Очередь синхронизации
CREATE TABLE sync_queue (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  client_mutation_id TEXT NOT NULL UNIQUE,  -- UUID для идемпотентности
  entity_type TEXT NOT NULL,     -- visit / task / photo
  entity_id TEXT NOT NULL,
  action TEXT NOT NULL,          -- create / update / delete
  payload TEXT,                  -- JSON с данными
  retry_count INTEGER DEFAULT 0,
  max_retries INTEGER DEFAULT 5,
  status TEXT DEFAULT 'pending', -- pending / in_progress / completed / failed
  error TEXT,
  created_at TEXT

-- Индексы для производительности

CREATE INDEX idx_tasks_dirty ON tasks(dirty) WHERE dirty = 1;
CREATE INDEX idx_photos_task ON photos(task_id);
CREATE INDEX idx_sync_queue_status ON sync_queue(status);

### Поведение кнопки «Назад» (Android)

Аппаратная кнопка «Назад» и swipe-жест сохраняют стандартную навигационную историю:

| Экран | Назад → |
|---|---|
| Задача → параметры | Визит (детальный) |
| Задача → фото | Задача (параметры) |
| Камера (съёмка) | Задача (фото) — НЕ к списку визитов |
| Визит (детальный) | Список визитов |
| Создание визита | Список визитов |
| Push → визит | Список визитов (не вложенный стек) |

**Важно:** не использовать `router.replace()` там, где нужен возврат. Использовать `router.push()` для сохранения стека.

### Deep linking из push-уведомлений

**Cold start (приложение закрыто):**
1. Push → тап → приложение запускается
2. Проверка авторизации (биометрия/PIN)
3. После авторизации → переход к визиту/заявке из push
4. Стек: [Tab Bar] → [Визит] — не глубже

**Warm start (приложение в фоне):**
1. Push → тап → приложение активируется
2. Переход к визиту/заявке из push
3. Стек сохраняется, новый экран — поверх

**Если визит не загружен локально:**
1. Показать skeleton
2. Запросить с сервера (если online)
3. Если offline → «Визит ещё не загружен. Подключитесь к сети для загрузки»

| `/api/refs/*?updated_since=<date>` | GET | **Delta-синхронизация** справочников | P1 |

### API-версионирование

Мобильное приложение обновляется медленнее PWA (Google Play: 1-3 дня + время на установку). Для защиты от breaking changes:

- Сервер отправляет `X-API-Version: 2` в заголовке ответа
- Приложение при старте проверяет минимальную поддерживаемую версию
- Сервер поддерживает N-1 версию (если текущая v3 — поддерживает v2)
- При несовместимой версии → экран «Обновите приложение» со ссылкой на Google Play

## 14. ОТЛИЧИЯ ОТ PWA

| Аспект | PWA | Мобильное приложение |

| GPS | Geolocation API — только при активной вкладке | expo-location — нативный GPS |
| Биометрия | ❌ Нет | ✅ expo-local-authentication + PIN-fallback |
| Auto-lock | ❌ Нет | ✅ 5 минут неактивности |
| Установка | «Добавить на главный экран» | Google Play / APK |
| Обновления | Service Worker (мгновенно) | Google Play + EAS Update (OTA для JS) |
| Офлайн | Service Worker + IndexedDB | SQLite + File System |
| UI-библиотека | Ant Design 5 | React Native Paper (Material Design 3) |
| Серверный кэш | Ручной (хуки) | TanStack Query (автоматический) |

## 15. СОГЛАШЕНИЯ И КОНВЕНЦИИ

- **Язык UI:** весь текст, лейблы, справочные данные — на **русском** (как в PWA)
- **Формат имени фото:** `{№}_{equipment_code}_{room_code}_{moment}.jpg`
- **Формат имени отчёта:** `OTCHET_{address}_{date}.zip`
- **Значения заключения:** `Исправно, замечаний нет` / `Исправно, есть замечания` / `Неисправно`
- **Условные обязательные поля:** «Дополнительные рекомендации» обязательны только при заключении «Исправно, есть замечания» или «Неисправно»
- **Автосохранение:** каждые 30 секунд (как в PWA)
- **Сброс задачи:** «Сбросить задачу» очищает только текущую задачу, не весь визит
- **Сезоны:** Лето (1 апреля — 31 октября), Зима (1 ноября — 31 марта)
- **Формат дат в UI:** `DD.MM.YYYY` (не ISO)
- **Формат чисел:** `1 234,5` (пробел-разделитель тысяч, запятая — десятичная)
- **Все строки UI** — через i18n-модуль (даже при одном языке — задел на будущее)
- **Логирование:** запрещено логировать токены, пароли, персональные данные в Sentry
