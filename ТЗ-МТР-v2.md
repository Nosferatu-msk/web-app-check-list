# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку модуля «Мелкий текущий ремонт (МТР)» в web-приложении «Цифровой чек-лист инженера»

**Версия:** 2.0  
**Дата:** 04.08.2026  
**Статус:** Утверждено

---

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Назначение
Настоящее ТЗ описывает требования к расширению функционала приложения за счет внедрения модуля «Мелкий текущий ремонт» (МТР). Модуль предназначен для оперативного устранения незначительных неисправностей (ремонт мебели, покрытий, дверей, стен и т.д.) и включает в себя новые роли пользователей, специфичный сценарий ведения визитов и новый справочник видов работ.

### 1.2. Ключевые принципы
* **Изоляция потоков:** Данные, визиты и заявки модуля МТР полностью изолированы от модуля «Техническое обслуживание» (ТО). Модуль ТО **не подвергается никаким изменениям** — он продолжает работать в текущем виде.
* **Масштабируемость ролевой модели:** Архитектура позволяет добавлять новые роли (помимо ТО и МТР) без изменения существующих таблиц и логики. Каждая роль имеет изолированные таблицы данных.
* **Гибридный справочник объектов:** ТМ МТР использует общий справочник адресов/объектов, но видит только те, которые закреплены за ним через отдельную таблицу привязок.
* **Поэтапное ведение работ:** Интерфейс инженера МТР жестко регламентирует последовательность действий (Фото ДО → Работы → Фото ПОСЛЕ) с возможностью сохранения черновиков для многосменных ремонтов.
* **Полный офлайн-режим:** Инженер МТР может работать без доступа к интернету — справочник работ кэшируется, черновики и фото сохраняются локально и синхронизируются при восстановлении связи.

## 2. РОЛЕВАЯ МОДЕЛЬ И ПРАВА ДОСТУПА

### 2.1. Роли
В систему добавляются две новые роли. Матрица изоляции представлена ниже:

| Роль | Видит объекты | Видит заявки/визиты ТО | Видит заявки/визиты МТР | Подчинение |
| :--- | :--- | :--- | :--- | :--- |
| **Администратор** | Все | ✅ Да | ✅ Да | — |
| **ТМ ТО** (существующая) | Только свои | ✅ Только свои | ❌ Нет | Администратору |
| **Инженер ТО** (существующий) | Только свои (через ТМ ТО) | ✅ Только свои | ❌ Нет | ТМ ТО |
| **ТМ МТР** | Только свои (из общего справочника) | ❌ Нет | ✅ Только свои | Администратору |
| **Инженер МТР** | Только свои (через ТМ МТР) | ❌ Нет | ✅ Только свои | ТМ МТР |

### 2.2. Масштабируемость
При добавлении новой роли (например, «Инженер электрик» / «ТМ электрик»):
- Создаётся отдельная таблица визитов (`xxx_visits`)
- Создаётся отдельная таблица привязок (`xxx_tm_objects`, `xxx_tm_engineers`)
- Добавляется одна строка в `VIEW all_visits` для администратора
- **Ни одна существующая таблица не изменяется**

### 2.3. Ограничения на комбинации ролей
Один пользователь может иметь **только одну роль**. Комбинации (например, ТМ ТО + ТМ МТР) невозможны на уровне БД (`role` — enum, одно значение).

## 3. ИЗМЕНЕНИЯ В СТРУКТУРЕ ДАННЫХ (БД)

### 3.1. Принцип изоляции
Таблица `visits` и все связанные с ней таблицы (`tasks`, `task_equipment_items`, `tm_objects`, `tm_engineers`) **не изменяются**. Для модуля МТР создаются новые таблицы.

### 3.2. Новая таблица `mtr_work_types` (Виды работ МТР)

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | UUID | Первичный ключ |
| `name` | VARCHAR(500) | Полное наименование работы |
| `category` | VARCHAR(100) | Категория для группировки (опционально) |
| `is_active` | BOOLEAN | Активность записи (default: true) |
| `created_at` | TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Дата обновления |

### 3.3. Новая таблица `mtr_visits` (Визиты МТР)

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | UUID | Первичный ключ |
| `engineer_id` | UUID FK → users(id) | Инженер МТР |
| `address_id` | UUID FK → addresses(id) | Адрес объекта |
| `request_number` | VARCHAR(15) | № заявки (формат SD + 10 цифр) |
| `date_start` | DATE | Дата начала работ |
| `time_start` | VARCHAR(5) | Время начала работ (HH:MM) |
| `status` | VARCHAR(30) | Статус визита (см. 3.6) |
| `is_draft` | BOOLEAN | Черновик (default: true) |
| `assigned_by_id` | UUID FK → users(id) | Кто назначил (ТМ МТР), nullable |
| `assigned_at` | TIMESTAMP | Дата назначения, nullable |
| `sent_at` | TIMESTAMP | Дата отправки инженером, nullable |
| `rejected_at` | TIMESTAMP | Дата отклонения ТМ, nullable |
| `rejection_reason` | TEXT | Причина отклонения, nullable |
| `created_at` | TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Дата обновления |

**Индексы:** `engineer_id`, `address_id`, `status`, `request_number` (unique).

### 3.4. Новая таблица `mtr_visit_works` (Работы в визите МТР)

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | UUID | Первичный ключ |
| `mtr_visit_id` | UUID FK → mtr_visits(id) | Визит |
| `mtr_work_type_id` | UUID FK → mtr_work_types(id) | Вид работы |
| `quantity` | INT | Количество (default: 1) |
| `comment` | TEXT | Комментарий к работе (опционально) |
| `sort_order` | INT | Порядок отображения (default: 0) |
| `created_at` | TIMESTAMP | Дата добавления |

**Уникальность:** `(mtr_visit_id, mtr_work_type_id, sort_order)` — одна и та же работа может быть добавлена несколько раз (например, «Окраска стен» в разных комнатах).

### 3.5. Расширение таблицы `photos` (Полиморфная связь)

Добавляется одно поле для привязки фото к визиту МТР:

```sql
ALTER TABLE photos ADD COLUMN mtr_visit_id UUID REFERENCES mtr_visits(id);
```

Логика:
- Для ТО: `task_id` или `task_equipment_item_id` заполнены, `mtr_visit_id = NULL`
- Для МТР: `mtr_visit_id` заполнен, `task_id = NULL`, `task_equipment_item_id = NULL`
- Поле `moment` (before/after) используется аналогично ТО

**CHECK-ограничение:** хотя бы одна из связей должна быть заполнена.

### 3.6. Новая таблица `mtr_tm_objects` (Привязка объектов к ТМ МТР)

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | UUID | Первичный ключ |
| `tm_id` | UUID FK → users(id) | ТМ МТР |
| `address_id` | UUID FK → addresses(id) | Адрес объекта |
| `created_at` | TIMESTAMP | Дата привязки |

**Уникальность:** `(tm_id, address_id)`

### 3.7. Новая таблица `mtr_tm_engineers` (Привязка инженеров к ТМ МТР)

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | UUID | Первичный ключ |
| `tm_id` | UUID FK → users(id) | ТМ МТР |
| `engineer_id` | UUID FK → users(id) | Инженер МТР |
| `created_at` | TIMESTAMP | Дата привязки |

**Уникальность:** `(engineer_id)` — инженер привязан только к одному ТМ.

### 3.8. VIEW для администратора (объединение визитов)

```sql
CREATE VIEW all_visits AS
SELECT id, user_id AS engineer_id, address_id, date_start,
       status, 'to' AS visit_type, created_at
FROM visits
UNION ALL
SELECT id, engineer_id, address_id, date_start,
       status, 'mtr' AS visit_type, created_at
FROM mtr_visits;
```

### 3.9. Жизненный цикл визита МТР (статусы)

| Статус | Код | Описание | Кто устанавливает |
| :--- | :--- | :--- | :--- |
| Черновик | `draft` | Инженер сохраняет промежуточный результат | Инженер МТР |
| В работе | `in_progress` | Визит начат, но ещё не завершён | Инженер МТР |
| Завершён | `completed` | Все работы выполнены, фото ПОСЛЕ загружено | Инженер МТР |
| Отправлен | `sent` | Отправлен на проверку ТМ МТР | Инженер МТР (авто при завершении) |
| Отклонён | `rejected` | ТМ вернул на доработку | ТМ МТР |
| Принят | `accepted` | ТМ подтвердил выполнение | ТМ МТР |

**Переходы:**
```
draft → in_progress → completed → sent → accepted
                                  ↓
                              rejected → in_progress → completed → sent
```

**Правила:**
- Из `draft` можно перейти в `in_progress` (начать работы)
- Из `in_progress` можно перейти в `completed` (только если есть Фото ДО + ≥1 работа + Фото ПОСЛЕ)
- Из `completed` автоматически → `sent` (отправка ТМ)
- Из `sent` → `accepted` или `rejected` (решение ТМ)
- Из `rejected` → `in_progress` (инженер дорабатывает)
- Из любого статуса до `sent` можно вернуться назад (удалить фото, работы)
- После `accepted` визит заблокирован для редактирования

## 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ: ИНЖЕНЕР МТР

### 4.1. Список визитов
Инженер МТР видит список своих визитов (аналогично списку визитов ТО, но изолированный):
- Фильтры по статусу: Все / Черновики / В работе / Завершённые / Отклонённые
- Поиск по адресу объекта
- Сортировка по дате (новые сверху)
- Кнопка «+ Добавить визит» (если визит не был создан ТМ МТР)

### 4.2. Создание и редактирование визита
При нажатии кнопки «Добавить визит» (или при открытии назначенного ТМ визита) открывается форма со следующими полями:

1. **Инженер:** ФИО. Заполняется автоматически из профиля. Только для чтения.
2. **№ заявки:** Текстовое поле. **Обязательно для заполнения.**
   * *Валидация (Regex):* `^SD\d{10}$` (начинается с `SD`, далее ровно 10 цифр).
   * *Нормализация:* При потере фокуса автоматически приводится к верхнему регистру.
   * *Уникальность:* Номер заявки должен быть уникальным в рамках `mtr_visits`. При дубликате — ошибка «Заявка с таким номером уже существует».
   * *Пример:* `SD0288019080`
3. **Адрес:** Поле с контекстным поиском (Autocomplete). Ищет по справочнику `addresses`, но выдаёт только те объекты, которые закреплены за текущим ТМ МТР (через `mtr_tm_objects`).
4. **Дата:** Заполняется автоматически текущей датой (редактируемо).
5. **Время:** Заполняется автоматически текущим временем (редактируемо).

*Кнопка «Добавить оборудование» отсутствует.*

### 4.3. Чек-лист «Оказанные услуги» (Страница визита)
По умолчанию в визит МТР добавляется один чек-лист «Оказанные услуги». При переходе в него открывается специализированный интерфейс.

#### 4.3.1. Логика состояний интерфейса (State Machine)

| Состояние | Фото ДО | Работы | Фото ПОСЛЕ | Доступные действия |
| :--- | :---: | :---: | :---: | :--- |
| **1. Начало** | ❌ | ❌ | ❌ | Активна кнопка **«Добавить Фото ДО»**. Кнопка «Добавить работу» **заблокирована**. Кнопка «Завершить» **заблокирована**. Активна кнопка **«Сохранить черновик»**. |
| **2. Фото ДО добавлено** | ✅ | ❌ | ❌ | Активна кнопка **«Добавить работу»**. Кнопка «Завершить» **заблокирована**. Можно **удалить Фото ДО** (возврат в состояние 1). Активна кнопка **«Сохранить черновик»**. |
| **3. Работы добавлены** | ✅ | ✅ | ❌ | Можно добавлять/удалять работы. Можно **удалить все работы** (возврат в состояние 2). Кнопка «Завершить» **заблокирована**. Активна кнопка **«Сохранить черновик»**. |
| **4. Фото ПОСЛЕ добавлено** | ✅ | ✅ | ✅ | Можно **удалить Фото ПОСЛЕ** (возврат в состояние 3). Кнопка **«Завершить визит»** становится **активной**. |

**Важно:** Переходы назад разрешены до момента нажатия «Завершить визит». После завершения визит блокируется.

#### 4.3.2. Добавление работ
* Инженер нажимает «Добавить работу».
* Открывается модальное окно с **контекстным поиском** по справочнику `mtr_work_types`.
* Поиск:
  - Клиентский (по кэшу в IndexedDB) — работает офлайн
  - Частичное совпадение (fuzzy search) по `name`
  - Минимальная длина запроса: 2 символа
  - Debounce: 300 мс
  - Результаты группируются по `category` (если указано)
  - Максимум 50 результатов в выдаче
* Инженер выбирает работу из списка, она добавляется в чек-лист.
* Количество добавляемых работ не ограничено.
* Одна и та же работа может быть добавлена несколько раз (например, «Окраска стен» в разных комнатах) — с указанием `quantity` и/или `comment`.
* Рядом с каждой работой — иконка «Удалить» (🗑️) и поле для комментария.

#### 4.3.3. Сохранение черновика vs Завершение
* **Сохранить черновик:** Визит сохраняется со статусом `draft` (или `in_progress` если работы уже добавлены). ТМ МТР видит его как «В работе (Черновик)». Позволяет инженеру закрыть приложение и продолжить работу на следующий день.
* **Завершить визит:** Визит переходит в статус `completed` → автоматически `sent`. Запускается процесс формирования отчёта и уведомления ТМ МТР.

### 4.4. Офлайн-режим для инженера МТР

#### 4.4.1. Кэширование справочника
* При первом входе справочник `mtr_work_types` (~1000 записей) загружается целиком и сохраняется в IndexedDB (Dexie).
* Обновление: при каждом входе проверяется `updated_at` на сервере. Если данные обновились — загружается только дельта.
* Размер кэша: ~50-100 КБ (приемлемо для мобильного интернета).

#### 4.4.2. Работа без связи
* **Черновики:** сохраняются в IndexedDB (`mtrVisits` table). При восстановлении связи — синхронизация с сервером.
* **Фото:** загружаются в локальное хранилище, добавляются в очередь синхронизации. При появлении связи — отправка на сервер.
* **Работы:** добавление/удаление работает локально, синхронизируется при связи.
* **Конфликты:** если ТМ МТР удалил визит, пока инженер был офлайн — при синхронизации визит помечается как «Удалён администратором», данные сохраняются в локальном архиве.

#### 4.4.3. Индикация офлайн-режима
* В интерфейсе отображается индикатор «Офлайн» (аналогично существующему для ТО).
* При сохранении в офлайн — уведомление «Сохранено локально. Будет отправлено при восстановлении связи».

## 5. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ: ТМ МТР

Функционал ТМ МТР зеркально повторяет функционал ТМ ТО, но работает исключительно в контуре МТР:

1. **Дашборд:** Статистика по заявкам МТР (Новые, В работе, Черновики, Завершённые, Отклонённые).
2. **Список визитов:** Просмотр визитов МТР своих инженеров. Фильтры по статусу, инженеру, адресу, № заявки.
3. **Управление визитами:**
   - Создание визита и назначение инженера МТР из своего списка подчинённых
   - Редактирование визитов в статусе `draft` / `in_progress`
   - Удаление визитов (мягкое удаление, аналогично ТО)
4. **Приёмка работ:**
   - Просмотр завершённого визита (Фото ДО + список работ + Фото ПОСЛЕ)
   - Кнопка «Принять» → статус `accepted`
   - Кнопка «Отклонить» → статус `rejected` + поле «Причина отклонения» (обязательное)
   - Уведомление инженеру при отклонении
5. **Отчетность:**
   - Формирование сводных отчётов по МТР (за период, по объектам, по номерам заявок SD)
   - Формат отчёта: PDF (аналогично ТО)
   - Структура отчёта МТР: общие сведения (№ заявки, адрес, дата, инженер) + список выполненных работ + фото ДО и ПОСЛЕ. Подписи и печати не требуются
6. **Уведомления:** Push-уведомления для ТМ МТР и инженера МТР — по аналогии с модулем ТО (назначение визита, отклонение, завершение)
7. **Доступ к объектам:** При создании визита ТМ МТР выбирает объект из общего справочника `addresses`, но выпадающий список отфильтрован только по объектам, закрепленным за данным ТМ МТР (через `mtr_tm_objects`).

## 6. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ: АДМИНИСТРАТОР

### 6.1. Управление справочником «Виды работ МТР»
* Администратор имеет доступ к разделу «Справочники → Виды работ МТР».
* **CRUD операции:** Создание, редактирование, деактивация записей.
* **Массовый импорт:** Загрузка из Excel (`.xlsx`).
  - Формат: колонка `name` (обязательно), `category` (опционально). Первая строка — заголовок.
  - Обработка дубликатов: дубликаты по `name` (case-insensitive) пропускаются с указанием в логе.
* **Экспорт:** Выгрузка текущего справочника в Excel.

### 6.2. Управление привязками МТР
* **Привязка объектов к ТМ МТР:** аналогично привязкам ТО, но через отдельный интерфейс (таблица `mtr_tm_objects`).
* **Привязка инженеров к ТМ МТР:** аналогично ТО (таблица `mtr_tm_engineers`).
* При создании пользователя с ролью `mtr_tm` или `engineer_mtr` — он попадает только в соответствующие таблицы привязок.

### 6.3. Глобальный доступ
* Администратор видит все визиты (ТО и МТР) через `VIEW all_visits`.
* Может просматривать детали визита МТР (фото, работы).
* Может переназначать объекты между ТМ ТО и ТМ МТР.
* Может деактивировать/активировать пользователей МТР.

## 7. НАЧАЛЬНОЕ НАПОЛНЕНИЕ СПРАВОЧНИКА

Справочник `mtr_work_types` должен быть первоначально наполнен данными, предоставленными Заказчиком.
*(Полный список из ~1000 позиций импортируется в БД на этапе развертывания).*

**Обработка дубликатов при импорте:** В предоставленном списке обнаружены повторяющиеся записи (например, «Обмазочная гидроизоляция в 1 слой» встречается в нескольких секциях). При импорте:
- Дубликаты по `name` (case-insensitive, trim) объединяются в одну запись
- В логе импорта указывается количество объединённых дубликатов
- Администратор может вручную разделить записи после импорта

**Категоризация:** При импорте категории определяются по контексту секции справочника (полы, стены, потолки, двери, окна, кровля, фасады и т.д.). Если категория не определена — `category = NULL`.

## 10. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 10.1. Изоляция данных
- Таблица `visits` и все связанные таблицы ТО **не изменяются**
- Модуль МТР имеет собственный набор таблиц
- При добавлении новых ролей — создаются новые таблицы по тому же принципу
- Администратор видит все визиты через `VIEW all_visits`

### 10.2. Фото
- Переиспользуется существующая таблица `photos`
- Добавляется поле `mtr_visit_id` (полиморфная связь)
- Для ТО: `task_id` / `task_equipment_item_id` заполнены
- Для МТР: `mtr_visit_id` заполнен
- Единый код загрузки, хранения и синхронизации фото

### 10.3. Офлайн-режим
- Справочник `mtr_work_types` кэшируется целиком в IndexedDB (Dexie)
- Черновики визитов МТР сохраняются локально
- Фото сохраняются локально, отправляются при восстановлении связи
- Обновление справочника — дельта по `updated_at`
- Конфликты — пометка «Удалён администратором» + локальный архив

### 10.4. Мобильная адаптация
Все страницы модуля МТР адаптируются по тем же правилам, что и модуль ТО:
- Целевая ширина экрана: 393px (CSS) как минимум
- Адаптивные таблицы с `scroll={{ x }}` и фиксированными ширинами колонок
- Кнопка камеры: `capture="environment"` на `input type="file"`
- Горизонтальные группы кнопок → вертикально на мобильном (`flexDirection: column`)
- Кнопка «Назад» — стрелка слева от заголовка (`showBack` + `onBack` в MobileHeader)
- PWA-баннер обновления — тёмный фон, белая кнопка с синим текстом

### 10.5. Быстродействие
- Поиск по справочнику — клиентский (IndexedDB), мгновенный
- Серверный поиск — только для админа при управлении справочником
- Индексы на `mtr_visits`: `engineer_id`, `address_id`, `status`, `request_number`
- Индексы на `mtr_visit_works`: `mtr_visit_id`
- Индексы на `photos`: `mtr_visit_id`

## 11. ПОЛЬЗОВАТЕЛЬСКОЕ ОПИСАНИЕ ДОРАБОТКИ

В приложении необходимо добавить новую роль «Инженер МТР» (инженер по мелкому текущему ремонту) и Территориального менеджера (ТМ) МТР.

Мелкий текущий ремонт — это комплекс работ, направленный на устранение незначительных неисправностей и поддержание объекта (здания, оборудования, помещения) в исправном состоянии. Его цель — не масштабное обновление, а оперативное исправление мелких дефектов, чтобы предотвратить более серьёзные поломки и обеспечить нормальную эксплуатацию.

Примером мелкого текущего ремонта является ремонт офисной мебели, ремонт покрытия крыльца, ремонт напольного покрытия и т.д.

Эти роли изолированы от других инженеров с различными специализациями и ТМ. При этом для ТМ МТР должны быть доступны объекты из общего справочника объектов, но заявки ТМ не должны быть видны для ТМ МТР и наоборот. Аналогично с Инженерами МТР, они подчиняются только ТМ МТР. Администратор может видеть всё.

**Основной сценарий работы Инженера МТР:**

Инженер МТР нажимает кнопку «Добавить визит» (если он не был добавлен ТМ МТР). При переходе в визит отображаются поля:
- **Инженер:** ФИО, заполняется автоматически по данным профиля.
- **№ заявки:** поле для ввода номера заявки. **Обязательно!** Формат: `SD` + 10 цифр (может начинаться с 0). Пример: `SD0288019080`. При вводе автоматически приводится к верхнему регистру. Проверяется уникальность.
- **Адрес:** контекстный поиск по справочнику адресов, доступных ТМ МТР.
- **Дата:** фиксируется дата начала работ.
- **Время:** фиксируется время начала работ.

Кнопки «Добавить оборудование» (как у Инженера ТО) у Инженера МТР нет.

Вместо этого, в визите Инженера по умолчанию добавляется чек-лист «Оказанные услуги», при переходе в который открывается страница, где Инженер МТР должен:
1. В первую очередь добавить фотографию объекта **до** начала ремонта
2. После загрузки фото ДО становится доступным добавление работ из справочника «Виды работ МТР» (контекстный поиск, работает офлайн)
3. Добавить необходимое количество работ (не ограничено, одна работа может повторяться)
4. Добавить фотографию **после** (результат ремонта)
5. После загрузки фото ПОСЛЕ становится активной кнопка «Завершить визит»

До добавления «Фото ДО» инженер не может добавить какую-либо работу. До добавления «Фото ПОСЛЕ» можно только сохранять промежуточный результат (черновик), так как работы могут быть выполнены не за одно посещение объекта, а за несколько (например, при ремонте стены: очистить → зашпаклевать → покрасить).

Функционал по отчётам и заявкам для ТМ МТР аналогичен тому, как это реализовано у ТМ по техническому обслуживанию. ТМ МТР может принять или отклонить визит (с указанием причины отклонения).
