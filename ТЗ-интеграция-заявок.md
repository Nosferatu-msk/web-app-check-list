# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на интеграцию внешнего перечня заявок с приложением «Чек-лист инженера»

**Версия:** 2.0  
**Дата:** 25.07.2026  
**Статус:** Проект

---

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Назначение
Настоящее ТЗ описывает функциональность импорта перечня заявок из внешнего сервиса (в формате Excel) и автоматического создания визитов в приложении «Чек-лист инженера» на основе этих заявок. Модуль обеспечивает связку между системой управления заявками заказчика и полевым исполнением работ инженерами.

### 1.2. Цели
- Автоматизировать создание визитов на основе внешних заявок.
- Исключить ручной ввод данных об объекте и оборудовании.
- Обеспечить контроль соответствия специализации инженера виду оборудования в заявке.
- Предоставить ТМ и Администратору возможность формировать сводные отчёты по номерам заявок.
- Уведомлять инженеров о новых назначенных задачах.

### 1.3. Источник данных
Excel-файл, выгружаемый из внешнего сервиса заявок, со следующей структурой:

| Колонка | Описание | Пример |
|---------|----------|--------|
| № заявки | Уникальный идентификатор заявки во внешней системе | `IS130366092` |
| Статус | Статус заявки во внешней системе | `Новая` |
| Вид оборудования | Тип оборудования, по которому требуется ТО | `Внутренний блок СС` |
| Код объекта | Аналитический код объекта (формат `RU/76/57`) | `RU/76/57` |
| Адрес | Полный адрес объекта | `г Ярославль, ул Серго Орджоникидзе, 37к2` |

## 2. РОЛИ И ПРАВА ДОСТУПА

| Роль | Права в модуле заявок |
|------|----------------------|
| **Администратор** | Импорт Excel, просмотр всех заявок, назначение/снятие инженеров на любые заявки, формирование отчётов по любым заявкам |
| **Территориальный менеджер (ТМ)** | Импорт Excel, просмотр заявок по объектам своей территории, назначение инженеров из своей группы, формирование отчётов по заявкам своей территории |
| **Инженер** | Просмотр назначенных ему заявок, получение уведомлений, переход к визиту по ссылке из уведомления, отказ от заявки с указанием причины |

## 3. СТРУКТУРА ДАННЫХ

### 3.1. Новая таблица `imported_requests` (импортированные заявки)

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|:-----------:|
| `id` | UUID | Первичный ключ | PK |
| `external_request_id` | VARCHAR(100) | № заявки из внешней системы | NOT NULL, UNIQUE |
| `external_status` | VARCHAR(100) | Статус из внешней системы | |
| `equipment_type_id` | UUID | FK → equipment_types.id (найденный вид оборудования) | NOT NULL |
| `equipment_type_code` | VARCHAR(50) | Код вида оборудования (denormalized, для отладки) | |
| `object_code` | VARCHAR(50) | Код объекта из заявки | NOT NULL |
| `address_raw` | TEXT | Адрес из заявки (как есть) | |
| `matched_address_id` | UUID | FK → addresses.id (найденный объект) | NULL если не найден |
| `visit_id` | UUID | FK → visits.id (созданный визит) | NULL до создания визита |
| `import_status` | VARCHAR(20) | Статус обработки: `new` / `matched` / `created` / `error` / `skipped` | DEFAULT 'new' |
| `error_message` | TEXT | Причина ошибки (если есть) | |
| `imported_by` | UUID | FK → users.id (кто импортировал) | |
| `imported_at` | TIMESTAMP | Дата импорта | |
| `created_at` | TIMESTAMP | Дата создания записи | |

> **Примечание:** `equipment_type_id` — это UUID FK на `equipment_types.id`, что согласуется с существующими паттернами (как `task.equipment_type_id`, `object_equipment.equipment_type_code`). Поле `equipment_type_code` хранится как denormalized для быстрого доступа и отладки.

### 3.2. Расширение таблицы `visits`

Добавляются поля для связи с заявками и поддержки множественного назначения:

```sql
-- Новый статус визита
ALTER TYPE "VisitStatus" ADD VALUE 'awaiting_assignment';

-- Поля для визитов из заявок
ALTER TABLE visits
  ADD COLUMN is_multi_specialist BOOLEAN DEFAULT FALSE;
```

> **Важно:** Поле `external_request_id` **не добавляется** в `visits`. Связь визита с заявками осуществляется через `imported_requests.visit_id`. Это исключает дублирование: при группировке нескольких заявок в один визит связь хранится в одной таблице, а не в нескольких местах.

> **Поле `userId` визита:** для визитов, созданных из заявок, `userId` устанавливается в `NULL` до момента назначения инженера. После назначения основного инженера — `userId` заполняется. Визит со статусом `awaiting_assignment` имеет `userId = NULL`.

### 3.3. Новая таблица `visit_engineers` (множественное назначение)

Связующая таблица для визитов с несколькими инженерами (визиты вида «ИСЖ объекта» и аналогичные):

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|:-----------:|
| `id` | UUID | Первичный ключ | PK |
| `visit_id` | UUID | FK → visits.id | NOT NULL |
| `engineer_id` | UUID | FK → users.id | NOT NULL |
| `is_primary` | BOOLEAN | Основной инженер (заполняет `visits.userId`) | DEFAULT false |
| `assigned_by` | UUID | FK → users.id (кто назначил) | |
| `assigned_at` | TIMESTAMP | Дата назначения | |
| `created_at` | TIMESTAMP | Дата создания записи | |

- Уникальность: `(visit_id, engineer_id)`
- Для **обычных визитов** (один инженер): одна запись в `visit_engineers` с `is_primary = true`, и `visits.userId` = `engineer_id`.
- Для **визитов «ИСЖ объекта»** (несколько инженеров): несколько записей, одна с `is_primary = true`.
- При назначении основного инженера — обновляется `visits.userId` и `visits.engineerName`.

### 3.4. Новая таблица `request_assignment_log` (история назначений)

Хранит историю всех действий по назначению/снятию инженеров:

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|:-----------:|
| `id` | UUID | Первичный ключ | PK |
| `imported_request_id` | UUID | FK → imported_requests.id | NOT NULL |
| `action` | VARCHAR(20) | `assigned` / `unassigned` / `declined` | NOT NULL |
| `engineer_id` | UUID | FK → users.id (кем/кого) | |
| `performed_by` | UUID | FK → users.id (кто выполнил) | |
| `reason` | TEXT | Причина (для отказа/снятия) | |
| `created_at` | TIMESTAMP | Дата действия | |

### 3.5. Расширение таблицы `tasks`

```sql
ALTER TABLE tasks
  ADD COLUMN external_request_id VARCHAR(100);  -- связь задачи с заявкой
```

> Поле нужно, потому что в одном визите могут быть задачи из разных заявок, и важно знать, какая задача из какой заявки.

### 3.6. Расширение enum `NotificationType`

Добавляются новые типы уведомлений:

```typescript
type NotificationType =
  | ... // существующие типы
  | 'request_assigned'       // инженер назначен на заявку
  | 'request_unassigned'     // инженер снят с заявки
  | 'request_declined'       // инженер отказался от заявки (уведомление ТМ)
  | 'request_imported';      // новые заявки импортированы (уведомление ТМ)
```

## 4. ФОРМАТ ИМПОРТА EXCEL

### 4.1. Требования к файлу

- **Формат:** `.xlsx` (Microsoft Excel 2007+)
- **Кодировка:** UTF-8
- **Первая строка:** заголовки столбцов (обязательно)
- **Разделитель:** стандартный Excel
- **Лимит:** до 5 000 строк за одну загрузку

### 4.2. Обязательные столбцы

| № | Название столбца | Тип данных | Валидация |
|---|------------------|------------|-----------|
| 1 | `№ заявки` | Текст | Не пустое, уникальное в файле |
| 2 | `Статус` | Текст | Не пустое |
| 3 | `Вид оборудования` | Текст | Должен соответствовать наименованию в справочнике `equipment_types` |
| 4 | `Код объекта` | Текст | Формат `RU/NN/NNN` (например `RU/76/57`) |
| 5 | `Адрес` | Текст | Не пустое |

### 4.3. Нормализация данных при импорте

#### 4.3.1. Вид оборудования

Поиск по полю `name` в справочнике `equipment_types` (регистронезависимо, с trim пробелов). Если не найден — строка помечается как ошибочная.

> **Важно:** требуемая специализация определяется по существующему полю `equipment_type.specialization_req`, а не по хардкод-матрице. Это единый источник истины.

#### 4.3.2. Код объекта (приоритетный поиск)

Поиск по полю `object_code` в справочнике `addresses` (точное совпадение, регистронезависимо). **Код объекта — первичный ключ поиска.** Если код найден — объект считается найденным, даже если адрес незначительно отличается.

#### 4.3.3. Адрес (вспомогательный поиск)

Если код объекта не найден — попытка поиска по адресу:

1. **Нормализация адреса** (применяется и к адресу из Excel, и к адресу из справочника):
   - Удаление лишних пробелов (двойные → одинарные, trim по краям)
   - Приведение сокращений к единому формату:
     - `г.` → `г `, `г.` (с пробелом) → `г `
     - `ул.` → `ул `, `улица` → `ул `
     - `д.` → ``, `дом` → ``
     - `к.` / `корп.` / `корпус` → `к`
     - `стр.` / `строение` → `стр`
   - Удаление слов-паразитов: `Россия`, `РФ`, почтовые индексы
   - Приведение к нижнему регистру для сравнения

2. **Сравнение:** если нормализованный адрес из Excel совпадает с `full_address` хотя бы одного объекта — объект найден.

3. **Если не найден ни по коду, ни по адресу** — строка помечается как `error` с причиной «Объект не найден». Заявка помещается в очередь на ручную обработку (раздел 4.4).

### 4.4. Очередь на ручную обработку

Заявки со статусом `error` (объект не найден) доступны в интерфейсе ТМ/Админа:
- Отображаются в отдельной вкладке «Ошибки импорта».
- ТМ может вручную привязать заявку к существующему объекту (выбор из справочника).
- Админ может создать новый объект (адрес) на основе данных заявки и привязать заявку.
- После ручной привязки статус меняется на `matched`, и визит создаётся автоматически.

### 4.5. Асинхронная обработка больших файлов

Для файлов объёмом более ~100 строк импорт выполняется **асинхронно** (фоновая задача):
1. Клиент загружает файл → сервер создаёт запись `import_log` со статусом `processing`.
2. Сервер возвращает клиенту ID задачи импорта.
3. Клиент опрашивает статус (`GET /api/imports/:id/status`) каждые 2 секунды.
4. После завершения — клиент показывает отчёт об импорте.

Это предотвращает таймаут HTTP при обработке 5000 строк (оценка: 30–60 секунд).

## 5. ЛОГИКА СОЗДАНИЯ ВИЗИТОВ ИЗ ЗАЯВОК

### 5.1. Алгоритм обработки строки импорта

```
Для каждой строки файла:
  1. Проверить уникальность № заявки (в БД и в текущем файле)
  2. Найти вид оборудования по наименованию (в equipment_types)
  3. Найти объект по коду (приоритет) или по нормализованному адресу
  4. Если заявка уже существует (по external_request_id) → статус 'skipped'
  5. Если вид оборудования не найден → статус 'error', причина: "Вид оборудования не найден"
  6. Если объект не найден → статус 'error', причина: "Объект не найден" (→ очередь, см. 4.4)
  7. Создать запись в imported_requests со статусом 'matched'
  
  // Группировка по объекту:
  8. Проверить, существует ли уже визит на этот объект (созданный в рамках ТЕКУЩЕГО импорта)
  9. Если визит уже есть → добавить задачу в существующий визит (шаг 11)
  10. Если визита нет → создать визит (visit) со статусом 'awaiting_assignment', userId = NULL
  11. Создать задачу (task) для указанного вида оборудования, сохранить external_request_id в task
  12. Обновить imported_requests: visit_id, статус 'created'
```

### 5.2. Группировка заявок по объекту

**Правило:** если на один объект (`object_code`) в одном файле приходит несколько заявок с **разным видом оборудования**, система создаёт **один визит** на объект, в который добавляются **несколько задач** (по одной на каждый вид оборудования).

**Пример:**
- Заявка 1: `Внутренний блок СС`, объект `RU/76/57`
- Заявка 2: `Наружный блок СС`, объект `RU/76/57`
- Заявка 3: `РЩ/ГРЩ`, объект `RU/76/57`

→ Создаётся **1 визит** на объект `RU/76/57` со статусом `awaiting_assignment` и **3 задачами**.

### 5.3. Визиты с разными специализациями

Если заявки на один объект требуют **разных специализаций** (например, ВиК + ИСЖ + ГПМ):
- Создаётся **один визит** с `is_multi_specialist = TRUE`.
- Визит имеет статус `awaiting_assignment` (ожидает назначения).
- ТМ назначает нескольких инженеров — по одному на каждую специализацию (см. раздел 6).
- Основной инженер (`is_primary = true`) — первый назначенный. Его ID записывается в `visits.userId`.

### 5.4. Исключение — вид оборудования "ИСЖ объекта"

Для вида оборудования **"ИСЖ объекта"** (специальный тип, см. раздел 9):
- Создаётся визит на объект со статусом `awaiting_assignment`.
- **Задачи (чек-листы) НЕ создаются** — их добавит инженер на месте.
- Визит помечается флагом `is_multi_specialist = TRUE`.

### 5.5. Жизненный цикл визита из заявки

```
  Импорт → [awaiting_assignment] → Назначение инженера → [planned] → ...
                                         ↓
                                   (если ИСЖ объекта) → несколько инженеров
                                         ↓
                                   Инженер начинает работу → [in_progress] → ...
```

Новый статус `awaiting_assignment` означает: визит создан, задачи добавлены, но инженер ещё не назначен. Визит в этом статусе:
- Видим ТМ в списке «ожидающих назначения».
- Не виден инженеру (ему ещё не назначили).
- Не имеет `userId` и `engineerName`.

## 6. ЛОГИКА НАЗНАЧЕНИЯ ИНЖЕНЕРОВ

### 6.1. Определение требуемой специализации

Требуемая специализация определяется по полю `equipment_type.specialization_req` того вида оборудования, который указан в задаче визита.

> **Единый источник истины** — поле `specialization_req` в справочнике `equipment_types`. Значения должны быть заполнены при seed (проверить и при необходимости обновить seed-скрипт).

**Ожидаемые значения `specialization_req`:**

| Значение | Расшифровка |
|----------|-------------|
| `vik` | ВиК (вентиляция и кондиционирование) |
| `iszh` | ИСЖ (инженерные сети и электрика) |
| `gpm` | ГПМ (грузоподъёмные механизмы) |
| `dgu` | ДГУ (дизель-генераторные установки) |
| `ibp` | ИБП (источники бесперебойного питания) |

### 6.2. Алгоритм валидации при назначении

```
При назначении инженера на заявку/визит:
  1. Определить требуемую специализацию:
     - Для обычной задачи → task.equipmentType.specialization_req
     - Для визита с несколькими задачами → для каждой задачи своя специализация
  2. Если вид = "ИСЖ объекта" (specialization_req = NULL или 'any') → пропустить проверку
  3. Проверить, есть ли у инженера нужная специализация 
     (specialization_vik/iszh/gpm/dgu/ibp = TRUE)
  4. Если нет → вернуть ошибку: 
     "Инженер [ФИО] не имеет специализации [требуемая]. 
      Назначение невозможно."
  5. Если да → создать запись в visit_engineers
  6. Если это первый инженер → обновить visits.userId, visits.engineerName, 
     статус визита → 'planned'
  7. Отправить уведомление инженеру (request_assigned)
  8. Записать в request_assignment_log: action = 'assigned'
```

### 6.3. Множественное назначение

- На **обычную заявку** (одна задача, одна специализация) — **один** инженер.
- На заявку вида **"ИСЖ объекта"** — **два и более** инженеров с **разными** специализациями.
- На **визит с несколькими задачами разных специализаций** — по одному инженеру на каждую специализацию.
- ТМ/Админ видит список назначенных инженеров в карточке заявки.

### 6.4. Отмена назначения

ТМ/Админ может снять назначение инженера:
1. Удалить запись из `visit_engineers`.
2. Если снят основной инженер — `visits.userId` очищается, статус → `awaiting_assignment`.
3. Если engineers пуст — визит возвращается в `awaiting_assignment`.
4. Отправить уведомление инженеру (`request_unassigned`).
5. Записать в `request_assignment_log`: action = 'unassigned', reason (опционально).

### 6.5. Отказ инженера от заявки

Инженер может отказаться от назначенной заявки:
1. Инженер нажимает «Отказаться» в интерфейсе, указывает причину (обязательно).
2. Запись в `visit_engineers` помечается (или удаляется).
3. Визит возвращается в `awaiting_assignment` (если это был единственный инженер).
4. ТМ получает уведомление (`request_declined`) с причиной отказа.
5. Записать в `request_assignment_log`: action = 'declined', reason.

### 7.1. Каналы уведомлений

| Канал | Когда срабатывает | Приоритет реализации |

| Тип | Получатель | Содержимое |


При переходе по ссылке PWA открывается даже если было свёрнуто.

## 9. ОСОБЫЙ СЛУЧАЙ: "ИСЖ ОБЪЕКТА"

### 9.1. Описание

Вид оборудования **"ИСЖ объекта"** — это специальная заявка, означающая "провести обслуживание всех инженерных сетей и электрики на объекте". Используется, когда точный состав оборудования неизвестен заранее.

### 9.2. Отличия от обычных заявок

| Параметр | Обычная заявка | "ИСЖ объекта" |
|----------|----------------|---------------|
| Создание чек-листа при импорте | ✅ Да | ❌ Нет |
| Количество назначаемых инженеров | 1 | 2+ |
| Требуемая специализация | Конкретная (из `specialization_req`) | Любая |
| Кто формирует состав работ | Система (по заявке) | Инженер на месте |

### 9.3. Сценарий работы

1. ТМ импортирует заявку с видом "ИСЖ объекта".
2. Система создаёт визит на объект **без задач**, статус `awaiting_assignment`, `is_multi_specialist = TRUE`.
3. ТМ назначает на визит двух инженеров: один со специализацией ВиК, второй — ИСЖ.
4. Оба инженера получают уведомление (`request_assigned`).
5. Приехав на объект, каждый инженер добавляет в визит задачи по своей специализации (через стандартный механизм добавления оборудования).
6. Визит завершается, когда все задачи выполнены.

## 10. СВОДНЫЙ ОТЧЁТ ПО ЗАЯВКАМ

### 10.1. Новый способ формирования отчёта

Помимо существующих способов (за период, по объекту), добавляется способ **"По номерам заявок"**.

### 10.2. Интерфейс выбора

```
┌─────────────────────────────────────────────────────────────┐
│  СВОДНЫЙ ОТЧЁТ                                              │
├─────────────────────────────────────────────────────────────┤
│  СПОСОБ ФОРМИРОВАНИЯ:                                       │
│  ( ) За период                                              │
│  ( ) По объектам                                            │
│  (x) По номерам заявок                                      │
├─────────────────────────────────────────────────────────────┤
│  НОМЕРА ЗАЯВОК:                                             │
│  [IS130366092, IS130366093, IS130366094________]           │
│                                                             │
│  Найдено заявок: 3                                          │
│  Объектов: 2                                                │
│  Инженеров: 2                                               │
│                                                             │
│  [📄 СФОРМИРОВАТЬ PDF]  [📊 СФОРМИРОВАТЬ EXCEL]            │
└─────────────────────────────────────────────────────────────┘
```

### 10.3. Структура отчёта

Отчёт по заявкам имеет ту же структуру, что и отчёт по объектам (раздел 7 основного ТЗ), но:
- В шапке указывается: «Отчёт сформирован по заявкам: IS130366092, IS130366093, ...»
- Визиты группируются по объектам.
- В каждой задаче указывается № заявки (из `task.external_request_id`).
- Включаются превью фотографий и сканы актов (как в обычных отчётах).
- Указывается внешний статус заявки (из `imported_requests.external_status`).
