## 1. Критические проблемы (требуют исправления до начала разработки)

### 1.1. Ссылки на удалённые файлы
Спецификация ссылается на файлы, которые больше не существуют по указанным путям:
- `mobile/mockups/mockups-final-v1.html` → перенесён в `mockups-mobile-v1.html`
- `mobile/DESIGN_RULES.md` → удалён вместе с папкой `mobile/`

**Решение:** обновить ссылки в спецификации. Файл `DESIGN_RULES.md` нужно либо восстановить из макета, либо описать правила заново.

### 1.2. Серверный endpoint `POST /api/sync/batch` не реализован
Оба документа указывают его как **P0-зависимость** для Этапа 4. Без него офлайн-синхронизация невозможна.

**Решение:** включить разработку batch-sync endpoint в план работ по серверу до начала Этапа 4 мобильного приложения.

### 1.3. Нет SQLite-схемы для модуля МТР
ТЗ описывает роль «Инженер МТР» с приоритетом P0, но SQLite-схема в спецификации (§6) содержит только таблицы для ТО-визитов. Нет таблиц для:
- `mtr_visits`
- `mtr_tasks`
- `mtr_works`
- `mtr_work_types`

**Решение:** дополнить SQLite-схему таблицами для МТР по аналогии с Prisma-схемой сервера.

## 2. Значительные проблемы

### 2.1. Не описана миграция SQLite-схемы
При обновлении приложения структура БД может меняться (новые поля, таблицы). Не описано:
- Механизм версионирования схемы (migration version в таблице)
- Стратегия миграции данных (ALTER TABLE vs пересоздание)
- Обработка ошибок миграции

**Решение:** добавить раздел «Миграции SQLite» в спецификацию.

### 2.2. Не описана стратегия очистки данных
SQLite на устройстве имеет ограниченный объём. Не описано:
- Когда удалять завершённые визиты старше N дней?
- Когда удалять загруженные фото из File System?
- Максимальный размер кеша справочников?

**Решение:** добавить раздел «Управление хранилищем» с правилами очистки.

### 2.3. Не описана обработка прерываний синхронизации
Если синхронизация прерывается (убийство процесса, разрядка батареи):
- Как восстановить состояние sync_queue?
- Как избежать частичной отправки batch?

**Решение:** описать механизм recovery: при старте приложения проверять sync_queue на status='in_progress' → сбрасывать в 'pending'.

### 2.4. Расхождение: групповые задачи (group_climate) в офлайн
ТЗ и спецификация описывают группировку климатического оборудования (`group_climate`), но:
- Не описано, как групповая задача хранится в SQLite (одна запись или несколько?)
- Не описана синхронизация групповой задачи через batch endpoint
- Не описан конфликт: если на сервере задачи уже разгруппированы

**Решение:** уточнить модель хранения групповых задач в SQLite и протокол синхронизации.

### 2.5. Не описана авторизация при истечении refresh token в офлайн
Если refresh token истёк, а интернета нет:
- Инженер не может войти
- Но данные в SQLite доступны

**Решение:** описать поведение: показывать экран «Нет интернета и истёк срок сессии. Данные сохранены локально.» + кнопка «Работать офлайн» (read-only доступ к последнему визиту).

## 3. Незначительные проблемы

### 3.1. Избыточный padding-bottom
Спецификация указывает `padding-bottom: 130px` для экранов с tab bar. Это много — на экране 393×800 это ~16% экрана.

**Решение:** пересчитать: tab bar 63px + nav bar 42px + зазор 8px = 113px. Использовать 113px вместо 130px.

### 3.2. Нет описания swipe-to-delete для карточек
В PWA визиты удаляются через кнопку с подтверждением. В мобильном приложении ожидается swipe-to-delete (стандарт Android), но он не описан.

**Решение:** добавить описание жеста или явно указать, что удаление — только через кнопку.

### 3.3. Нет i18n-модуля в технологическом стеке
Спецификация (§15) требует: «Все строки UI — через i18n-модуль». Но в стеке (§2) нет i18n-библиотеки.

**Решение:** добавить `i18next` + `react-i18next` в стек, либо упростить: использовать константы в отдельном файле `src/constants/strings.ts`.

### 3.4. Не описана анимация перехода между экранами
Android-стандарт — slide-right для push, slide-left для pop. Не описано:
- Использовать ли стандартные анимации Expo Router?
- Нужны ли кастомные анимации для модалок (камера, выбор оборудования)?

**Решение:** указать: использовать стандартные анимации Expo Router. Для модалок — `presentation: 'modal'`.

## 4. Положительные стороны

✅ **Хорошо проработанная офлайн-архитектура** — очередь мутаций, идемпотентность, conflict resolution  
✅ **Детальные user stories** — понятны сценарии использования, критерии приёмки  
✅ **Переиспользование кода из PWA** — чётко указано, что можно переиспользовать (shared/types, валидация)  
✅ **Тестовые устройства** — указаны конкретные модели, разрешения, RAM  
✅ **Метрики производительности** — целевые значения для ключевых операций  
✅ **Безопасность** — Secure Store, auto-lock, запрет логирования токенов

## 5. Рекомендации по улучшению

### 5.1. Добавить раздел «Мониторинг и алертинг»
- Какие метрики собирать (crash-free rate, sync success rate, avg sync time)
- Пороги алертов (crash-free rate < 95% → алерт)
- Каналы алертов (Telegram, email)

### 5.2. Добавить раздел «Backup и восстановление»
- Что происходит при переустановке приложения?
- Как восстановить данные, если устройство потеряно?
- Нужно ли экспортировать данные визитов локально?

### 5.3. Уточнить ролевую модель для МТР
ТЗ описывает «Инженер МТР» и «ТМ МТР», но функциональные требования (§4) описывают только ТО-процессы. Нужно:
- Добавить user stories для МТР-инженера (отличия от ТО: работы вместо параметров, другие формы)
- Указать, какие экраны МТР идентичны ТО, а какие отличаются

### 5.4. Добавить раздел «Обработка ошибок сети»
- Таймауты запросов (сколько секунд?)
- Повторные запросы при 5xx (сколько раз?)
- Поведение при 401/403 (принудительный logout?)
